## 一图看懂本篇流程


EVM 像一台按步骤执行的自动售货机：输入交易和当前状态，程序逐条运行；每一步消耗 Gas。执行失败时状态按规则回滚。

> **怎么读这张图：**从左向右看，先确认输入是什么，再看系统如何检查和处理，最后看结果如何保存或验证。图中是帮助理解的简化流程，协议细节仍以本篇后续说明和官方规范为准。


例如，自动售货机每执行一步都会消耗电力和机械资源。EVM 的 Gas 用来计量执行成本；程序出错回滚时，已消耗的执行资源仍需按规则计费。

可以按以下三组问题把教材概念变成区块链判断。

第一组是**完整性与保密性**：交易哈希或状态根可以发现替换，但不会隐藏公开交易；签名可以证明密钥授权，但不加密金额；某个协议使用零知识证明，也要看公开输入和发布数据后才能判断用户隐私。

第二组是**原语与协议**：ECDSA 或 BLS 的数学验证通过，只能说明被验证消息和公钥满足相应关系。链 ID、分叉域、nonce、账户权限与业务金额如何进入消息，属于协议设计。丢掉这些字段，底层原语再强也可能允许跨用途重放。

第三组是**计算证据与世界事实**：Merkle 证明可以把余额绑定到状态根，证明系统可以把新根绑定到规定计算，但根的规范性、预言机价格的现实意义、合约管理员的权限与数据长期可用性仍需额外机制。这些关键在于不同保证需要不同输入和假设。

## 三、附录 C：20 道复习题与参考答案

<a id="sec-034"></a>
### 3.1 为什么主网 Merge 后用户不必把 ETH 兑换成 ETH2？

**答：**ETH2 是历史升级叙事中的名称。Merge 改变区块生产与共识协作方式，执行层的账户和资产历史继续存在。执行层与共识层是职责分工，不是要求用户迁移到另一种必须兑换的代币。

<a id="sec-035"></a>
### 3.2 2013 与 2014 两个白皮书日期为什么不一定互相矛盾？

**答：**早期构想、草稿传播、后来整理的网页版本和正式历史条目可能指不同事件。本文把 2013 年起源与当前官网保留白皮书版本的描述分开，不把某个版本的页面日期机械套成全部思想出现的唯一日期。

<a id="sec-036"></a>
### 3.3 Shanghai 和 Capella 分别对应哪一层？

**答：**Shanghai 是执行层升级名称，Capella 是共识层名称，合称 Shapella。提款要跨越共识验证者余额与执行账户余额两类状态，因而不能只用一层的名称解释全部处理。

<a id="sec-037"></a>
### 3.4 为什么 slot 65 不意味着执行块高度为 65？

**答：**slot 是时间位置，可能没有块；执行块高度只随有效父子执行块递增。两种计数的起点和是否允许空位也不同。65 可以用来定位 epoch 内位置，但不能直接推导执行高度。

<a id="sec-038"></a>
### 3.5 钱包将交易提交给第三方 RPC，为什么无需交出私钥？

**答：**签名在钱包或授权签名器完成。节点依据签名恢复或验证发送者并检查交易规则，只需要公钥相关验证信息和交易字节。发送私钥不是协议验证的输入要求。

<a id="sec-039"></a>
### 3.6 执行客户端认为某个载荷有效，是否意味着它已经最终确定？

**答：**不意味着。执行有效性说明载荷按给定父状态和规则计算正确；是否成为规范历史以及获得最终性还需要共识层选链和检查点处理。有效候选可以处于后来未被选择的分支。

<a id="sec-040"></a>
### 3.7 `ExecutionPayloadHeader.state_root` 是哪一种根？

**答：**它仍是该执行载荷的账户状态 MPT 根，与对应 EL 头的 `stateRoot` 同值。`BeaconBlockHeader.state_root` 才是信标状态的 SSZ 根。外层容器位置不能替代字段语义。

<a id="sec-041"></a>
### 3.8 为什么 `ExecutionPayloadHeader.transactions_root` 不能直接与 EL `transactionsRoot` 比较？

**答：**前者按 SSZ 对交易列表作承诺，后者是以 `RLP(index)` 为键的交易 MPT 根。它们编码同一交易集合的不同结构，根通常不同。验证时必须使用该字段所属结构的构造规则。

<a id="sec-042"></a>
### 3.9 LMD 为什么只保留最新相关消息？

**答：**它避免同一验证者的旧意见不断累积，导致其权重在多个分支重复计算。真实协议还要判断消息的 epoch、资格和冲突条件；玩具程序仅按递增整数替换，并没有实现所有规则。

<a id="sec-043"></a>
### 3.10 两个各占至少三分之二的集合为什么至少重叠三分之一？

**答：**在同一归一化总权重为 1 的模型中，由容斥有交集权重至少为两者之和减 1，即至少三分之一。这给最终性可追责阈值提供直觉；真正的跨 epoch 证明还需完整协议条件。

<a id="sec-044"></a>
### 3.11 32 ETH 与 2048 ETH 为什么不能当作同一种上限？

**答：**32 ETH 是最低激活有效余额条件，并仍是相关旧式执行提款凭证的有效余额上限；2048 ETH 是 0x02 复投凭证下的最大有效余额。它不等于所有验证者已持有的余额，也不等于任意存入金额的最大值。

<a id="sec-045"></a>
### 3.12 为什么旧验证者的历史签名都能验证，还可能是长程攻击？

**答：**签名有效只说明旧密钥认可了对应消息。退出后的旧密钥可能被用于重造另一套历史，新节点如果没有近期可信检查点，不能仅凭“这条分支也有合法签名”判断其应被接受。弱主观性为历史锚点提供必要上下文。

<a id="sec-046"></a>
### 3.13 Alice 的 ETH 余额证明能否证明她拥有某个 ERC-20 的余额？

**答：**通常不能。原生 ETH 在 Alice 的账户字段中；ERC-20 余额通常位于代币合约的存储映射，需要证明相应合约账户及目标存储位置，并正确应用其布局与语义。

<a id="sec-047"></a>
### 3.14 SSZ 列表 `[1,2,3,4]` 与 `[1,2,3,4,0,0,0,0]` 为什么根不同？

**答：**在示例的同一最大容量下，它们补零后的数据部分可以相同，但列表根还混入实际元素个数。长度 4 和 8 是不同语义，不能仅靠相同补零字节把它们合并成同一承诺。

<a id="sec-048"></a>
### 3.15 `memory`、`storage` 和 transient storage 的主要区别是什么？

**答：**memory 是当前调用帧的临时字节空间；storage 是账户跨交易的持久状态；transient storage 可以在同一交易相关账户上下文中跨调用协作，但交易结束后清空。三者的生命周期与回滚边界不同。

<a id="sec-049"></a>
### 3.16 `eth_call` 成功，是否保证真实交易成功？

**答：**不保证。模拟依赖所指定区块和输入，真实交易入块前的状态、排序和环境可能改变；同时真实交易还涉及签名、nonce、费用等有效性与提交条件。模拟结果是重要信息，但不是未来执行的承诺。

<a id="sec-050"></a>
### 3.17 base fee=20、fee cap=22、priority cap=3 Gwei 时，有效单价是多少？

**答：**可容纳的优先费为 `22-20=2` Gwei，小于 priority cap，因此有效单价为 22 Gwei。若最终使用 21,000 Gas，普通执行费用为 462,000 Gwei，即 0.000462 ETH；其中基础部分 420,000 Gwei 销毁。

<a id="sec-051"></a>
### 3.18 合约执行 revert 后，发送者 nonce 是否恢复？

**答：**对于已经有效纳入区块的外层交易，不恢复，费用也按实际计量结算。回滚的是规定执行范围内的修改，不是把整个交易从历史中抹去。7702 授权处理的保留又是必须单独理解的补充边界。

<a id="sec-052"></a>
### 3.19 B emit 事件后 revert，A catch 住错误再 emit，最终有哪些日志？

**答：**B 失败帧产生的事件撤销；如果 A 后续正常完成，A 在 catch 后产生的日志可以保留。顶层收据可能成功。调试追踪里曾执行过某条 `LOG` 不等于最终收据包含它。

<a id="sec-053"></a>
### 3.20 一个 Rollup 的有效性证明验证通过，能否推出数据一定可下载且用户立即可提现？

**答：**不能仅从这件事推出全部结论。证明覆盖规定计算关系；数据可用性、L1 确认、桥的状态、退出流程与管理权限仍各有条件。完整分析必须把计算、数据、共识和资产释放路径连接起来。

## 四、智能合约账户包含什么

以太坊账户可以分为外部账户和合约账户。

- **外部账户（EOA）：** 由私钥控制，可签署并发起交易。
- **合约账户：**
  保存合约代码与持久化存储，按收到的调用执行代码。合约本身不会像外部账户一样自行签署并发起顶层交易；通常由外部账户发起交易，再在执行过程中触发合约之间的内部调用。

合约账户的主要信息包括：

- 余额：账户持有的原生资产数量。
- nonce：与账户交易序号或创建合约相关的状态字段。
- code：合约运行的字节码。
- storage：合约持久化状态。

合约代码一般以 Solidity 等高级语言编写，再编译为 EVM
字节码。EVM（Ethereum Virtual
Machine，以太坊虚拟机）为不同节点提供一致的执行规则。

| 组成部分              | 作用                     | 拍卖示例中的用途                       |
|-----------------------|--------------------------|----------------------------------------|
| `contract`            | 声明合约                 | 定义拍卖程序                           |
| 状态变量              | 保存跨交易持续存在的数据 | 受益人、结束时间、最高出价、最高出价者 |
| `mapping`             | 根据键查询对应值         | 记录每个地址的出价余额                 |
| 数组                  | 保存有序元素             | 记录参与者地址，以便后续遍历           |
| `event`               | 产生可供外部检索的日志   | 记录最高价变化、拍卖结算               |
| 构造函数              | 在合约部署时初始化状态   | 设置受益人和拍卖结束时间               |
| `public` 等可见性声明 | 控制函数或状态的访问方式 | 允许外部账户调用竞拍、退款等入口       |
| `payable`             | 允许函数调用接收原生资产 | 竞拍时将出价资产发送到合约             |

### 5.1 Mapping 的一个重要限制

`mapping`
适合按键查询，例如查询某个地址的余额，但它本身不提供“枚举所有键”的能力。如果业务需要遍历所有参与者，通常需要额外保存参与者列表，并确保列表更新与映射状态一致。

## 六、合约如何部署

课程示例中的部署过程可以概括为：

1.  编写合约源码。
2.  将源码编译为 EVM 字节码。
3.  由外部账户发起合约创建交易，并支付执行所需的 Gas。
4.  节点执行创建过程，部署成功后生成合约地址。
5.  之后的交易可以调用该地址对应的合约。

部署交易的数据与普通合约调用的数据含义不同：创建交易携带合约创建代码；调用交易通常携带函数选择器与参数编码。

## 七、外部调用与合约内部调用

### 7.1 外部账户调用合约

外部账户向合约地址发起交易。交易中的 `data` 通常编码了：

- 要调用的函数；
- 函数参数；
- 必要的调用数据。

交易的 `value` 表示随交易发送的原生资产数量。它与执行消耗的 Gas
费用是两个不同概念：`value` 进入接收方或合约逻辑，Gas
费用用于支付执行资源。

### 7.2 合约调用另一个合约

合约在执行过程中也可以调用其他合约。课程比较了几类调用方式：

- **普通的高层调用：**
  以合约接口形式调用目标函数，失败可能沿调用链传播并导致外层执行回滚。
- **低级 `call`：**
  通过调用数据发起消息调用，调用失败通常以返回状态表示；调用方需要显式检查返回值。
- **`delegatecall`：**
  在调用方的执行上下文中执行目标代码，尤其要注意存储和权限上下文。错误使用可能影响调用方自己的状态。

调用方式的语义并不相同。审计时必须确认目标地址、调用数据、返回值检查、Gas
传递方式和执行上下文，不能仅凭函数名称推断安全性。

## 八、`payable` 与 fallback 的历史语义

课程中的拍卖合约要求竞拍者把实际出价随调用发送给合约，因此竞拍入口需要允许接收原生资产。历史
Solidity 版本使用 `payable` 标注相应函数。

课程还介绍了早期的 fallback
函数：当调用数据无法匹配到常规函数，或收到没有明确函数选择器的转账时，执行可能进入
fallback 逻辑。若合约没有合适的接收路径，转账可能失败；若 fallback
中执行了复杂逻辑，则需要额外关注调用与 Gas 行为。

实际开发必须根据所使用的 Solidity 版本核对
`receive`、`fallback`、可支付函数和转账方法的准确语义。

## 九、Gas：为什么执行要收费

智能合约可以执行比简单转账复杂得多的计算。若任意调用都不受资源限制，恶意交易就可能让节点进行大量计算或存储操作，影响整个网络。

Gas 是对执行资源计量的机制：

- 不同操作消耗不同数量的 Gas。
- 计算、哈希、存储读取与存储写入的成本可能不同。
- 交易发起者需要为执行设定资源上限，并承担实际执行所产生的费用。
- 区块也有整体执行资源上限，避免单个区块占用无限资源。

课程使用的历史交易字段包括 `gasLimit` 和
`gasPrice`。在该语境下，`gasLimit` 表示调用愿意消耗的最大 Gas
数量，`gasPrice` 表示单位 Gas
的价格。实际费用与实际消耗量及适用的费用规则有关。现代以太坊费用市场已演进，不能把这组历史字段直接当作所有现行交易类型的完整模型。

### 9.1 Gas 的两个不同上限

不要混淆：

1.  **交易级 Gas 上限：** 这笔交易最多允许消耗多少执行资源。
2.  **区块级 Gas 上限：**
    一个区块中所有交易合计最多允许消耗多少执行资源。

区块级上限限制的是区块实际承载的总执行资源，不等于把每笔交易由发送者自行设定的
`gasLimit` 简单相加。

## 十、交易执行的原子性与回滚

以太坊交易执行具有原子性：状态变更要么按成功路径整体生效，要么在执行失败时回滚。课程强调的典型失败情形包括：

- 执行所需 Gas 超过交易允许的上限；
- `require` 等条件检查不通过；
- 执行到 `revert` 等回滚指令；
- 调用链中的其他执行错误导致外层调用失败。

回滚会撤销本次执行所产生的状态变更，但已经消耗的执行资源仍然需要计费。否则，攻击者可以反复发起高成本调用，在失败后不承担相应费用，从而浪费节点资源。

课程提到的 `assert`、`require` 和 `revert` 用途并不完全相同：`require`
常用于检查输入或外部条件；`assert` 用于表达内部不变量；`revert`
用于主动终止并回滚执行。具体异常语义和错误信息机制会随 Solidity
版本变化。

## 十一、确定性执行：为什么不能直接依赖随机数或多线程

以太坊是交易驱动的状态机。对于同一条链上同一顺序的交易，各节点必须得到相同的执行结果，否则计算出的状态根就会不同，节点无法就区块有效性达成一致。

因此，合约执行环境需要避免依赖每个节点都可能不同的外部状态，例如：

- 不受协议约束的本地文件或操作系统信息；
- 不同节点各自生成的真正随机数；
- 会因线程调度顺序不同而产生不同结果的并发执行；
- 节点本地时间等不一致的环境细节。

合约可以读取协议明确提供的区块与调用上下文信息，但这些信息的精度和可操纵性都有限。尤其是区块时间戳等值，不应直接当作安全随机数。

## 十二、拍卖合约：把状态和调用串起来

课程的拍卖案例包含以下业务状态：

- 受益人地址；
- 拍卖结束时间；
- 当前最高出价和最高出价者；
- 各参与者尚未取回的出价余额；
- 拍卖是否已经结束或结算。

业务流程可分为三个阶段。

### 12.1 竞拍

参与者调用可接收资产的竞拍函数，并把出价金额随交易发送。合约检查拍卖是否结束、出价是否高于当前最高价，再更新最高价相关状态。

### 12.2 退款

未中标者需要取回自己的出价。若合约把退款写在一个遍历所有参与者的循环里，单个异常接收方可能让整笔结算交易失败。因此，退款流程本身也是重要的安全边界。

### 12.3 结算

拍卖结束后，最高出价应按规则支付给受益人，未中标者应能够取回各自资金。结算逻辑需要确保同一笔余额不会被重复支付，也不能因为某个参与者的合约行为导致所有其他参与者都无法退款。

## 十三、重入攻击：外部调用如何改变当前执行流程

重入攻击（Reentrancy）发生在合约向外部地址发起调用后，外部地址在当前调用尚未结束时再次调用原合约，导致原合约在关键状态尚未更新的情况下重复执行某段逻辑。

典型危险顺序：

1.  合约检查调用者有一笔可取回的余额。
2.  合约先向调用者转账。
3.  接收方是一个合约，它在收款回调中再次调用提款函数。
4.  原合约尚未把余额清零，重入调用再次通过检查。
5.  余额可能被重复提取，直至资金、Gas 或调用深度不足。

### 13.1 防御思路：Checks–Effects–Interactions

较安全的组织顺序是：

1.  **Checks：** 检查权限、余额、时间和业务条件。
2.  **Effects：** 先更新内部状态，例如将可提取余额清零。
3.  **Interactions：** 最后才与外部地址交互。

若外部调用失败，需要设计清晰的失败处理，确保内部状态与资金实际流转一致。还可以使用重入锁、拉取式提款等方法。具体防御措施需要结合当前
Solidity 版本和调用语义选择；单纯依赖某个历史转账函数的 Gas
限制并不是通用的安全保证。

## 十四、拍卖退款中的拒绝服务风险

如果结算函数用一个循环向所有参与者退款，而其中一个接收合约拒绝收款或让调用失败，可能导致整笔结算回滚。结果是其他本来无问题的参与者也无法完成退款。

一种常见的设计方向是 **Pull Payment（拉取式支付）**：

- 结算函数只记录每个参与者可以领取的金额；
- 每位参与者单独调用提款函数领取；
- 一个地址领取失败，不影响其他地址的提款。

这种设计将复杂的批量外部交互拆分为相互隔离的交易，但仍需检查重入、重复领取、权限和余额更新顺序。

## 十五、代码审查清单

- 是否检查所有外部调用的返回值？
- 是否在外部调用之前更新关键状态？
- 是否存在可由外部控制的循环长度？
- 单个收款地址失败是否会阻塞其他人的资金领取？
- 是否区分交易金额 `value` 与 Gas 费用？
- 是否限制用户可消耗的执行资源？
- 是否依赖时间戳或伪随机值进行高价值决策？
- 是否核对 `call`、`delegatecall`、`transfer`、`send` 的当前版本语义？
- 是否在测试网充分测试异常路径和回滚路径？

## 十六、本讲小结

智能合约把业务规则转化为链上可重复执行的程序。Gas
限制资源消耗，原子回滚维持状态一致性，确定性执行让不同节点可以独立验证结果。合约安全的重点在于状态更新顺序、外部调用、资源上限和失败路径，而不只在于主流程能否正常运行。
