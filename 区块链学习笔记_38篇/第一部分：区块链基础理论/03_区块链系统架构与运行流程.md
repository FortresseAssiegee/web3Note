## 二、趋势五：RWA 和稳定币

<a id="sec-049"></a>
### 2.1 RWA 是什么

RWA 是 Real-World Assets 的缩写，通常讨论把现实世界资产或相关权利表示为可编程代币。底层对象可能是金融资产、应收账款、商品等；但一个代币究竟代表直接所有权、受益权、债权还是其他请求权，必须读取具体安排，不能仅靠代币名称判断。

最容易混淆的地方是“资产”和“资产表示”。一幢房屋不能物理地进入一组字节；系统可以记录对房屋相关权利的声明和转让规则。链上记录与现实权利之间的对应关系，需要登记、法律文件、托管、估值和执行机制维持。

<a id="sec-050"></a>
### 2.2 一个 RWA 系统的完整生命周期

下面是一种**教学架构**，不是所有项目的标准流程：

| 阶段 | 操作 | 参与者与证据 | 主要失败条件 |
|---|---|---|---|
| 资产进入 | 核实资产与权利、安排保管 | 发行方、托管或登记机构 | 资产不存在或权属有争议 |
| 映射规则 | 确定一枚代币对应何种请求权 | 合同、发行文档、合约规则 | 链上与链外约定不一致 |
| 发行 | 满足条件后铸造代币 | 授权签名、发行记录 | 超额发行或未经批准发行 |
| 流转 | 按权限和交易规则转让 | 交易、名单、账本状态 | 不允许的受让方仍能取得代币 |
| 存续管理 | 分配收益、更新估值、处置异常 | 现金流记录、审计材料 | 数据迟到、资不抵债、管理员失误 |
| 赎回或终止 | 销毁或锁定代币并交付相应权利 | 链上状态及链外处理记录 | 代币销毁后资产未交付，或反之 |

密码学可以保护各阶段的消息和记录，却不能独立保证资产可出售、价格公允或权利可执行。比如托管机构签名确认持有一吨黄金，签名能绑定该声明与密钥，黄金是否真实存在还需要另一个层面的证据。

<a id="sec-051"></a>
### 2.3 用 100 万单位资产说明份额映射

**教学例子。** 某安排下可供分配的资产净值是 1,000,000 个计价单位，发行 1,000,000 份等额凭证，忽略费用时每份对应 1 个单位的净值。

如果发生 20,000 的损失，且其他条件不变，净值变为 980,000，每份净值为 0.98。链上仍有 1,000,000 枚代币，并不会因为代币数量没有变就让每枚继续对应 1 单位资产。

如果收益通过增加代币数量发放，余额可能改变；如果通过单独支付分配，余额可以不变。会计规则必须明确，否则观察者会误把增加的代币数量当成新的真实资产创造。

<a id="sec-052"></a>
### 2.4 稳定币是什么，又为何可能不稳定

稳定币是一类试图相对某个参考单位维持较稳定价值的代币。“稳定”描述目标或机制，不是对任何时间都能按固定价格兑换的无条件保证。

按机制可以作一个教学区分：

| 类型 | 维持锚定的主要来源 | 需要重点观察 |
|---|---|---|
| 储备与赎回支持 | 储备资产、发行与赎回安排、市场套利 | 储备质量、托管、赎回资格与时间 |
| 加密资产抵押 | 链上抵押、超额担保、清算规则 | 抵押物波动、价格输入、清算流动性 |
| 主要依赖供给调节和激励 | 规则化增减供应、相关资产激励 | 需求下降时机制是否仍可持续 |

现实设计可能混合多种机制，所以这张表是分析入口，不是足以涵盖全部产品的分类定理。不能看到白皮书里有数学公式，就认为它已经证明了在任何市场冲击下都不会脱锚。

<a id="sec-053"></a>
### 2.5 稳定币、银行存款和链原生资产的区别

稳定币可能承载对发行方的某类请求权；代币化银行存款通常涉及银行存款关系；链原生资产用于相应网络的资产与激励体系；RWA 凭证则取决于其具体资产安排。它们即使都能显示在一个钱包里，也不意味着债务主体、保障安排和赎回权利相同。

| 比较维度 | 应该提出的问题 |
|---|---|
| 计价单位 | 锚定美元、其他法币、商品还是没有锚定 |
| 责任主体 | 谁承担兑付义务，是否存在明确主体 |
| 持有资格 | 任何地址能持有，还是有条件限制 |
| 赎回安排 | 谁可以直接赎回，需要何种手续 |
| 资产风险 | 底层资产是什么，价值和流动性如何变化 |
| 技术权限 | 谁能冻结、增发、升级、改变转让规则 |
| 支付用途 | 结算的是链上资产，还是某类链外义务 |

BIS 2025 年报告强调：代币化平台的潜力，与稳定币能否承担整个货币体系的核心功能，是需要分别评估的问题。[R11] 本笔记据此保持概念区分，不把“使用同样的区块链技术”当成不同货币安排已经等价。

<a id="sec-054"></a>
### 2.6 RWA 与稳定币如何连接

一个常见设想是，用稳定币支付 RWA 份额，随后由合约分配收益或处理赎回。它涉及至少两组风险：支付代币本身的风险，以及 RWA 资产安排的风险。

**教学例子。** Alice 支付 100 单位稳定币，取得一份资产凭证。如果稳定币后来只能以 0.97 的市场价格卖出，资产凭证的底层价值又发生损失，这两种变化不能混成“链上价格波动”一个指标。风险分析应分层记录计价资产、支付资产、投资资产和担保资产。

若二者可以在同一事务里交割，能够减少某些交付与付款错位；但这并不消除各自的资产风险，也不保证链外赎回同步完成。技术上的原子转移，与现实世界风险已经消失，是不同结论。

## 三、趋势六：Web3 业务仍可创新，但创新空间是否持续减弱

<a id="sec-056"></a>
### 3.1 这是一个需要定义和证据的问题

原目录的“持续减弱”没有给出时间范围、衡量指标或数据。本讲把它保留为待讨论观点，不替作者补造证明。

首先要定义“创新”：

- 是新提出的密码原语和协议机制？
- 是已有技术在新的业务中有效落地？
- 是性能、成本或可用性的实质改善？
- 是出现更多项目名称、代币或融资活动？

这些指标变化可能不同。例如，项目数量减少，同时有用户价值的系统更成熟，不能直接说明技术创新在下降。反过来，新项目很多也不能证明解决了更多真实问题。

<a id="sec-057"></a>
### 3.2 用反事实判断区块链有没有贡献

一个实用方法是：把方案里的区块链替换成普通数据库，再看哪些目标会消失。

**例一：单公司优惠券。** 如果发券、兑券、争议处理和所有数据库权限都属于一家平台，改用区块链之后仍由平台随时调整规则，那么用户到底获得了什么新增能力？可能有公开核验，也可能只有额外费用，需要实际比较。

**例二：多个互不完全信任的机构共同记录交接。** 如果每家都希望保留自己的签名证据，并避免某一家无痕删除共同历史，那么共享规则和第三方可核验记录可能具有价值。仍应与签名日志、共同审计服务、许可数据库等基线比较。

这个方法的关键是检验具体约束，不是预先认定所有业务都需要或不需要区块链。

<a id="sec-058"></a>
### 3.3 值得持续研究的具体问题

以下是从本讲机制分析得到的研究问题，不主张它们尚无人研究，也不据此宣布创新：

| 问题 | 为什么存在 | 可测量的改进方向 |
|---|---|---|
| 签名内容难理解 | 用户看到编码，未必理解授权范围 | 误签率、可理解性、域和额度展示 |
| 密钥丢失与恢复 | 单个秘密控制大范围权限 | 恢复成功率、串谋门槛、恢复时延 |
| 链外数据可信度 | 合约依赖外部观察 | 错误检测率、时效、依赖来源风险 |
| 完整性与遗漏 | 有效签名不证明预期记录齐全 | 缺失发现率、额外通信与存储成本 |
| 可核验与保密冲突 | 各方需要验证却不愿公开原文 | 证明开销、泄漏范围、授权灵活性 |
| 跨系统交割 | 不同系统失败与确认语义不同 | 锁定时间、失败恢复、信任假设 |
| 多机构运维 | 权限、版本和异常流程复杂 | 误配置率、升级影响、审计成本 |

密码学在这里的价值应通过具体机制体现。例如，若方案提出用零知识证明隐藏敏感字段，就要说清证明的命题、见证数据、公开输入、验证方式，以及它是否真的证明了业务关心的事情；不能只把“使用零知识”作为安全结论。

<a id="sec-059"></a>
### 3.4 一张可用于学习和项目判断的评价表

| 维度 | 最低需要回答的问题 | 一个不充分的回答 |
|---|---|---|
| 问题真实性 | 谁遇到什么困难，现在如何处理 | “这个行业需要 Web3” |
| 信任模型 | 谁可以作恶、作恶后能影响什么 | “去中心化所以没人能作恶” |
| 密码学保证 | 检查哪个命题、依赖哪些假设 | “有哈希所以数据是真的” |
| 可实现性 | 输入输出、部署、调用和状态如何组织 | “用智能合约自动完成” |
| 总体成本 | 通信、计算、存储、人工和异常成本 | “链上手续费低” |
| 业务效果 | 与合理基线相比改善什么 | “链上交易数很多” |
| 长期治理 | 谁改参数、如何恢复、如何退场 | “代码一旦部署永远不用管” |

对未来前景更稳妥的判断是：不同场景会沿着不同约束发展。需要透明核验、共享执行和可编程资产的业务，可能从这些机制中获益；现实数据质量、资产权利和组织治理仍需独立解决。是否出现创新，应依据可比较的效果和新的机制证据判断，而不是把某个时期的市场热度当作技术上限。

## 四、知识回顾：密码学在本讲中的位置（教学补充）

<a id="sec-061"></a>
### 4.1 必须分清的五种保证

| 性质 | 所回答的问题 | 典型机制 | 容易遗漏的前提 |
|---|---|---|---|
| 内容完整性 | 字节是否被更改 | 哈希、认证机制 | 比较基准是否可信 |
| 授权可验证性 | 是否由被认可的密钥授权 | 数字签名、账户规则 | 公钥与主体如何绑定 |
| 机密性 | 未获授权的人是否能读懂 | 认证加密、访问控制 | 密钥如何管理与分发 |
| 历史一致性 | 各方是否接受同一记录顺序 | 共识与执行规则 | 协议和网络假设 |
| 现实真实性 | 记录描述的事实是否发生 | 采集、审核、来源交叉核验 | 密码学证据与现实对象的绑定 |

第五项不能简单由前四项推出。把一个错误的温度值签名、哈希、上链并获得多方一致认可，仍可能只是共同保存了一个错误温度值。

<a id="sec-062"></a>
### 4.2 常见误区与修正

| 常见说法 | 更准确的理解 |
|---|---|
| 钱存在钱包里 | 钱包管理访问和授权；资产状态由对应账本或系统记录 |
| 有签名就已经付款 | 签名只是授权证据，还需要执行成功并满足业务确认条件 |
| 公钥可以验证，所以身份绝对真实 | 公钥验证密钥关系，现实身份需要额外绑定 |
| EIP-712 自动防止所有重放 | 结构化签名仍需业务 nonce、期限或一次性状态 |
| 溯源记录上链就不会有假货 | 上链不能替代实物标识、检测和采集过程 |
| 哈希后的客户数据一定保密 | 小范围、可猜测输入可能被枚举 |
| 所有节点都签了就代表很多独立来源 | 多个节点可能复制同一数据源 |
| 稳定币永远等于一美元 | 锚定是目标，兑付和市场价格受具体机制约束 |
| RWA 代币就是现实资产本身 | 代币表示某种权利，具体权利需核实 |
| 合约保证原子性，所以跨链也天然原子 | 跨域操作需要独立的协调和安全分析 |
| 大机构参与说明所有业务都值得上链 | 一个案例只能支持其已公开的具体范围 |
| 创新项目变少证明技术空间耗尽 | 需要明确创新指标、样本和时间范围 |

<a id="sec-063"></a>
### 4.3 术语速查

| 术语 | 本讲中的含义 |
|---|---|
| 哈希 / 摘要 | 把内容映射为固定长度输出，用于内容标识与一致性核验 |
| 数字签名 | 用秘密密钥生成、能按对应验证规则检查的消息授权证据 |
| nonce | 为区分或限制重复操作而使用的值；具体含义由协议规定 |
| 域隔离 | 在编码中区分用途、版本、网络或应用，避免语义混用 |
| 规范编码 | 使双方对同一结构化数据得到一致且无歧义字节表示的规则 |
| 承诺 | 先固定某个值，之后按规定材料验证所固定的内容 |
| 智能合约状态 | 合约持久保存并按规则更新的数据 |
| 事件 | 合约执行产生的日志，常供链外系统查询和索引 |
| 预言机 | 将外部信息送入链上应用的机制与服务 |
| 原子执行 | 指定范围内的多步操作按整体成功或整体失败语义处理 |
| 最终性 | 协议在其安全假设下对记录稳定性的保证；确定性最终化与概率性稳定性的前提和强度不同 |
| 商户确认策略 | 商户按风险容忍度决定何时接受付款，例如等待规定确认数或协议最终化；这种业务策略不自行创造更强的协议保证 |
| RWA | 对现实资产或相关权利进行链上表示的一类应用 |
| 赎回 | 按发行安排把代币换回对应资产或履行相关请求权的过程 |

### 5.1 自测题

1. Alice 对“向 Bob 支付 25”签名后，商户为什么仍不能直接认定已收到钱？
2. 一条签名消息包含 chain ID 和合约地址，为什么仍可能在同一合约中重放？

5. 溯源合约检查记录序号从 1 到 2 到 3，能否证明期间没有漏测？
6. 只把身份证号的 SHA-256 摘要放上链，为什么仍可能有隐私问题？
7. RWA 合约余额没有变化，为什么对应的资产净值仍会下跌？
8. 一个代币在公开链上流转，为什么仍可能存在集中管理与冻结权限？
9. 将两种资产放在同一事务里交换，减少了哪类风险，又没有消除哪些风险？
10. 一家公司宣布了区块链试点，怎样才能严谨地描述其意义？
11. 在 Go 示例中，删除 `Used` 检查后，第二次提交同一签名会怎样？
12. 在 Solidity 示例中，允许同批次的任何已授权报告者追加，意味着什么组织治理前提？

### 5.2 参考答案

1. 签名仅说明特定消息获得相应授权。还需要实际交易被执行、资产正确转移，并满足商户的确认条件。
2. 域字段区分应用场景；若合约没有记录授权已经使用，同一个域中的同一合法消息仍可能多次被接受。
3. 哈希处理字节，不直接理解 JSON 的业务语义。不同序列化得到不同字节，需要规范化或明确编码规则。
4. 不能。它们可能来自同一上游传感器、API 或控制主体。证据独立性应通过来源关系核实。
5. 不能。连续编号只能约束已提交序列，不能证明预期采样时刻全部出现；需要预期任务和缺失状态规则。
6. 身份证号结构可预测，攻击者可能结合其他信息枚举候选并比对摘要；确定性哈希还可能支持跨系统关联。
7. 余额表示份额数量，净值取决于底层资产及负债。份额数不变不意味着每份价值不变。
8. 网络公开性和资产管理权限是不同维度。发行方可能在合约内设置准入、冻结、升级或增发能力。
9. 在执行语义允许的范围内，可减少一边已交付而另一边未付款的错位风险；不消除价格、兑付、合约漏洞或现实资产风险。
10. 说明公告日期、目标、参与范围和阶段；不要把试点改写为全面部署，也不要把机构表述当成效果已经得到独立验证。
11. 签名仍然有效，只要其他业务条件满足，就会再次被接受。这说明防重放是协议状态责任。
12. 必须接受管理员对报告者准入的管理，并考虑报告者误报、串谋和追加冲突。链只验证合约规定的权限，不替组织判断报告内容为真。

<a id="sec-067"></a>
### 5.3 可继续动手的三个练习

**练习 A：给订单增加币种。** 在 Go 示例中增加一个固定长度代币标识，将它加入编码，并在验证器中检查。先不把字段放入签名，观察篡改币种是否仍然可能通过，再补上绑定。这个练习用于理解“漏签字段”的后果。

**练习 B：补上采样完整性。** 为一个批次预先登记 4 个采样时段，规定每个时段最终只能处于“已收到、缺失、迟到、冲突”之一。写出状态转换表，再思考谁可以确认缺失，以及网络延迟如何影响判断。不要一开始就把缺失等同于作恶。

**练习 C：比较链与签名日志。** 选择一个三家组织共同维护交接记录的场景，分别画出“共同签名日志＋可信保管者”和“区块链＋权限合约”的流程。列出每种方案需要信任谁、能检测什么错误、有哪些存储和运维成本。比较应保留相同的业务目标。

## 七、先识别业务瓶颈

区块链常被用于解决交易记录共享、数据难以被单方篡改、多个参与方缺少共同可信记录等问题。但应用中出现的延迟或成本，未必来自账本或支付技术。

### 7.1 案例：保险理赔

理赔流程可能耗时很长，但延迟通常涉及事故证据收集、责任认定、人工审核和争议处理。如果金额已经确定，实际付款可能很快完成。

因此，在引入区块链之前，需要区分：

- **业务审核问题：** 谁来确认事故是否发生、责任归属和理赔金额？
- **支付结算问题：** 在金额确定后，资金如何到达收款方？
- **记录协作问题：**
  多家机构是否需要共享一份可审计、难以被单方改写的记录？

区块链可能改善多方记录与协作，但不能仅靠写入链上的交易自动完成现实世界的事故认定。

## 八、供应链追溯：记录可信不等于输入真实

供应链系统可以记录农产品的产地、采摘时间、运输过程、仓储和销售流向。多个参与方共同维护记录，有助于追踪责任与发现记录变更。

但这里存在一个关键的信任边界：

- 区块链可以让已写入的记录更难被单方篡改；
- 它不能自动验证录入时提供的信息是否真实；
- 如果有人在源头就把非有机蔬菜标记为有机，或者在运输中调换商品，账本本身无法凭空识别这种现实世界的欺骗。

因此，供应链追溯仍需要可靠的数据采集、身份管理、现场检查、传感器校验、审计和责任追究机制。链上完整性与链下真实性是两个不同的问题。

## 九、区块链建立的是哪一类信任

课程将区块链的重要目标概括为：让彼此缺少完全信任的参与方，仍能围绕共同的交易记录或状态达成一致。

这并不意味着所有参与方都必须放弃中心化服务。中心化与去中心化不是只有两个极端选项：

- 一个中心化电商平台可以接受比特币等链上资产作为支付方式；
- 一个系统可以用中心化机构处理客户服务，同时用区块链记录多个机构共同认可的结算结果；
- 一个完全开放的链上系统，也可能依赖中心化交易所、前端网站或链下数据服务。

因此，需要分别判断支付方式、账本维护、业务决策、争议解决和客户服务由谁控制。采用区块链支付，不会自动让整个商业模式变成去中心化。

## 十、不可逆转账与退款机制

区块链交易被确认后，通常不能由单个参与者像编辑数据库记录一样直接撤销。课程指出，这不等于区块链无法退款。

退款通常是新的交易：

1.  买方向卖方支付一笔资产。
2.  双方发现需要退款。
3.  卖方再发起一笔新交易，把相应资产退回买方。

账本上保留了支付与退款两笔记录。退款不是把第一笔交易从历史中抹去，而是通过后续状态变化完成资金返还。

传统支付系统有时提供拒付、争议处理或消费者保护机制。其覆盖范围取决于支付产品、合同和适用法律。使用不可逆转账方式时，用户需要考虑错误地址、欺诈和私钥泄露带来的损失，以及是否存在有效的救济途径。

## 十一、加密货币支付适合哪些场景

课程认为，加密货币不必与所有已有支付方式正面竞争。若信用卡或本地转账已经能低成本、高效率地完成交易，换用另一种支付方式未必能带来实际收益。

更值得分析的场景包括：

- 跨境小额支付或专业服务付款；
- 传统银行转账流程复杂、到账时间较长或覆盖不足的场景；
- 需要把支付与互联网信息交互结合起来的应用；
- 多方之间需要共同验证支付记录的场景。

是否适用仍取决于交易费用、确认时间、汇率波动、法币兑换、合规要求、消费者保护和系统可用性。课程中的跨境咨询费案例说明的是一种需求类型，不代表所有跨境支付都更适合使用加密货币。

## 十二、如何评价支付效率与能耗

课程提醒，评价支付方式时应与同一时期、同一应用场景下的替代方案比较。除了共识层能耗，还要考虑银行基础设施、数据中心、网络、合规与争议处理等成本。

同时，比较必须避免混淆指标：

- 年度总能耗与单笔交易平均能耗是不同指标；
- 单笔交易的能耗估算取决于如何分摊网络整体能耗；
- 吞吐量、最终确认时间、成本和可用性不能用单一指标替代；
- 协议演进可能改变系统的能耗与性能特征。

课程中的 PoW
能耗统计属于历史数据。引用或比较现实系统时，应重新核对数据来源、统计时间和测量方法。

## 十三、智能合约的价值与边界

智能合约将业务规则写成程序，使符合条件的状态转换可以按统一规则执行。自动取款机可以作为直观类比：系统根据预设条件处理请求，但设备和程序仍可能出现故障。

智能合约的主要优势包括：

- 规则可以被公开检查；
- 多个节点按相同规则执行；
- 可将资产转移与程序条件绑定；
- 可以减少部分依赖人工操作的环节。

它的局限也很明确：

- 程序可能存在漏洞；
- 合约部署后，修复方式受到权限与升级设计限制；
- 链上执行不能自动验证所有现实世界事实；
- 一旦资金被错误锁定，未必存在简单的管理员恢复途径；
- 复杂业务中的判断、尽职调查和争议处理仍可能需要链下流程。

所以，智能合约应当经过代码审计、测试网验证、异常路径测试和权限设计审查。不可篡改性提高了规则执行的一致性，也使错误设计可能持续产生后果。

## 十四、The DAO 给治理设计的启示

The DAO
事件表明，程序化决策和代币投票并不能自动替代所有商业判断。评估一个投资项目可能需要考察创始团队、财务状况、技术路线、市场和执行能力，这些信息不能只靠多数票生成。

去中心化也不是所有问题的统一解法。对于不同系统，需要比较：

- 谁有权修改规则；
- 谁承担决策失败的损失；
- 少数参与者如何保护自身权益；
- 如何发现并处理程序漏洞；
- 是否允许升级、暂停或紧急恢复；
- 应急权限是否会形成新的信任集中。

任何治理设计都有成本和权衡。投票可以表达偏好，却不保证多数人的判断一定正确；中心化管理可能提高协调效率，却可能带来单点控制与审查风险。

## 十五、应用选型清单

在决定使用区块链之前，可依次回答：

1.  是否存在多个需要共同维护记录的参与方？
2.  各方是否缺少一个可被所有人接受的单一管理者？
3.  业务是否需要公开审计、历史追踪或多方验证？
4.  现实世界数据如何采集、签名、验证和纠错？
5.  若输入数据为假，系统能否发现或追责？
6.  交易是否需要退款、撤销或争议处理？
7.  智能合约出现漏洞时，资金如何保护和恢复？
8.  费用、吞吐量、确认时间和用户体验是否满足需求？
9.  区块链方案相对于普通数据库或支付系统，究竟改善了哪一项关键指标？
10. 新增的治理、运维和安全成本是否合理？

## 十六、本讲小结

区块链的价值需要结合业务问题、参与方信任关系和系统成本判断。它可以增强多方记录的一致性与可审计性，但不能自动保证输入数据真实、商业模式合理或智能合约没有漏洞。技术选型的关键是明确它解决什么问题，以及它引入了哪些新的约束。
