## 二、XXX FI 的含义与可能解释

<a id="sec-021"></a>
### 2.1 原文可确认的内容与教学补充

这一缩写写作 **“XXX FI”**，其全称尚无法确定。本节不能断言老师原本只想讲 DeFi。结合上下文，下面把它作为“某个领域与金融化、代币机制结合”的泛称作教学补充；如果之后取得原课件，应以原文纠正具体名称。

| 常见名称 | 大致含义 | 需要进一步追问 |
|---|---|---|
| DeFi | 用合约提供交易、借贷等金融功能 | 价格、流动性、清算和治理由谁控制 |
| GameFi | 游戏与代币或资产交易机制结合 | 游戏价值是否独立于补贴和拉新存在 |
| SocialFi | 社交关系、内容或权益与金融机制结合 | 内容价值与代币投机是否混淆 |
| NFT 相关金融应用 | 对特定数字凭证进行交易、抵押等 | 凭证代表哪些权利，价格如何取得 |

这些名称是行业分类词，不是具有同等成熟度和同等安全保证的协议标准。判断项目时，要看具体规则和现金流，而不是后缀是否叫 `Fi`。

<a id="sec-022"></a>
### 2.2 用一个自动兑换池理解“可编程金融”

**以下为省略手续费的教学模型，不代表任何具体协议完整实现。** 池子里有 100 个 A 资产和 200,000 个 B 资产，采用常数乘积关系：

$$
xy=k=100\times200{,}000=20{,}000{,}000.
$$

如果用户放入 10 个 A，新的 A 储备为 110。保持 $k$ 不变时：

$$
y'=\frac{20{,}000{,}000}{110}\approx181{,}818.18,
$$

因此用户取出的 B 约为：

$$
200{,}000-181{,}818.18=18{,}181.82.
$$

初始储备比率给出的边际比价是每 A 约 2,000 个 B，但这笔交易的平均成交价约为 1,818.18 个 B。差异来自交易本身改变了池子的储备比例，说明“界面显示一个价格”不代表任意数量都能按同价成交。

这个模型怎样与密码学关联？用户签名授权交易；合约根据余额与交易条件计算；区块执行确定先后顺序；摘要与账本记录让结果可核验。但“最终兑换比例是否合理”由储备、交易顺序、费用及其他市场条件决定，不是签名算法保证的。

<a id="sec-023"></a>
### 2.3 借贷中的价格不是从签名中自动产生

再看一个**教学模型**。用户抵押 2 个 A，参考价格为每个 2,000 单位，债务为 2,500，清算阈值取 80%。定义一个简化健康度：

$$
\mathrm{HF}=\frac{\text{抵押物数量}\times\text{参考价格}\times\text{清算阈值}}{\text{债务}}.
$$

初始有 $\mathrm{HF}=2\times2{,}000\times0.8/2{,}500=1.28$。若价格降到 1,500，则 $\mathrm{HF}=0.96$。若协议定义小于 1 可触发清算，该头寸就进入清算区间。各协议可能采用不同参数和规则，此公式只解释这类阈值计算。

若价格源错误地报告 1,500，即使其签名完全有效，合约仍可能按错误价格触发清算。因此，数据来源、时效、聚合规则、异常处理和价格操纵成本都需要分析。预言机是将链外数据带入合约的机制，其存在不能自动消除输入可信度问题。[R8]

<a id="sec-027"></a>
### 4.2 机构为什么关注代币化

从系统设计看，多机构业务经常需要在不同数据库之间重复核对：一方记交易已成交，另一方记证券已交割，第三方记录资金已到账。若参与者能够在共同的可编程状态上执行某些步骤，可能减少部分对账与衔接工作。

但收益成立需要条件：交易规则被共同接受，资产与资金能够按照兼容方式表示，参与者身份和权限明确，异常处置有约定，系统能与现有业务连接。如果只把旧数据库的一列余额复制成代币，却仍保留所有旧核对流程，总成本可能上升。

因此，应当把机构的“布局”拆成不同层次：

1. 研究或概念验证：验证某个技术能否执行。
2. 受限试点：在少量客户、地区或资产中验证流程。
3. 生产运行：实际业务依赖该系统，但范围可能仍然有限。
4. 大范围采用：要用持续业务量、客户覆盖、失败率和成本等证据支持。

这些阶段有不同证据要求。发布一个演示视频，与在生产环境承接大规模结算不是同一件事。

<a id="sec-028"></a>
### 4.3 技术采用与“完全去中心化”不是同义词

一个机构可以在公开链上发行资产，同时限制哪些地址允许接收；也可以在许可网络上使用共享账本，仍由一个委员会决定准入和升级。网络是否公开、资产是否允许自由转让、管理员权限是否集中，是三个不同维度。

学习时建议画出三张权力表：谁能写入、谁能改规则、谁能兑付。如果三张表都只有同一家机构，不应因为用了哈希和智能合约就把它描述为无需信任任何组织。是否值得采用，仍取决于系统对审计、协作和程序执行提供了什么额外能力。

## 五、趋势二：Web3 支付

<a id="sec-030"></a>
### 5.1 支付、清算与结算分别指什么

为了理解链上支付，先作业务层面的区分：

- **支付指令**：付款人表达要付多少钱、付给谁。
- **清算**：各参与方计算彼此应付、应收的义务，可能包括匹配、对账和净额计算。
- **结算**：根据系统约定完成资产或债权记录的转移。

区块链可以承载其中一个或多个环节。用户界面显示“支付成功”的时刻、链上交易被收录的时刻、资产达到所要求确认强度的时刻、商户在银行取得可用法币的时刻，可能不同。

<a id="sec-031"></a>
### 5.2 一次稳定币付款的完整链条

以下是**教学业务流程**：付款人已有稳定币，商户最终想取得银行账户中的法币。

1. 商户生成订单，指定网络、代币合约、金额、收款地址和有效期。
2. 客户核对订单，钱包签署交易或相应业务授权。
3. 交易被广播、执行并进入账本。
4. 商户服务检查真实的代币合约、接收地址和实际到账金额。
5. 商户按照自身业务容忍度等待所需的确认或最终性条件。
6. 商户将这笔付款与订单关联，避免重复记账或用一笔付款匹配多个订单。
7. 若需法币，商户通过其有资格使用的渠道卖出或赎回稳定币。
8. 中间服务商与银行处理相应链外流程。
9. 商户银行账户中出现满足业务定义的可用余额。

第 3 步发生得快，并不保证第 9 步同样快。如果赎回窗口、银行通道或账户审核受限，链上转账速度无法独自解决最后一段延迟。

<a id="sec-032"></a>
### 5.3 密码学在支付流程中具体保护什么

**金额与收款人的完整性。** 如果这些字段被纳入签名，转发者不能在不使签名失效的情况下随意替换。

**授权关系。** 验证者可以检查该指令是否由被认可的密钥或账户规则授权。密钥与现实人或组织的绑定仍由开户、证书、登记或其他身份流程提供。

**记录核验。** 摘要、交易记录和证明帮助商户检查特定内容是否进入了所依赖的账本状态。但商户若只信任一个未经验证的 RPC 返回值，实际还依赖该服务给出真实结果。

**机密信息保护。** 发票明细、客户地址等可以在链外加密传递。普通公开链交易默认并不因为有签名而隐藏金额或参与地址。

<a id="sec-033"></a>
### 5.4 支付系统常见的四类错误

第一类是**代币混淆**。名字和图标可以相似，接收时必须绑定网络及合约地址，不能只检查界面写着某个代币简称。

第二类是**金额单位混淆**。同样写 `1000000`，在 6 位小数代币中等于 1，在 18 位小数代币中则远小于 1。代币精度也不是可以对所有协议统一硬编码的常量。

第三类是**重放与重复记账**。链层面的 nonce 约束，不会自动防止你的业务系统把同一成功付款处理两次。后台需要保存订单与交易、日志位置等之间的唯一对应规则。

第四类是**可见但未满足确认条件**。观察到交易不代表已经满足业务要求；应区分待处理、已执行、确认条件满足、已结算或已退款等状态。如何选择确认强度，需要结合链的具体协议和业务风险，而不是统一写成“等一个区块即可”。

<a id="sec-034"></a>
### 5.5 怎样比较支付成本

一个更完整的教学成本模型可以写成：

$$
C_{\text{total}}=
C_{\text{入金}}+C_{\text{兑换}}+C_{\text{链上执行}}
+C_{\text{服务}}+C_{\text{出金}}+C_{\text{异常处理}}.
$$

这不是金融定价公式，只是提醒评估时不要漏项。对跨境付款，还要考虑汇率价差、流动性占用、交易失败与人工处理。对持续运营的系统，还要计算密钥保管、索引、监控和安全维护成本。

用一个**虚构数字例子**说明：方案 A 的链上费用为 0.02 单位，但入金和出金合计 3；方案 B 的链上费用为 0.2，但其他费用合计 0.5。仅比较链上费用会选 A，总显性费用却分别是 3.02 与 0.7。真实比较还应把到账时间和服务条件统一。

<a id="sec-035"></a>
### 5.6 对发展前景的条件判断

支付场景的潜力取决于它是否改善了具体链条：能否覆盖原本难以覆盖的时间和地区，能否减轻多机构对账，能否使程序按明确条件付款，能否降低可比口径下的总成本。

Visa 的官方案例说明，可以先改变机构之间的结算层，而不要求普通持卡用户直接操作钱包。[R15] 由此可以得到一个**分析推断**：未来采用的方式可能包括嵌入现有产品后台，用户并不一定每天看见“Web3”三个字。该推断描述可能的产品形态，并不预测特定企业或代币的价值。

## 六、趋势三：Web3 金融体系

<a id="sec-037"></a>
### 6.1 把体系拆成可以组合的功能

“Web3 金融体系”关键在于多个功能互相调用的系统。可以将其拆成：

| 功能 | 典型状态 | 密码学与协议作用 | 仍需处理的问题 |
|---|---|---|---|
| 发行与登记 | 总量、持有人余额、权限 | 签名授权、状态核验 | 增发权限与资产依据 |
| 交易与兑换 | 订单、储备、成交结果 | 签名、原子执行、排序 | 流动性、滑点、交易排序影响 |
| 抵押与借贷 | 抵押物、债务、利息 | 授权及状态一致性 | 价格正确性、清算能力 |
| 结算与交割 | 资产和资金的交付状态 | 条件执行、账本记录 | 资产是否同域、兑付边界 |
| 保管与恢复 | 密钥、账户控制规则 | 多签或门槛授权等 | 丢失、串谋、恢复权限 |
| 治理与升级 | 参数、提案、执行权限 | 可验证投票或授权 | 权力集中与变更风险 |

这种分解有助于读代码：某个库负责签名，某个合约负责会计状态，某个服务负责价格输入，不能期待它们彼此自动补上缺失的职责。

<a id="sec-038"></a>
### 6.2 原子交割到底改变了什么

假设 Alice 卖给 Bob 1 份资产凭证，价格是 100 个支付代币。希望实现：资产交给 Bob 与付款交给 Alice 要么同时完成，要么都不完成。这个目标通常称为 **货银对付**，即交付与付款互为条件。

在同一执行环境中，如果两种资产都能由合约可靠控制，可将两步放进一次符合该环境语义的事务：先检查权限和资产，再执行两边的转移。如果某一步失败，整体回退相关业务状态。BIS 2025 年报告第三章以此说明可编程资产操作的潜在作用。[R11]

然而，把两个动作写在两个不同区块链上，不会自动获得同样原子性。一条链完成后，另一条链可能停机、重组或拒绝执行。跨链系统需要额外协议、证明、超时与退款机制。此时新的信任条件来自桥、验证器和链间状态判断，不能沿用单链原子执行的全部保证。

<a id="sec-039"></a>
### 6.3 组合性同时带来依赖传播

设借贷合约使用价格服务 A，A 又引用交易池 B 的价格，而保险合约 C 依据借贷结果赔付。B 的短时价格异常可能沿依赖路径影响多个应用。

“每份合约单独通过代码审查”并不足以说明组合后没有问题。需要查看：

- 多个系统是否把同一个外部来源当成独立证据。
- 一个事务内是否可以先改变价格，再使用改变后的价格借出资产。
- 参数变更能否传播到依赖方，依赖方是否会及时停止操作。
- 一处流动性不足是否阻断多处清算。
- 一家管理员或托管方是否实际上控制了多个表面独立的组件。

这一分析强调的是系统依赖，而不是“合约越多越危险”。组合可以减少手工工作，也可能把原先隔离的错误串联起来。评价时应同时记录节省了什么，以及增加了什么耦合。

<a id="sec-040"></a>
### 6.4 收益来自哪里

如果一个应用向用户承诺收益，至少要问：收益是来自借款人支付利息、交易者支付手续费、底层资产产生现金流，还是来自新发行代币的补贴。

这些来源有不同的持续条件。补贴可以帮助冷启动，但其存在不直接证明业务本身已形成稳定需求。链上数据容易查看，也可能让人误把活动量、抵押资产总额或代币价格当成利润。

对开发和研究而言，更可操作的问题是：收入由谁支付，真实服务是什么，提供服务的成本是否被计入，风险由谁承担，激励减少后用户是否仍需要它。密码学可以增强过程的可验证性，无法替代经济模型的成立条件。

<a id="sec-041"></a>

## 七、趋势四：区块链溯源

<a id="sec-042"></a>
### 7.1 从“存一个哈希”走向可审计的业务记录

第二部分已经说明存证原理。本节进一步考虑一个可操作的模型：每个批次有一个已知的最新承诺，提交新事件时必须引用它。合约检查提交者权限、序号和上一条承诺，从而让记录形成按规则追加的序列。

设第 $i$ 条记录的文档摘要为 $h_i$，上一条承诺为 $c_{i-1}$，构造：

$$
c_i=\operatorname{Keccak256}\!\left(
\operatorname{Encode}(d,\mathrm{chainId},\mathrm{contract},\mathrm{batchId},
i,h_i,c_{i-1},t_i,a_i)\right).
$$

其中 $d$ 是用途域，$t_i$ 是提交者声称的观察时间，$a_i$ 是提交地址。把上一条承诺包含进来，可以把当前记录与此前的序列关联。合约同时检查 `expectedPrevious`，可以防止两个提交者都基于旧头部成功追加而导致应用忽视并发冲突。

这是一种**教学应用设计**，不是以太坊底层的区块哈希公式。链本身已有区块结构；这里额外建立的是某个批次的业务记录链。

<a id="sec-043"></a>
### 7.2 Solidity 实验：按批次追加存证

本程序支持管理员登记批次、授权报告者，以及报告者追加文档摘要。它没有外部依赖，不执行转账，不手写签名恢复；普通链上调用由交易和调用上下文确定 `msg.sender`，合约再检查该地址是否获准提交。

代码使用 Solidity `^0.8.24` 语法。可在兼容版本的编译器或 Remix 本地虚拟机中学习。`abi.encode`、`keccak256`、`block.chainid` 和 `msg.sender` 的含义可查 Solidity 官方文档；事件用于向链外程序提供可检索的提交记录。[R9] [R16]

**验证记录：** 本合约已使用 Solidity 0.8.30 编译通过；自身没有 OpenZeppelin 依赖。本次未对该合约进行交易执行测试，下面的操作步骤供读者在本地环境复现。

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

// Teaching example: records claims; does not certify physical truth.
contract BatchProvenance {
    bytes32 public constant DOMAIN = keccak256("BatchProvenance.v1");
    address public immutable administrator;

    struct Head {
        bytes32 commitment;
        uint64 sequence;
        bool exists;
    }

    mapping(bytes32 => Head) public heads;
    mapping(bytes32 => mapping(address => bool)) public reporters;

    event BatchCreated(bytes32 indexed batchId);
    event ReporterSet(bytes32 indexed batchId, address indexed reporter, bool allowed);
    event Anchored(
        bytes32 indexed batchId,
        uint64 indexed sequence,
        address indexed reporter,
        bytes32 documentHash,
        bytes32 previousCommitment,
        bytes32 commitment,
        uint64 observedAt,
        uint256 recordedAt
    );

    constructor() {
        administrator = msg.sender;
    }

    modifier onlyAdministrator() {
        require(msg.sender == administrator, "not administrator");
        _;
    }

    function createBatch(bytes32 batchId) external onlyAdministrator {
        require(batchId != bytes32(0), "empty batch id");
        require(!heads[batchId].exists, "batch already exists");
        heads[batchId].exists = true;
        emit BatchCreated(batchId);
    }

    function setReporter(bytes32 batchId, address reporter, bool allowed)
        external
        onlyAdministrator
    {
        require(heads[batchId].exists, "unknown batch");
        require(reporter != address(0), "zero reporter");
        reporters[batchId][reporter] = allowed;
        emit ReporterSet(batchId, reporter, allowed);
    }

    function anchor(
        bytes32 batchId,
        bytes32 documentHash,
        bytes32 expectedPrevious,
        uint64 sequence,
        uint64 observedAt
    ) external returns (bytes32 commitment) {
        Head storage head = heads[batchId];
        require(head.exists, "unknown batch");
        require(reporters[batchId][msg.sender], "not reporter");
        require(documentHash != bytes32(0), "empty document hash");
        require(expectedPrevious == head.commitment, "stale previous");
        require(sequence == head.sequence + 1, "wrong sequence");
        require(observedAt <= block.timestamp, "future observation");

        commitment = keccak256(abi.encode(
            DOMAIN, block.chainid, address(this), batchId, sequence,
            documentHash, expectedPrevious, observedAt, msg.sender
        ));
        head.commitment = commitment;
        head.sequence = sequence;
        emit Anchored(
            batchId, sequence, msg.sender, documentHash,
            expectedPrevious, commitment, observedAt, block.timestamp
        );
    }
}
```

<a id="sec-044"></a>
### 7.3 怎样走一轮，而不是只看代码

可按以下顺序操作，先使用本地教学环境：

1. 账户 A 部署合约。构造函数把 A 保存为管理员。
2. A 用一个非零的 32 字节批次标识调用 `createBatch`。
3. A 调用 `setReporter(batchId, B, true)`，授权账户 B 为此批次提交。
4. B 准备文档摘要，第一次调用 `anchor` 时传入 `expectedPrevious = 0x00...00`、`sequence = 1`，以及不大于当前区块时间的观察时间。
5. 查看 `Anchored` 事件及 `heads(batchId)`。现在最新序号为 1，最新承诺为事件中的 `commitment`。
6. B 提交第二条时，必须把第一条的承诺作为 `expectedPrevious`，并传入 `sequence = 2`。
7. 再次提交旧的 `sequence = 1`，或继续引用全零前驱，会被拒绝。
8. 让未授权的账户 C 调用同一个批次的 `anchor`，会被拒绝。

链外文档摘要可以使用固定约定的 SHA-256，外层业务承诺使用合约中的 Keccak-256；两者服务不同层次。双方必须约定文档摘要算法与文档编码。不能把 SHA3-256、Keccak-256 和 SHA-256 的输出视为可互换。

<a id="sec-045"></a>
### 7.4 这份程序已经保证什么

- 未授权地址不能通过本合约为指定批次追加事件。
- 新提交必须接在合约认可的当前头部后面。
- 同一合约状态下，序号必须连续递增。
- 每条承诺绑定批次、序号、文档摘要、前驱、报告者和用途域。
- 当前头部写在合约状态，历史事件写入交易日志，方便链外索引。

其中，“序号连续”只表示已提交记录的序列连续。例如报告者完全可以把三天后才发生的事件写成序号 2。若规则要求每天必须提交一条，仍要额外定义预期时间槽与缺失状态；本合约没有该机制。

<a id="sec-046"></a>
### 7.5 这份程序没有保证什么

它不能证明文档写的温度、产地、所有权是真实的；不能证明原始文件始终可下载；不能证明记者或设备按时上报；不能防止获准报告者和管理员串谋；不能保证用户使用的查询服务总是返回完整日志。

管理员能够调整报告者权限，因此权限管理集中在一个地址。为了让示例聚焦于追加规则，代码没有加入管理员更换、多人治理、暂停和升级。生产场景应该根据实际组织关系重新设计这些能力，不能把这个教学合约当成已审计的商业系统。

合约也没有销毁或覆盖历史事件的入口，不过读取历史记录仍依赖可获得的数据和所接受的链状态。索引程序应记录区块和日志位置，处理其所使用链的重组语义，而不只按本地到达时间追加数据库。

<a id="sec-047"></a>
### 7.6 哪些场景更值得采用

一个合理的采用条件是：多家组织各自掌握记录，又需要共同核验，且不愿让其中一家单独拥有无痕修改权。区块链可以作为共享记录与规则执行的一种方案。

如果只有一家企业内部使用，参与者都接受其中心数据库，且审计需求能由数据库日志、数字签名和备份满足，那么首先比较这些更简单的方案通常更合理。判断指标可以是争议取证时间、对账工作量、遗漏记录发现率、长期存储成本和访问控制效果，而不只是“是否上链”。
