## 二、P2P 协议的基本原理

<a id="sec-047"></a>
### 2.1 连接生命周期

一个完整 P2P 会话可以按下表观察。真实实现可能重叠这些步骤，但每一类职责都需要有明确边界。

| 步骤 | 输入 | 输出 | 主要失败情况 |
|---|---|---|---|
| 发现 | 启动地址、DHT、局域网发现等 | 候选 peer 地址 | 地址过期、来源被操纵、无可达邻居 |
| 拨号 | 地址和传输方式 | 底层连接 | NAT、防火墙、超时、连接数耗尽 |
| 安全握手 | 公钥、协议握手材料、预期身份 | 经认证和保护的通道 | 身份不匹配、协商失败、无可信绑定 |
| 协议协商 | 支持的协议名与版本 | 双方认可的应用协议 | 版本不兼容、错误降级 |
| 同步状态 | 网络标识、已知高度、检查点等 | 识别对方能力和所缺数据 | 错网、旧状态、虚报高度 |
| 消息交换 | 带边界的请求与响应、广播消息 | 经过验证的候选对象 | 超大消息、重复洪泛、非法证明 |
| 退出和重连 | 超时、错误、资源指标 | 清理状态和寻找替代邻居 | 泄漏连接、无界重试、反复恶意重连 |

发现协议解决“在哪里能找到人”，安全握手解决“连接的密钥身份是什么”，共识成员表解决“这个身份是否有投票资格”。三种验证不可互换。libp2p 将发现、路由、传输和安全通道模块化，正是因为它们的职责不同。[S29] [S32]

<a id="sec-048"></a>
### 2.2 传输加密、消息签名和认证身份

安全通道可以防止链路上的第三方直接读改传输内容，并通过握手验证所连接的密钥身份。libp2p 提供 TLS 1.3、Noise 等安全通道方案；某些传输本身已有加密能力，例如 QUIC，不同组合的建立流程不同。[S29]

但是一条加密连接可以通向恶意节点。对方完成握手只说明它控制相应密钥，不说明它报告的链头、交易或投票诚实。消息还需要按应用规则验证，特别是投票的签名与当期资格。

传输保护和消息签名也服务于不同范围。假设 A 与 B 建立安全通道，B 再把 A 的投票转给 C。A-B 通道的认证结果不会自动成为 C 能验证的原始授权证明；保留 A 对投票的端到端签名，C 才能独立检查。这也是为什么区块链明明已经使用加密连接，仍要在区块、交易和投票里保留数字签名。

密钥分离则降低误用风险。网络身份密钥、共识签名密钥和资产支出密钥通常承担不同权限。将它们未经设计地复用，会扩大某个暴露面的影响范围，也让域隔离和运维审计更困难。是否复用必须由具体协议明确规定，不能只是开发时图方便。

<a id="sec-049"></a>
### 2.3 TCP 字节流为什么需要消息边界

TCP 为应用提供有序可靠的字节流，应用不能假设“发送一次 Write，接收端就一次 Read 到一整条消息”。两条消息可能在一次读取中相连，一条消息也可能被分成多次读取。[S42]

因此协议需要明确 framing，例如：

$$
\text{length}_{4\text{ bytes}}\ \|\ 
\text{version}_{1\text{ byte}}\ \|\ 
\text{kind}_{1\text{ byte}}\ \|\ 
\text{payload}.
$$

长度字段的含义必须固定：是否包括自身、是否包括头部、使用大端还是小端。下方示例规定长度不包含自身 4 字节，但包含 version、kind 和 payload。接收方先读满 4 字节，检查长度上限，再分配缓冲区和读取后续内容。

如果攻击者把长度声明为 4 GB，正确程序不应先分配 4 GB 再发现内容不足。资源限制要放在不可信长度被使用之前。类似地，压缩数据还需要限制**解压后的**长度，单看网络包大小不足以阻止解压炸弹。

<a id="sec-050"></a>
### 2.4 Go 示例 3：分帧、短读和长度限制

文件：`code/ch05/framing/main.go`。程序把两条消息连续写入内存缓冲区，再用一个每次最多返回 3 字节的 reader 模拟分段到达，验证解析不依赖一次读全。Go 的 `io.ReadFull` 适合表达“读满固定长度”；若读到部分内容后遇到 EOF，会返回 `io.ErrUnexpectedEOF`。[S35]

```go
// In-memory framing demonstration. No listening socket or public connection.
package main

import (
	"bytes"
	"encoding/binary"
	"fmt"
	"io"
)

const maxBody = 1024

type Frame struct {
	Kind    byte
	Payload []byte
}

func writeAll(w io.Writer, p []byte) error {
	for len(p) > 0 {
		n, err := w.Write(p)
		if n < 0 || n > len(p) {
			return fmt.Errorf("invalid writer count")
		}
		p = p[n:]
		if err != nil {
			return err
		}
		if n == 0 {
			return io.ErrShortWrite
		}
	}
	return nil
}

func writeFrame(w io.Writer, f Frame) error {
	if (f.Kind != 1 && f.Kind != 2) || len(f.Payload) > maxBody-2 {
		return fmt.Errorf("unsupported kind or oversized payload")
	}
	var prefix [4]byte
	binary.BigEndian.PutUint32(prefix[:], uint32(2+len(f.Payload)))
	if err := writeAll(w, prefix[:]); err != nil {
		return err
	}
	if err := writeAll(w, []byte{1, f.Kind}); err != nil {
		return err
	}
	return writeAll(w, f.Payload)
}

func readFrame(r io.Reader) (Frame, error) {
	var prefix [4]byte
	if _, err := io.ReadFull(r, prefix[:]); err != nil {
		return Frame{}, err
	}
	n := binary.BigEndian.Uint32(prefix[:])
	// Check the untrusted length before allocation.
	if n < 2 || n > maxBody {
		return Frame{}, fmt.Errorf("invalid body length %d", n)
	}
	body := make([]byte, int(n))
	if _, err := io.ReadFull(r, body); err != nil {
		return Frame{}, err
	}
	if body[0] != 1 || (body[1] != 1 && body[1] != 2) {
		return Frame{}, fmt.Errorf("unsupported version or message kind")
	}
	return Frame{Kind: body[1], Payload: body[2:]}, nil
}

// Makes each read arbitrarily short, like a byte-stream transport may do.
type chunkReader struct{ r io.Reader }

func (c chunkReader) Read(p []byte) (int, error) {
	if len(p) > 3 {
		p = p[:3]
	}
	return c.r.Read(p)
}

func main() {
	var wire bytes.Buffer
	for _, f := range []Frame{{1, []byte("block-88")}, {2, []byte("vote-A")}} {
		if err := writeFrame(&wire, f); err != nil {
			panic(err)
		}
	}
	r := chunkReader{bytes.NewReader(wire.Bytes())}
	count := 0
	for {
		f, err := readFrame(r)
		if err == io.EOF {
			break
		}
		if err != nil {
			panic(err)
		}
		count++
		fmt.Printf("frame %d: kind=%d payload=%s
", count, f.Kind, f.Payload)
	}
	fmt.Println("decoded frames:", count)
	var oversized [4]byte
	binary.BigEndian.PutUint32(oversized[:], maxBody+1)
	_, err := readFrame(bytes.NewReader(oversized[:]))
	fmt.Println("oversized frame rejected:", err != nil)
	truncated := []byte{0, 0, 0, 5, 1, 1, 'a'}
	_, err = readFrame(bytes.NewReader(truncated))
	fmt.Println("truncated body rejected:", err == io.ErrUnexpectedEOF)
}
```

运行：

```bash
go run code/ch05/framing/main.go
```

实际输出：

```text
frame 1: kind=1 payload=block-88
frame 2: kind=2 payload=vote-A
decoded frames: 2
oversized frame rejected: true
truncated body rejected: true
```

本程序只处理消息边界，不实现真实 TCP、连接超时、签名、加密或并发会话。生产环境还要设置读取截止时间、累计流量上限、每连接并发数，并对长时间只发一点字节的慢连接作出处理。`ReadFull` 正确处理短读，不代表它能自动决定等待多久。

为什么写入侧也使用 `writeAll`？接口允许一次写入只完成部分字节；代码检查已写数量并继续，避免把“调用过 Write”误当成“整条消息已发出”。错误路径在网络程序里是协议正确性的一部分，不能只验证本机缓冲区的理想情况。

<a id="sec-051"></a>
### 2.5 广播不是无限转发：消息标识、去重和 TTL

在有环图中，如果每个节点收到消息后都无条件发给所有邻居，消息会不断绕圈。常见处理包括为消息定义稳定标识、记录最近见过的标识、限制传播范围、请求缺失消息以及为不同 peer 设置预算。

一种教学消息标识是：

$$
\mathrm{ID}=H(\text{协议域}\,\|\,\text{消息类型}\,\|\,\text{规范化内容}).
$$

协议域和类型避免不同用途的同一串字节意外共用缓存语义；规范化编码确保相同逻辑内容获得可重复标识。TTL 是每跳减少的传播预算，通常不应放入这个内容标识，否则同一消息每转发一跳就产生新 ID，去重会失效。

TTL 也不是作恶节点的物理边界。恶意中继可以重新发布、改写元数据或生成新消息，所以 TTL 只能作为协议参与者按规则执行时的控制手段，还需要限流、连接管理和应用验签。

去重缓存同样不能无限增长。若每条消息占用一个条目，攻击者持续提交新 ID，内存就会增长。生产系统需要容量上限、过期时间、替换策略，以及对无效消息的低成本筛选。在高价值共识消息中，还常结合高度、轮次和时间窗口，只保留相关范围的对象。

<a id="sec-052"></a>
### 2.6 Go 示例 4：有限图中的 gossip

文件：`code/ch05/gossip/main.go`。程序使用前面的五节点图，在进程内逐条处理消息，不启动网络服务。每个节点对同一消息只向应用交付一次；如果后来收到相同内容但更高 TTL 的副本，可以继续转发以免首次低 TTL 到达抑制较好路径，但不会重复交付应用。

这是一种课堂传播策略，**不是 libp2p GossipSub 实现**。真实 GossipSub 还包含 mesh 管理、元数据 gossip、评分及多项限额。这里的目标是看清消息 ID、内容一致性、去重和传播预算之间的关系。[S31]

```go
// Deterministic, finite, in-memory gossip model. It is not GossipSub.
package main

import (
	"crypto/sha256"
	"fmt"
	"sort"
)

const maxTTL = 8

type Message struct {
	ID      [32]byte
	Payload string
	TTL     uint8
}

type Seen struct {
	MaxTTL uint8
}

type Node struct {
	Neighbors []string
	Seen      map[[32]byte]Seen
	Delivered int
}

type Delivery struct {
	From, To string
	Message  Message
}

func messageID(payload string) [32]byte {
	return sha256.Sum256(append([]byte("CH05-GOSSIP/v1/block\x00"), payload...))
}

func receive(n *Node, m Message) (deliver, forward bool, err error) {
	if len(m.Payload) > 1024 || m.TTL > maxTTL || m.ID != messageID(m.Payload) {
		return false, false, fmt.Errorf("invalid message")
	}
	old, exists := n.Seen[m.ID]
	if !exists {
		n.Delivered++
		deliver = true
	} else if m.TTL <= old.MaxTTL {
		return false, false, nil
	}
	// A later arrival with a larger TTL may forward again but never redelivers.
	n.Seen[m.ID] = Seen{MaxTTL: m.TTL}
	return deliver, m.TTL > 0, nil
}

func main() {
	adjacency := map[string][]string{
		"A": {"B", "C"}, "B": {"A", "C", "D"},
		"C": {"A", "B", "E"}, "D": {"B", "E"}, "E": {"C", "D"},
	}
	nodes := make(map[string]*Node)
	var ids []string
	for id, neighbors := range adjacency {
		nodes[id] = &Node{Neighbors: neighbors, Seen: make(map[[32]byte]Seen)}
		ids = append(ids, id)
	}
	sort.Strings(ids)
	msg := Message{Payload: "block-88", TTL: 3}
	msg.ID = messageID(msg.Payload)
	queue := []Delivery{{To: "A", Message: msg}}
	processed := 0
	for len(queue) > 0 {
		d := queue[0]
		queue = queue[1:]
		processed++
		if processed > 1000 {
			panic("simulation event limit")
		}
		n := nodes[d.To]
		_, forward, err := receive(n, d.Message)
		if err != nil {
			panic(err)
		}
		if !forward {
			continue
		}
		next := d.Message
		next.TTL--
		for _, neighbor := range n.Neighbors {
			if neighbor != d.From {
				queue = append(queue, Delivery{d.To, neighbor, next})
			}
		}
	}
	for _, id := range ids {
		fmt.Printf("%s delivered=%d
", id, nodes[id].Delivered)
	}
	_, forward, err := receive(nodes["A"], msg)
	if err != nil {
		panic(err)
	}
	fmt.Println("repeated message suppressed:", !forward && nodes["A"].Delivered == 1)
	bad := msg
	bad.Payload = "altered-but-id-unchanged"
	_, _, err = receive(nodes["B"], bad)
	fmt.Println("mismatched ID rejected:", err != nil)
	fresh := &Node{Seen: make(map[[32]byte]Seen)}
	zero := msg
	zero.TTL = 0
	delivered, forwarded, err := receive(fresh, zero)
	if err != nil {
		panic(err)
	}
	fmt.Printf("TTL=0: delivered=%t forwarded=%t
", delivered, forwarded)
}
```

运行：

```bash
go run code/ch05/gossip/main.go
```

实际输出：

```text
A delivered=1
B delivered=1
C delivered=1
D delivered=1
E delivered=1
repeated message suppressed: true
mismatched ID rejected: true
TTL=0: delivered=true forwarded=false
```

“mismatched ID rejected”只表示内容与宣称的 ID 不一致。攻击者若改内容后重新计算哈希，会得到另一个自洽 ID；这个程序不会因此认出它是否有业务授权。**无密钥哈希不是发送者认证。** 真正的区块和投票，还要调用相应签名与状态检查。

本例为有限模拟，节点的 Seen 表没有时间淘汰，队列通过有限拓扑、TTL 上限和事件上限约束运行；不能把它的内存管理直接用于面对无穷新消息的公网节点。模拟器中的可终止性与真实网络中的抗 DoS 是不同性质。

<a id="sec-053"></a>
### 2.7 Gossip 与请求响应的配合

广播擅长让大家快速知道新对象；请求响应擅长精确取回缺失数据。完整块很大时，可以先广播块标识或摘要，邻居发现缺少内容再请求。若每次都广播全部历史，带宽会浪费；若只有请求响应而无人告诉你新对象存在，传播又会迟缓。

GossipSub 使用完整消息 mesh 与元数据传播配合，节点可以用“我见过哪些消息”的信息补齐遗漏；官方介绍中的 IHAVE/IWANT 分别表达告知和请求的角色。它不意味着每个节点必须一直向所有邻居发送完整内容。[S31]

以太坊共识网络同样区分 gossip 与 request-response：新块、证明等需要快速扩散，指定块根或 slot 范围的历史获取则适合请求响应。具体编码和消息大小限制由对应网络规范规定。[S45]

<a id="sec-054"></a>
### 2.8 消息排序、缓存和背压

即使底层连接按字节有序，多条连接之间也没有统一全局到达顺序。A 先收到区块 B 的投票却还没有 B 本身，是正常情况。节点可以在受控缓存中保存依赖关系，先请求 B，待其验证通过再处理关联票；不能因为先到的消息就直接跳过依赖验证。

如果验签速度是每秒 1000 条而入站速度是每秒 5000 条，无界队列每秒净增长 4000 条，最终耗尽内存。背压意味着系统根据处理能力限制输入、拒绝额外任务或降低某些优先级。去重必须尽量靠前，但复杂签名验证之前的去重策略也应避免攻击者用伪造标签污染合法消息缓存。

一个合理的课堂处理顺序是：固定格式和长度上限检查；网络及版本检查；廉价的重复和上下文过滤；预算允许后做密码学检查；再进入状态相关验证；最后把合格对象交给共识。具体实现为了避免缓存投毒，会明确区分“已见未验证”“已验证有效”“已判无效”等状态，而不是只有一个布尔 seen。

<a id="sec-055"></a>

## 三、P2P 网络的组织结构

<a id="sec-056"></a>
### 3.1 非结构化、结构化与混合网络

| 结构 | 邻居如何组织 | 擅长的问题 | 主要代价 |
|---|---|---|---|
| 非结构化覆盖网络 | 按随机、可达性、评分等维持邻居 | 新消息传播、动态加入退出 | 精确查找可能需要额外索引或更多传播 |
| 结构化网络 | 按标识空间与路由规则组织 | 查找指定 peer、内容记录或提供者 | 维护路由表，处理 churn 与恶意路由 |
| 混合结构 | 发现和精确查找用结构，广播另建 mesh | 组合定位效率与传播速度 | 多套状态和安全策略需要协调 |
| 含超级节点或中继的结构 | 部分节点承担更大转发或发现职责 | NAT 场景、移动终端、降低连接复杂度 | 中继容量、集中依赖及元数据暴露 |

这些是分析维度，不是相互排斥的产品标签。一个系统完全可以用 DHT 发现节点，再用稀疏 gossip mesh 广播，并在 NAT 障碍下经中继连接。[S30] [S32]

<a id="sec-057"></a>
### 3.2 Kademlia 的 XOR 距离

Kademlia 类 DHT 用标识空间中的距离指导路由。常见距离定义为两个固定长度标识的按位异或，按整数比较：

$$
d(x,y)=x\oplus y.
$$

用 3 位教学标识，目标是 `101`。候选 `001` 的距离是 `100`，数值 4；`100` 的距离是 `001`，数值 1；`111` 的距离是 `010`，数值 2。因此按 XOR 距离，`100` 更接近目标。

这不是地理距离，也不是实际网络延迟。一个标识很接近的 peer 可能在另一洲；一个局域网邻居的 XOR 距离可能很远。路由表的“近”属于覆盖网络的逻辑空间，需要另行优化物理连接质量。

查找时，节点向已知较近节点询问更接近目标的节点，再迭代推进。实际 Kademlia 还涉及桶大小、并发查询、记录验证、过期和路由表维护；本例只解释距离和逐步缩小搜索范围的思想。[S30]

DHT 返回的内容也不应无条件相信。若查到一份“某块根由地址 X 提供”的记录，客户端仍应下载并验证块内容和相关证明。路由答案告诉你去哪找，不等于替你认证账本状态。对于可变记录，还要检查签名、版本和有效期等对应规则。

<a id="sec-058"></a>
### 3.3 Bootstrap 的实际地位

新节点一开始没有邻居，需要启动信息。它可能内置若干地址，通过 DNS 或其他发现方式获得候选地址，也可能由用户指定可信连接。启动服务若被控制，可能把新节点引向恶意邻居；但合理的账本验证仍应阻止无效区块被接受。

因此启动服务的风险更常体现为连接可用性、视图隔离和元数据收集，而不是自动获得任意改账权。设计应允许多来源启动、持久化历史良好邻居、地址多样性和后续发现，减少某个单点造成的影响。

“有 bootstrap 就不是 P2P”和“有哈希验证所以 bootstrap 完全不重要”都过于简单。前者混淆引导与决定权，后者忽略网络视图和活性风险。

<a id="sec-059"></a>
### 3.4 NAT、中继和打洞

许多家用、移动和企业设备位于 NAT 或防火墙后，外部节点不能直接使用其内网地址发起连接。P2P 仍要面对这些互联网现实。打洞尝试在两端协调建立直接连接，中继则让双方通过一个可达第三方转发流量。libp2p 的相关文档解释了发现可达性、中继预约和打洞协调等组件。[S43] [S46]

中继并不必然能读出应用明文，因为双方可以在中继路径上建立端到端安全通道。但中继仍可能观察连接关系、时间和流量大小，也可以丢包、限速或断开。加密保护内容，不能强迫中继提供带宽。

打洞也不是百分之百成功的魔法：NAT 行为、防火墙策略和网络变化都可能阻止直连。实际系统需要失败回退、重试上限和中继预算。过分追求全网任意节点直接互连，可能增加复杂性而没有相应收益。

<a id="sec-060"></a>
### 3.5 拓扑与共识性能之间的关系

假设一个块大小为 $B$ 字节，经单条瓶颈链路速率 $r$ 字节/秒，忽略协议开销时仅传输就需要约 $B/r$ 秒。块越大、路径越多跳，节点获得完整候选所需时间通常越长。如果共识投票截止时间比传播和验证所需时间还短，诚实节点也会频繁错过提案。

这意味着“把区块做大以提高吞吐”会反过来影响传播、验证和共识活性。优化不能只看 EVM 或哈希速度，还要观察端到端延迟分布、慢节点比例、地理跨度和重传开销。对延迟尾部的处理，常比平均延迟更重要。

提高邻居数可能缩短传播路径，但会增加带宽、连接状态和重复消息处理。降低邻居数节省资源，却可能更容易形成隔离或瓶颈。合理配置是资源与韧性的权衡，不存在对所有区块链都适用的唯一邻居数量。

<a id="sec-061"></a>

## 四、P2P 协议的应用场景

<a id="sec-062"></a>
### 4.1 区块链交易、区块与投票传播

不同消息有不同的时间价值。交易可能在交易池中等待；当前轮的投票若过了上下文窗口，继续高优先级传播价值很低；历史区块需要准确完整，但通常无需抢占当前共识消息带宽。分类队列、消息窗口和优先级可以保护关键路径。

不过“重要消息”仍不能免检。攻击者若能把任意大对象标记成高优先级投票，优先级机制反而成为放大器。优先级与消息类型、大小、签名及上下文要配合验证。

<a id="sec-063"></a>
### 4.2 历史同步与状态同步

新节点可能下载并验证完整历史，也可能从可信检查点和经过验证的状态承诺开始同步。两者的数据量和初始信任不同，应向使用者明确。状态快照如果没有绑定到认可的块根或检查点，仅仅“下载成功且文件哈希匹配”并不足以证明它属于正确链。

轻客户端通常不保存所有执行数据，而是依赖区块头、委员会证明或其他协议化证据验证某些断言。它减少资源需求，同时把验证范围和初始信任条件变成必须理解的部分。轻客户端轻客户端仍需按协议验证证据，不能仅依赖 RPC 返回的陈述。

<a id="sec-064"></a>
### 4.3 内容分发与可验证存储

内容寻址把数据与内容摘要联系起来，使下载者可以检查收到字节是否匹配预期对象。区块链历史块、软件安装包、公开数据集都可能受益于多节点分发。但“哈希匹配”只证明与预期摘要一致，预期摘要自身的可信来源仍需解决。

即使文件被正确寻址，也不能保证永远有节点保存它。存储激励、复制策略、离线恢复和内容保留政策与哈希算法不同。数据删除和长期可获得性甚至可能有相反目标，应用设计要提前声明。

<a id="sec-065"></a>
### 4.4 联盟链与跨机构协作

联盟网络可以在已知身份之间建立受控 P2P 通信，减少所有数据都经过单个业务服务的需要。组织身份认证、通道访问控制和消息保密可以与账本一致性结合，但网络可达节点不一定都有读取所有业务数据的权限。

例如订单金额只能向参与交易的机构公开，而区块的公共承诺或排序信息面向更大范围。这需要应用与隐私架构设计，不能单靠“P2P 是去中心化的”自动实现。共享哈希也可能泄漏可枚举的低熵信息，敏感数据承诺应考虑盐、随机化或专门隐私方案。

<a id="sec-066"></a>
### 4.5 分布式应用与链下协作

P2P 也可用于多人协作、实时通信、分布式计算任务或链下签名协议。区块链只是其应用之一。只要任务涉及多个互不完全信任参与者，就需要分别判断身份认证、消息可获得性、顺序要求和隐私目标。

并不是所有 P2P 应用都要全球共识。一份多人聊天消息可以只要求相关参与者接收，不需要把全世界所有聊天排成同一个全序。区分局部协作与全局账本，有助于避免为普通通信引入不必要的共识成本。

<a id="sec-067"></a>

## 五、P2P 协议的优缺点

<a id="sec-068"></a>
### 5.1 优势需要和条件一起说明

P2P 可以分散带宽和服务负担，使数据从多个位置获得；冗余路径有助于节点失效后的继续传播；用户能运行自己的验证节点，减少对单一服务提供者的依赖。这些优势需要足够多的可用节点、合适拓扑和可独立验证的数据格式支持。

网络规模大不等于实际控制分散。很多节点若位于同一云服务、使用同一客户端、依赖同一 DNS 或由同一机构运营，故障可能相关。分析韧性应观察独立故障域，而不只统计公开节点数量。

<a id="sec-069"></a>
### 5.2 主要代价

| 代价 | 原因 | 可采取的方向 |
|---|---|---|
| 重复传播 | 多路径与冗余 | 消息 ID、去重、mesh、请求响应 |
| 延迟不稳定 | 地理分布、网络抖动、节点资源差异 | 超时设计、良好邻居、恢复机制 |
| 连接管理复杂 | NAT、掉线、动态地址、版本差异 | 多传输、中继、协商与兼容策略 |
| 恶意输入面大 | 任意 peer 可尝试发消息 | 长度限制、预算、验签、上下文检查 |
| 观测困难 | 没有单点掌握全局状态 | 本地指标、分布式追踪、证据日志 |
| 元数据暴露 | 邻居可观察请求与传播行为 | 网络层隐私设计和访问模式约束 |
| 运维负担 | 状态同步、升级、密钥保护、存储增长 | 版本管理、监控与可恢复流程 |

“去中心化”并不意味着“不需要运维”，而是运维职责分散给更多参与者。每个节点都应知道磁盘耗尽、时钟异常、验证线程拥塞、邻居耗尽和密钥不可用时会发生什么。

<a id="sec-070"></a>
### 5.3 Sybil、Eclipse 与 DoS 的区别

Sybil 攻击利用大量伪身份影响某个按身份计数或依赖邻居分布的机制。Eclipse 攻击针对受害者的连接视图，使它主要或完全连接到攻击者控制的邻居。DoS 则通过资源消耗或阻断让服务无法正常响应。三者可以结合，但目标不同。

数字签名可以验证每个伪身份各自控制一把私钥，却不能证明这些身份属于不同的人。因此“所有连接都验签了”不足以防 Sybil。权益、工作量、权限名单、网络多样性和行为评分分别从不同侧面约束影响力，但任何一个都需要明确攻击模型。

被 Eclipse 的完整节点仍可能拒绝无效区块，却可能看不到新的有效历史，无法及时交易或参与共识。对 PoS 新同步节点，如果起点与来源也被攻击者控制，还要进一步分析弱主观性风险。保持多个相对独立的连接来源，是降低视图隔离风险的一部分，不是绝对保证。

DoS 资源管理应覆盖连接、流、消息、内存、CPU 和磁盘。libp2p 官方资料强调尽量避免让对手以小成本强迫本地做大量工作，提供连接与资源限制等思路。先做便宜筛选、限制验签并发、约束解压规模、控制日志量，都是这一原则的具体运用。[S33]

<a id="sec-071"></a>
### 5.4 一个资源预算的手算

假设节点允许 100 个连接，每连接最多缓存 20 条消息，每条消息最大 64 KiB。仅消息载荷的最坏缓存量就是：

$$
100\times20\times64\,\mathrm{KiB}=125\,\mathrm{MiB}.
$$

这还没算对象开销、队列结构、解压缓冲区、签名任务和块存储。若每连接缓存升到 200 条，载荷预算便约为 1.22 GiB。资源上限之间存在乘法关系，分别看起来很小的配置组合起来可能很大。

为了防止单个 peer 占满全局资源，通常需要同时设置全局、每连接、每协议和每来源的预算。又要给正常共识流量保留足够空间，避免简单的一刀切限流把活性也一并切断。这是工程权衡，不能由密码学强度参数直接决定。

<a id="sec-072"></a>
### 5.5 隐私不等于内容加密

即使传输内容加密，邻居仍可能观察你何时上线、请求哪个对象、流量大小和传播时序。区块链交易还可能公开出现在账本中。网络层隐私、账户隐私和业务内容保密是不同目标。

例如新广播某笔交易的首个观察时间，可能帮助观察者推断来源；轻客户端频繁向同一个服务器查询某地址，也可能暴露关注对象。是否需要匿名路由、批量查询、隐私检索或其他方案，应结合具体应用威胁模型评估，不能从“使用 P2P”直接推出匿名性。

<a id="sec-073"></a>


## 六、为什么短出块间隔会增加分叉

比特币课程模型中的出块间隔约为 10
分钟，而课程讨论的历史以太坊设计将目标出块间隔缩短到十几秒。P2P
网络传播区块仍需要时间，因此：

1.  矿工 A 找到区块 A 并开始广播。
2.  在区块 A 到达矿工 B 之前，矿工 B 可能仍基于旧父区块工作。
3.  矿工 B 找到区块 B，网络暂时出现两个分支。
4.  后续区块使其中一条分支获得更强的链选择优势，另一条分支可能不再成为主链。

如果未进入主链的区块完全得不到任何奖励，矿池等拥有更强算力或更好传播能力的参与者，可能更容易从分叉中获得优势。

## 七、叔父区块是什么

课程使用 uncle
block（叔父区块）来称呼某些有效但没有进入主链的竞争区块。它们与主链上的区块具有共同祖先，因网络传播延迟或竞争分支未获胜而没有成为主链的一部分。

在课程介绍的历史以太坊设计中，主链区块可以引用符合规则的叔父区块。这样，部分未成为主链的有效工作仍可被协议识别并获得一定奖励。

## 八、叔父区块奖励的动机

叔父区块机制试图缓和两个问题：

- **减少工作浪费**：有效但未进入主链的区块仍可能获得部分奖励。
- **减轻中心化偏差**：个体矿工产生的区块更容易因传播较慢而成为竞争分支；对合格叔父区块给予奖励，可以降低其收益完全归零的概率。

课程所讲的历史规则示例中，距离为 1 的叔父区块可获得基础区块奖励的
$7/8$，引用叔父区块的主链区块还可获得与叔父数量相关的额外奖励（课程示例为每个叔父对应基础奖励的
$1/32$）。这些比例属于特定历史规则示例，具体奖励取决于协议版本和叔父区块与引用区块的距离。

## 九、GHOST 的核心直觉

GHOST 是 Greedy Heaviest Observed Subtree
的缩写，可理解为“贪心选择观察到的最重子树”。其设计动机是让链选择考虑分叉结构中被观察到的工作，而不是只看一条路径上的区块数量。

课程讨论的是以太坊对相关思路的历史改造，尤其强调叔父区块的引用和奖励机制。实际链选择还需遵循具体客户端版本中的共识规则，不能仅凭
GHOST 名称推断所有细节。

## 十、为什么它不能消除所有分叉

叔父区块机制只能改变分叉产生后的奖励与处理方式，不能消除网络延迟，也不能保证所有区块都进入主链。分叉频率仍受出块间隔、区块传播时间、网络拓扑、算力分布和区块大小等因素影响。

同时，奖励设计会影响参与者策略。若奖励比例、可引用范围或链选择规则发生变化，矿工的收益和系统的中心化倾向也可能变化。

## 十一、与比特币课程模型的对比

| 维度     | 比特币课程模型                             | 以太坊历史设计示例                   |
|----------|--------------------------------------------|--------------------------------------|
| 出块节奏 | 较长的目标间隔                             | 更短的目标间隔                       |
| 分叉处理 | 未被选中分支上的区块通常不获得主链区块补贴 | 合格叔父区块可按规则获得部分奖励     |
| 设计关注 | 通过工作量与链选择形成稳定历史             | 还关注短间隔下的分叉率和矿工收益偏差 |

## 十二、本讲小结

短出块间隔提高响应速度，却增加区块传播期间发生竞争分叉的机会。GHOST
思路与叔父区块机制试图在历史链选择、有效工作奖励和中心化偏差之间取得平衡；它们属于特定历史协议设计，不能脱离具体版本理解。

## 十三、PoW 的成本来自哪里

在 PoW
系统中，矿工通常投入资金购买设备和电力，再通过持续计算参与出块竞争。其安全性与攻击者能够获得的有效算力、设备和电力成本有关。

课程强调了两点：

1.  **参与成本较高。** 专用矿机、能源和维护成本可能限制普通参与者。
2.  **攻击资源来自系统外部。**
    攻击者可以先在外部经济体系中积累资金，再购买设备或租用算力，对目标链发起攻击。

课程以当时的能耗统计说明 PoW 的能源开销。那些数字属于 2018
年课程使用的历史估计，不宜作为今天的能耗数据引用。

## 十四、PoS 的基本思想

PoS
将参与共识的权重与质押的链内资产联系起来。课程用“直接比较投入的权益，而不是先把资金换成矿机再比较算力”来解释这一思路。

一个简化的流程如下：

1.  参与者将一定数量的原生代币锁定为质押资产。
2.  协议根据规则选择或授权验证者参与提议、投票等共识工作。
3.  验证者遵守协议时可获得奖励。
4.  对违反协议的行为，系统可以扣减或没收部分质押资产。

质押资产承担两种作用：一方面体现参与者的经济权益，另一方面为违反规则的行为提供可处罚的经济担保。

## 十五、PoW 与 PoS 的攻击资源差异

| 比较维度             | PoW                                                | PoS                                          |
|----------------------|----------------------------------------------------|----------------------------------------------|
| 参与共识的主要资源   | 算力、硬件与电力                                   | 被协议认可并质押的链内资产                   |
| 主要运行成本         | 持续计算与能源消耗                                 | 质押机会成本、验证运行成本与协议风险         |
| 攻击者需要控制的资源 | 足够比例的有效算力                                 | 足够比例的有效质押权重，或利用协议漏洞       |
| 惩罚方式             | 攻击投入可能成为沉没成本，收益与风险取决于攻击情形 | 可对可识别的违规行为执行罚没或削减质押       |
| 关键风险             | 算力集中、租赁算力、矿池集中                       | 权益集中、验证者串谋、投票规则与罚没机制设计 |

课程把 PoS
描述为一种“闭环”安全资源结构：攻击者必须先获得目标系统中的代币，才能获得相应的质押权重。这个描述有助于比较两种机制的资源来源，但不能理解成
PoS
不可能被攻击。代币可能被集中购买、借入或通过其他方式控制，系统内部也可能存在治理、实现和经济设计风险。

## 十六、Nothing at Stake：无利害关系问题

早期 PoS 设计面临的一个典型问题是 **Nothing at Stake（无利害关系）**。

假设区块链出现两个分叉：

- 在 PoW
  中，矿工若同时在两条分叉上挖矿，就要分散自己的算力，通常会降低在任一分叉上成功出块的概率。
- 在某些早期 PoS
  设计中，验证者可以在两个分叉上都投票，而质押资产并未因这种行为受到惩罚。这样一来，支持多个互相冲突的分叉可能几乎没有额外成本。

这会削弱验证者选择唯一历史的经济动机。因此，PoS
协议需要明确哪些投票属于可罚没的冲突行为，并让违规证据可以被其他节点验证。

## 十七、课程介绍的 Casper 与最终性

课程介绍的早期 Casper 方案试图在 PoW
链上增加验证者投票，为一部分区块建立更强的确认保证。

### 17.1 验证者与保证金

- 验证者先锁定一定数量的以太币作为保证金。
- 验证者根据协议对候选检查点投票。
- 投票权重与保证金数量相关。
- 诚实参与可获得奖励；未履行职责可能受到惩罚；对互相冲突的候选历史重复投票等可罚没行为，可能导致保证金被没收。

保证金使投票行为具有经济后果。若没有可执行的惩罚，验证者可能在多条冲突分叉上同时投票。

### 17.2 检查点与两阶段投票

课程使用了类似两阶段提交的类比来说明投票流程：

1.  **Prepare：** 验证者先对候选检查点表达支持。
2.  **Commit：** 在满足协议要求后，对检查点进行提交确认。
3.  每一轮投票需要达到按质押权重计算的超多数阈值。课程举例使用了 `2/3`
    作为门槛。
4.  连续的检查点达到相应条件后，可以形成课程所说的 finality（最终性）。

这里的 `2/3`
是课程讲解该历史方案时使用的关键阈值。实际协议的检查点定义、投票结构、时序和罚没条件必须以相应版本规范为准。

### 17.3 最终性与概率性确认

PoW
链中，等待更多区块通常会降低交易被重组回滚的概率，但不能仅凭“已经有六个确认”就把概率性确认理解为数学上绝对不可逆。

课程中的 Casper
思路通过验证者投票为检查点建立最终性条件。若想推翻已经获得最终性的历史，攻击者需要面对验证者投票规则及相应的经济惩罚，而不只是单纯增加算力。

## 十八、验证者奖励、惩罚与退出等待期

课程描述的设计包括：

- 正常履行职责的验证者获得奖励。
- 验证者长时间不参与投票，可能导致共识进展受阻，并受到相应惩罚。
- 对冲突分叉同时投票等违规行为，可触发保证金罚没。
- 退出后并非立即取回全部保证金；等待期为网络提供检查和提交违规证据的机会。

这套机制需要在三个目标之间权衡：鼓励在线参与、抑制冲突投票、避免对短暂网络故障施加过度惩罚。

## 十九、PoS 的优点与局限

**潜在优势**

- 不依赖 PoW 式持续哈希竞争，可显著减少这类共识机制的挖矿能耗。
- 通过质押与罚没，把部分攻击成本绑定到链内经济资产。
- 可为协议设计更明确的检查点投票与最终性规则。

**需要解决的问题**

- 如何防止验证者在冲突分叉上重复投票。
- 如何定义可证明的违规行为与合理的罚没范围。
- 如何防止质押权重过度集中。
- 如何处理验证者离线、网络分区和共识无法继续推进的情况。
- 如何确保验证者激励与长期网络安全目标一致。

课程也讨论了 PoW
的另一种观点：挖矿可以为难以储存或远距离输送的剩余电力提供需求。这个论点属于能源系统层面的争论，不能单凭这一点判断某种共识机制整体更优。

## 二十、本讲小结

PoS
将共识参与权与质押资产联系起来，并通过奖励、罚没和投票规则来处理分叉选择。课程介绍的
Casper 方案重点是用验证者投票为检查点建立最终性，从而补充单纯依赖 PoW
链累计工作量的确认方式。
