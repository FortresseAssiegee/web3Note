## 二、区块头和区块体

### 2.1 区块头：把内容摘要与历史上下文绑定

区块头并非所有交易内容的缩略表示。它是一组结构化字段，其中包含父块引用、状态或列表承诺以及验证所需的元数据。

把交易或状态组织成树，只能得到一个根 $R$。当根被放入区块头，再与父块、块号、时间等字段共同参与区块标识计算时，根才被放到一个具体历史位置。

一个简化关系是：

$$
\text{blockHash}_h=
H(\operatorname{Encode}(\text{parentHash},R_{\text{state}},
R_{\text{tx}},R_{\text{receipt}},\ldots)).
$$

这不是所有链通用的字节公式，只表达内容承诺被区块头绑定。比特币和以太坊的哈希、编码和字段均不同，真正实现必须使用各自协议。

如果只改变交易内容，交易根通常会变；进而区块头标识变；再进而后继区块引用需要变化。但这只是可检测的链式依赖。攻击者能否让新的历史被接受，仍取决于共识与确认规则，不能用“哈希会变化”单独证明绝对不可篡改。

<a id="sec-061"></a>
### 2.2 Ethereum：先区分执行区块与信标区块

以太坊 PoS 系统包含执行层与共识层。学习“区块头”时要先问：讨论的是哪一层？

| 对象 | 主要承担的任务 | 典型内容 |
|---|---|---|
| 执行区块头 | 绑定交易执行相关结果 | 账户状态根、交易根、收据根、Gas 等 |
| 执行负载 | 向执行引擎提供交易执行所需数据 | 交易列表及相应执行字段 |
| 信标区块 | 承载共识操作和执行负载等数据 | slot、提议者、证明/投票相关对象、执行负载 |
| 信标状态 | 维护共识状态 | 验证者集合、质押余额、检查点等 |
| 共识层执行负载头 | 对执行负载的 SSZ 视图做摘要化表示 | 字段值以及交易/提款列表的 SSZ 根等 |

同名字段必须写出所在结构，才能确定承诺对象：

| 精确字段路径 | 承诺的状态与关系 |
|---|---|
| 执行区块头的 `stateRoot` | 执行后的账户状态 MPT 根 |
| `BeaconBlock.state_root`、`BeaconBlockHeader.state_root` | 对应信标状态的 SSZ 根，承诺共识状态 |
| `ExecutionPayload.state_root`、`ExecutionPayloadHeader.state_root` | 仍然是执行层账户状态 MPT 根；对同一个执行区块，与执行头 `stateRoot` 同值 |

一个执行状态根出现在共识层的 SSZ 容器中，并不会使这个字段的值变成信标状态根。容器本身的 SSZ 根与其中保存的执行状态根是不同层次的承诺。账户 MPT 证明应针对执行状态根验证，不能直接拿去验证 `BeaconBlock.state_root`。

执行层常见 MPT 节点使用 RLP 与 Keccak；共识层使用 SSZ 及其 Merkle 化规则。**SSZ，Simple Serialize**，是一套根据类型进行编码和树化的规则，不是 RLP 的另一种拼写。

**资料：**[Ethereum SSZ 文档](https://ethereum.org/en/developers/docs/data-structures-and-encoding/ssz/)；[Phase 0 共识规范中的 BeaconBlock 与 BeaconBlockHeader](https://ethereum.github.io/consensus-specs/specs/phase0/beacon-chain/)；[Capella 共识规范中的 ExecutionPayload 与 ExecutionPayloadHeader](https://ethereum.github.io/consensus-specs/specs/capella/beacon-chain/)。

<a id="sec-062"></a>
### 2.3 执行层头的核心字段：理解它证明什么

下表给出历史上稳定、适合学习的核心含义。它不是逐字节的完整序列化规范，也不声称覆盖 2026 年所有网络与升级。

| 字段或常见 JSON 名称 | 含义 | 阅读时的注意点 |
|---|---|---|
| `parentHash` | 父执行区块的哈希 | 将当前块连接到特定父块 |
| `sha3Uncles / ommersHash` | ommer 列表的承诺 | 合并后列表为空，保留规范常量 |
| `miner / feeRecipient` | 执行费用接收相关地址 | PoS 下旧 JSON 名字可能仍叫 miner，不代表仍在挖矿 |
| `stateRoot` | 区块执行完成后的账户状态根 | 不是父状态根，也不是每笔交易后的所有状态根列表 |
| `transactionsRoot` | 本块交易列表的执行层 Trie 根 | 键是块内索引编码 |
| `receiptsRoot` | 本块收据列表的执行层 Trie 根 | 对应执行结果，与交易根不同 |
| `logsBloom` | 日志地址与 topics 的筛选结构 | 2048 bit，只做候选筛选 |
| `difficulty` | 历史 PoW 难度字段 | 合并后按规范为 0 |
| `number` | 执行区块号 | 不必与信标 slot 数字相同 |
| `gasLimit` | 执行 Gas 上限相关字段 | 不是区块字节数 |
| `gasUsed` | 实际消耗的执行 Gas | 不能直接当成 CPU 秒数 |
| `timestamp` | 区块时间字段 | 要满足目标协议规则 |
| `extraData` | 受长度约束的附加数据 | 不是任意大文件存储区 |
| `mixHash / prevRandao` | 合并后承载 prevRandao 语义 | 旧字段名可能保留，不再是 PoW 混合摘要语义 |
| `nonce` | 历史 PoW nonce 字段 | 合并后按规范固定为零 |

这些字段的客户端映射可在 [Geth core/types/block.go](https://github.com/ethereum/go-ethereum/blob/master/core/types/block.go) 中核对。观察 RPC 数据时还应区分原始头字段与客户端额外返回的便利字段，例如接口中出现 `hash`，不意味着原始头把自己的哈希也放进去递归计算。

合并后的常量由 [EIP-3675](https://eips.ethereum.org/EIPS/eip-3675) 规定；`mixHash` 的新语义需结合 [EIP-4399](https://eips.ethereum.org/EIPS/eip-4399)，不能停留在 EIP-3675 表格中的初始常量说明。

<a id="sec-063"></a>
### 2.4 随升级追加的字段：一张版本边界表

| 升级或规范 | 相关追加/变化 | 对本讲的意义 |
|---|---|---|
| London / EIP-1559 | `baseFeePerGas` | 头包含执行 Gas 基础费用参数 |
| Shanghai / EIP-4895 | `withdrawalsRoot` | 执行层头承诺提款列表 |
| Cancun / EIP-4844 | `blobGasUsed`、`excessBlobGas` | blob 使用量与费用调整状态 |
| Cancun / EIP-4788 | `parentBeaconBlockRoot` | 绑定父信标区块根 |
| Prague / EIP-7685 | `requestsHash` | 承诺执行层产生的请求集合 |

对应一级资料：[EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)、[EIP-4895](https://eips.ethereum.org/EIPS/eip-4895)、[EIP-4844](https://eips.ethereum.org/EIPS/eip-4844)、[EIP-4788](https://eips.ethereum.org/EIPS/eip-4788)、[EIP-7685](https://eips.ethereum.org/EIPS/eip-7685)。

这张表的用途是学习“头结构会随分叉改变”，不是宣布 Prague 是当前最后一次升级。客户端主分支还可能包含为后续规则准备的可选字段；一个字段出现在 `master` 代码中，并不能单独证明某个网络已经激活它。

解析一个历史区块时，应根据该网络的分叉配置与区块时间/高度确定哪些字段适用。旧字段不足或新字段多出，都是区块哈希计算不一致的常见原因。

#### 2.4.1 并不是每个新字段都叫 MPT 根

`requestsHash` 不能因为也是 32 字节，就按 MPT 根算法处理。EIP-7685 对非空、按请求类型排序的请求项分别做 SHA-256，再对中间摘要的拼接做 SHA-256，形成其规定的承诺。

因此，阅读根、哈希、摘要一类字段时，每次都要核对：

- 承诺的对象；
- 是否有排序；
- 使用哪一种哈希；
- 是否有层次树；
- 空集合怎样编码；
- 字段在哪一层被使用。

“以太坊用 Keccak”是一条过粗的口号，不代表它的所有子协议、所有承诺都用同一种哈希函数。

#### 2.4.2 同名的 transactions_root 也可能不是同一个根

这是执行层与共识层交界处很容易踩的坑：

| 所在位置 | 名称 | 计算对象与机制 |
|---|---|---|
| 执行层 RLP 区块头 | `transactionsRoot` | 按块内索引构造的交易 MPT 根 |
| 共识规范 `ExecutionPayloadHeader` | `transactions_root` | 交易列表的 SSZ `hash_tree_root` |
| 执行层 RLP 区块头 | `withdrawalsRoot` | EIP-4895 规定的提款 Trie 根 |
| 共识规范 `ExecutionPayloadHeader` | `withdrawals_root` | 提款列表的 SSZ `hash_tree_root` |

两种视图都可以承诺同一份列表，但编码、树形和哈希规则不同，根值不应想当然地视为相同。

**直接依据：**[Capella 的 process_execution_payload](https://ethereum.github.io/consensus-specs/specs/capella/beacon-chain/#modified-process_execution_payload) 显式用 `hash_tree_root(payload.transactions)` 和 `hash_tree_root(payload.withdrawals)` 构造共识层负载头。这是查看准确类型比只看字段名字更可靠的例子。

### 2.5 区块体里面有些什么

在执行区块的常见结构中，区块体主要携带交易列表，并按适用分叉包含相关附加列表，例如提款。合并后的 ommer 列表为空。

两个常见误解需要改正。

**误解一：所有账户状态都直接装在每个区块体里。**通常不是。节点根据父状态执行交易等规定操作，得到新状态。头保存状态根；实际状态数据库另行维护。否则每出一个块都复制整个世界状态，成本会非常高。

**误解二：RPC 能查到收据，所以收据一定作为普通区块体字段一起传播。**收据是执行产生的数据，节点可以保存并通过接口提供。它与区块体的原始结构是不同层面。区块头里的收据根能约束收据，但不意味着收据列表在所有网络消息与编码中都和交易列表放在一起。

区分“原始区块结构”“执行后派生数据”“本地数据库对象”“RPC 返回 JSON”后，阅读客户端代码会清楚很多。同一个 `Block` 对象里可能还有缓存、接收时间、来源等字段，这些也不是都参与共识哈希。

<a id="sec-065"></a>
### 2.6 Blob 数据与交易列表的关系

EIP-4844 引入 blob 交易后，交易中可包含与 blob 承诺相关的版本化哈希，但大块 blob 内容并不是普通 EVM calldata 的等价替代。EVM 不能直接像读取 calldata 那样读整个 blob 内容。

这也说明“链上有一个承诺”与“所有字节都永久存储在交易体里、供合约随时读取”不同。具体 blob 数据传输和保存遵循相应共识与网络规则，不能仅从交易根推出数据会永久可取。

本讲不把后续数据可用性升级概括成固定的 2026 参数，因为不同升级可能调整数量、费用和网络细节。稳定的学习点是：**数据对象、承诺、交易引用、传输载体和保留时间分别需要定义。**

<a id="sec-066"></a>
### 2.7 教学补充：与比特币区块头对照

比特币传统区块头固定为 80 字节：

| 字段 | 字节数 | 核心意义 |
|---|---:|---|
| version | 4 | 版本与规则信号 |
| previous block hash | 32 | 父块头引用 |
| Merkle root | 32 | 本块交易承诺 |
| time | 4 | 区块时间 |
| nBits | 4 | 压缩目标表示 |
| nonce | 4 | PoW 搜索用变化字段 |
| 合计 | 80 | 不包含完整交易列表 |

这与以太坊变长 RLP 头完全不同。比特币链上的交易验证围绕 UTXO 模型；不能因为以太坊头有 `stateRoot`，就推测比特币传统头也有同样的全球账户状态根字段。

**依据：**[Bitcoin Developer Reference：Block Headers](https://developer.bitcoin.org/reference/block_chain.html#block-headers)。比较两条链时，应对照实际承诺对象，不应只把“哈希”“树”“区块头”三个共同名词机械匹配。

<a id="sec-067"></a>
### 2.8 从一次修改看所有承诺如何连动

假设以太坊某块里一笔交易的收款地址改变了：

1. 交易编码改变，原签名通常不再适配这个新交易消息。
2. 即使重新获得了合法签名，交易列表对应的根也会改变。
3. 执行效果可能改变，导致相关账户或存储状态变化。
4. 收据和日志也可能变化，收据根、logsBloom 可能随之变化。
5. 这些变化进入执行头，使执行区块标识改变。
6. 后续对该执行结果的共识认证和父引用关系必须相应一致。

这里使用“可能”是有意义的：有些字段变化不一定改变全部状态字段；两个不同操作也可能在某些结果上相同。但交易承诺绑定原始交易字节，执行规则约束结果，签名约束授权，几种机制各自处理不同环节。

把它们都叫作“加密保证不可篡改”会丢失细节。准确的说明是：**签名检查授权，编码与哈希检查内容绑定，树提供局部证明，执行验证检查状态转换，共识决定认可哪条历史。**

## 三、附录 A：术语与易混淆概念

| 术语 | 一句话解释 | 需要避免的误解 |
|---|---|---|
| 哈希摘要 | 固定长度的内容指纹 | 不是可解密压缩包 |
| 承诺 | 用较短对象绑定某份数据或状态 | 不自动提供保密性 |
| Merkle root | 对树中内容的顶层摘要 | 根可信性仍需来源 |
| Trie | 按键组成逐段走路径的树 | 不是普通哈希表的别名 |
| Patricia 压缩 | 合并无分叉的连续路径 | 不会消除路径匹配成本 |
| nibble | 4 bit，取值 0–15 | 不等于一个 ASCII 字符 |
| HP | 带奇偶与节点类型标记的紧凑路径编码 | 不是加密 |
| RLP | 字节串和列表的确定性编码 | 不自动解释业务类型 |
| SSZ | 根据类型编码和 Merkle 化的一套规则 | 不等于 RLP |
| 子节点内联 | 把整个 RLP 编码不足 32 字节的子节点嵌入父节点表示 | branch 也可内联；与“两项短节点”不是同一分类 |
| stateRoot | 特定执行状态的账户承诺 | 不等于区块全部历史记录 |
| storageRoot | 某账户存储的承诺 | 验证时需要先绑定账户 |
| receipt | 交易执行结果记录 | 不是原交易本身 |
| 非包含证明 | 认证结构证明某键不存在 | 不等于服务器没返回数据 |
| 多重证明 | 多个查询共享证明节点 | 不自动证明集合完整 |
| Bloom | 快速排除候选的近似集合结构 | 阳性不能用于最终授权 |
| 假阳性 | 不存在却被标为可能存在 | 不等于密码学哈希被攻破 |
| 最终性 | 某种共识规则下的历史稳定性保证 | 不是 Merkle 树单独提供的 |
| 数据可用性 | 需要时能够取得数据 | 有根不代表有数据 |
| 持久化 | 按存储策略保留并可恢复数据 | 不等于网络已达成共识 |

## 四、附录 B：分层练习与参考答案

<a id="sec-070"></a>
### 4.1 1 基础题

**1. 已有四叶 Merkle 树，要验证第 3 个叶子，为什么通常只需要两份兄弟摘要？**

因为目标到根有两层，每层只缺另一侧的摘要。目标原文由验证方自己哈希；第一层得到半棵树摘要，第二层得到根。这个结论假设四叶平衡二叉树、固定树规则，不能直接用于任意 MPT 证明大小。

**2. `[]byte("ab")` 与十六进制字节 `ab` 相同吗？**

不同。前者是两个 ASCII 字节 `61 62`，后者是一个字节 `ab`。对应 nibble 序列分别是 `[6,1,6,2]` 与 `[10,11]`。

**3. MPT branch 为什么有第 17 项？**

为了保存恰好在该节点结束的键的值，使一个键可以同时是另一个键的前缀。前 16 项分别指向下一位 nibble 的子树。

**4. 片段 `[1,2,3]` 的 leaf HP 编码是什么？**

长度为奇数，leaf 标志 2 再加奇数标志 1，首 nibble 为 3。组合 `[3,1,2,3]`，得到字节 `31 23`。

**5. 某叶子的 Value 正好 32 字节，能否断言它是子节点哈希？**

不能。leaf 的第二项是业务值。是否为子引用首先由节点类型和字段位置决定。只有在子引用语义位置上，才按引用编码规则处理内联或哈希。

<a id="sec-071"></a>
### 4.2 2 机制题

**6. `RLP(node)` 长度恰好 32 字节，作为非根孩子时内联吗？**

不内联。规则是小于 32 才内联，达到 32 使用节点编码的 Keccak 哈希引用。

**7. 删除 `car` 时，为何不能把整个 `car` 子树删掉？**

因为 `cart` 等更长键可能仍通过该节点。应删除 `car` 的终止值，再仅清理不再承载任何值和孩子的节点，并按所用结构做压缩。

**8. 交易 Trie 的 Key 是交易哈希吗？**

不是。按本讲讨论的以太坊执行层规则，它是交易在块内的索引的 RLP 编码。交易哈希与 Trie 索引键是不同的标识。

**9. 证明缺少一个应该存在的中间节点，能否作为非包含证明？**

不能。那是证据不足。非包含证明需要在经过认证的路径上到达空槽、不匹配叶子或其他合法终止情形。

**10. 一个合约存储槽证明通过，就能确认它属于指定合约吗？**

如果只把某个任意 `storageRoot` 当可信输入，还不能。需要先从可信 `stateRoot` 验证指定合约账户记录，再取其中 `storageRoot` 验证槽。

**11. 为什么两份正确的包含证明不能说明查询结果完整？**

因为它们只覆盖已经返回的两项。另一个符合条件但未返回的项，可以完全不影响这两份证明的正确性。需要范围、全集或计算完整性等额外约束。

<a id="sec-072"></a>
### 4.3 3 计算与反例题

**12. Bloom 使用 $m=10000,n=1000,k=7$，近似误判率如何写？**

$$
p\approx(1-e^{-0.7})^7\approx0.0082.
$$

这是常用独立均匀模型下的近似，不是有限实现的精确保证。

**13. 计数 Bloom 的查询返回真，是否可以马上删除该元素？**

不应仅据此删除。它可能是假阳性；错误减计数会破坏其他真实元素。删除应由精确成员记录或可靠业务状态确认。

**14. 同一块 Bloom 分别命中合约地址 A 和 topic Y，能确认 A 发出了 Y 事件吗？**

不能。A 和 Y 可能来自两条不同日志，也可能存在位映射假阳性。应检查具体日志，并按需求验证它与收据根的关系。

**15. `Commit()` 返回根，能否认为该区块已最终确认？**

不能。函数调用属于本地数据结构或数据库流程，共识接受与最终性是另一层状态。

**16. 以太坊 `ExecutionPayloadHeader.transactions_root` 一定等于执行层 RPC 的 `transactionsRoot` 吗？**

不能这样认为。前者在共识规范中由 SSZ 列表树化得到，后者是执行层交易 MPT 根。名称相似不代表算法相同。

<a id="sec-073"></a>
### 4.4 4 实践任务

按以下顺序改动示例，比较现象：

1. 在 Merkle 程序中把 5 个元素改为 1、2、6 个，检查证明长度与方向。
2. 只改变一个叶子值，观察旧证明对新根是否还能验证。
3. 在 HP 程序中增加空 extension 的编解码例，随后思考为什么结构层仍应避免冗余扩展。
4. 在 Trie 程序中反转插入顺序，确认相同字典最终根是否一致；这是检验自定义编码确定性的练习。
5. 删除 `cart` 而保留 `car`，观察终止值与子路径的独立性。
6. 在 Bloom 程序中不断增加插入数，统计一批确定未插入键的误报比例，与近似公式比较。
7. 将 Bloom 改为多 goroutine 写入前，先设计同步策略；不能把偶尔运行结果正确当作无数据竞争的证据。

第 6 项是你可以进行的实验设计，不是本文已经完成的性能实验。要比较不同方案，需要记录数据量、查询集、Go 版本、硬件、参数与重复次数，不能把一次运行耗时直接归因于算法优劣。

## 五、三棵树分别记录什么

### 5.1 状态树（State Trie）

状态树承诺执行区块后所有账户的状态。它跨区块保留未变化的结构，并只为发生变化的路径建立新节点。

### 5.2 交易树（Transaction Trie）

交易树组织当前区块中的交易。课程介绍的历史以太坊实现使用
MPT，并以交易在区块中的序号作为查找键。交易顺序由最终被接受区块中的交易列表确定。

交易树的根哈希写入区块头，允许验证某笔交易是否属于该区块的交易集合。

### 5.3 收据树（Receipt Trie）

交易执行后会生成收据记录。收据包含与执行结果有关的信息；在课程所讲的历史结构中，收据也可关联日志与
Bloom Filter 等信息。收据树的根哈希承诺该区块的收据集合。

交易树与收据树按交易位置对应：某个交易的收据可以通过相应索引定位。

## 六、为什么需要收据树

智能合约交易的执行可能产生复杂结果，例如日志事件。若每次查询都扫描全部交易并重新执行，成本可能很高。收据树把执行后记录组织起来，使节点可以证明某个收据与区块中的承诺相匹配。

收据证明与交易包含证明回答不同问题：

- **交易树证明**：某笔交易被纳入区块。
- **收据树证明**：某个执行收据被纳入区块。
- **状态树证明**：某个账户状态与区块状态根一致。

单独的包含证明并不自动解释全部业务语义，仍需理解相应交易与收据字段。

## 七、Bloom Filter 的基本思想

Bloom Filter
是一种紧凑的集合成员查询结构。它通过一个位向量和若干哈希映射，记录元素可能出现的位置。

构建过程：

1.  初始化长度为 $m$ 的位向量，所有位设为 0。
2.  对每个元素计算若干个哈希映射。
3.  把这些映射对应的位置设置为 1。
4.  查询元素时，重新计算这些位置。
5.  若查询位置中有任何一位为 0，则元素一定不在集合中；若全部为
    1，则元素可能在集合中。

### 7.1 误报与漏报

标准 Bloom Filter 在正常构建和查询条件下可能出现**假阳性（False
Positive）**：查询结果显示元素可能存在，但实际不存在。它不会因哈希碰撞而产生假阴性（False
Negative）：若查询对应位中存在 0，就可以判定元素不在集合中。

这种性质适合先排除明显不相关的区块，再对候选区块执行更精确的查询。

## 八、Bloom Filter 如何帮助查询日志

课程介绍的历史以太坊结构中，区块级 Bloom Filter 使用 2048
位向量，并通过哈希结果设置多个位置（课程示例中为三个位置）。区块头和收据会包含
Bloom Filter 相关信息。若要查询某个合约地址或事件主题：

1.  先检查区块级 Bloom Filter。
2.  若查询条件不可能匹配，跳过该区块。
3.  若可能匹配，再检查相关收据或取得更完整的数据。
4.  最后检查实际日志和交易，确认查询结果。

Bloom Filter 只是预筛选工具，不能把“可能存在”当作已验证的交易或事件。

## 九、以太坊作为交易驱动的状态机

以太坊执行过程可以抽象为状态转移：

$$
S_{n+1}=Apply(S_n, T_n)
$$

其中 $S_n$ 是当前账户状态，$T_n$ 是按协议规则执行的交易集合，$Apply$
表示确定性的状态转移过程。所有节点必须按同一规则计算后续状态，才能比较状态根并达成一致。

## 十、为什么不能轻易删除位

简单 Bloom Filter 的位向量只记录某些位置被置为
1，并不记录每个位由多少元素贡献。若删除一个元素时把对应位置清零，可能误删其他元素也依赖的位置，造成假阴性。因此，标准位向量型
Bloom Filter 不支持简单删除；若要支持删除，需要计数型等额外结构。

## 十一、三棵树的跨区块差异

- 状态树表示执行后的全局账户状态，未改变的子树可在相邻状态间共享。
- 交易树只组织当前区块的交易。
- 收据树只组织当前区块的执行收据。

这种区分能避免把“全局状态”“输入交易记录”和“执行结果”混为一谈。

## 十二、本讲小结

状态树、交易树和收据树承诺三类不同数据。Bloom Filter
通过紧凑位向量帮助筛选可能相关的区块和日志，但最终仍需验证实际数据。
