## 一图看懂本篇流程


数字承诺像把答案写进信封并封口：先公开封口后的标记，之后再打开信封供大家核对。零知识证明则像只证明自己满足某个条件，而不公开全部隐私资料。

> **怎么读这张图：**从左向右看，先确认输入是什么，再看系统如何检查和处理，最后看结果如何保存或验证。图中是帮助理解的简化流程，协议细节仍以本篇后续说明和官方规范为准。


例如，投标截止前先提交报价承诺值，截止后公开报价和随机数，任何人都能核对报价是否与先前承诺一致。

## 二、把本讲各机制放到同一个业务案例中

<a id="sec-061"></a>
### 2.1 场景：带私密附件的多方采购审批

这是一个原创教学设计，用于理解分工，不是声称已部署的产品或新的研究贡献。

设采购系统有三类对象：公开审批状态、私密合同正文、多方批准消息。

1. **合同正文**用 AEAD 加密，密钥在链下授权管理。
2. **内容摘要**由固定编码产生，并在批准消息中绑定；若摘要会泄露低熵内容，要重新设计承诺方式。
3. **批准消息**包含业务域、合同标识、金额、执行者、nonce 和期限。
4. **个人批准**由相应私钥签名；合约验证消息和业务权限。
5. **多人批准**可以采用合约多签，也可以在明确假设下使用门限或多签协议。
6. **链上状态**记录批准是否消费、合同版本和流程进度。
7. **批量查询**可用认证树证明某条记录与可信根对应。

每个模块的失败含义不同：密文校验失败拒绝解密；签名失败拒绝授权；nonce 重复拒绝执行；Merkle 证明失败拒绝某个数据归属声明。不能把它们统称为一个模糊的“验证失败”，否则排错时很难知道哪项假设出了问题。

<a id="sec-062"></a>
### 2.2 用攻击者的动作检查设计

| 攻击者动作 | 由哪个检查应对 | 仍可能发生的问题 |
|---|---|---|
| 修改已签名金额 | 签名绑定金额 | 用户原本就签错金额，算法无法替用户判断 |
| 重放已批准操作 | nonce/消费状态 | 分叉或多环境域重复还需协议处理 |
| 把密文移到另一合同编号 | AAD 绑定对象 | 若双方构造 AAD 不一致，正常请求也会失败 |
| 伪装成多人联合批准 | 安全多签协议或合约逐签验证 | 成员登记、密钥控制归属仍需管理 |
| 提交真实签名的假合同信息 | 业务审核与证据流程 | 签名只保证授权关系，不保证现实真实性 |
| 隐瞒应该提交的材料 | 任务定义、收件承诺、缺失记录等 | 有效性证明本身不必然证明完整性 |
| 删除存放在链外的合同文件 | 数据复制、可用性与恢复机制 | 链上摘要不能凭空还原已丢失的正文 |

这张表可作为继续学习 Web3 基础设施和预言机时的连接点，但不要把一个普通认证原语扩展解释为它没有定义过的系统保证。

### 3.2 如何运行纯标准库示例

```bash
go run code/ch03/hash_hmac/main.go
```

### 3.3 如何运行带模块依赖的示例

压缩包已经为三个外部依赖示例附上 `go.mod` 和 `go.sum`。进入对应目录，执行 `go mod download`，再执行 `go run .`。

如果是从本 Markdown 新建空目录，则各自执行一次：

```bash
go mod init example.com/cryptonotes/keccak

```

另两个例子使用独立目录及相应命令：

```bash
go mod init example.com/cryptonotes/schnorr

```

```bash
go mod init example.com/cryptonotes/bls

```

BLS 绑定涉及 CGO，需 C 编译器。在没有本地编译器的在线 Go 环境中，这个示例可能无法构建；其他纯标准库程序适合优先在线运行。

<a id="sec-067"></a>
### 3.4 如何编译 Solidity 示例

把合约保存为 `SignedRecord.sol`，在独立目录建立 npm 项目后使用固定依赖：

```bash
npm init -y
npm install --save-exact solc@0.8.30 @openzeppelin/contracts@5.0.2
npx solcjs SignedRecord.sol --bin --abi --base-path . --include-path node_modules --output-dir build
```

合约中的库导入路径由 `node_modules` 解析。上述 CLI 命令使用编译器的默认 EVM 目标生成 ABI 和字节码；本次本地执行测试另通过标准 JSON 输入设置 `settings.evmVersion = "shanghai"`，与测试虚拟机保持一致。配套压缩包中的 `verification/check_solidity.cjs` 保留了该编译设置和实际执行流程。只编译成功不能验证防重放；实际执行记录还检查了消息、域、nonce 和期限的失败分支。

## 四、复习题与参考答案

<a id="sec-070"></a>
### 4.1 先尝试自己回答

1. 为什么“SHA-256 的输出是 256 位”不等于“寻找任意碰撞需要 $2^{256}$ 次尝试”？
2. `H("ab" || "c")` 和 `H("a" || "bc")` 相等，是否破解了哈希的碰撞抗性？
3. 为什么公开手机号的 SHA-256 不能自动隐藏手机号？
4. GCM 的 nonce、交易 nonce、Schnorr 的临时秘密 $k$，分别是否应该保密？
5. 把租户编号放在 AAD 中，能否隐藏租户编号？它实际解决什么问题？
6. ECDH 协商计算成功，为什么仍不能确认对方身份？
7. ECDSA 签名正确，为什么转账仍可能失败？
8. 为什么 P-256 的签名不能直接交给 Ethereum 的 secp256k1 验签接口？
9. Schnorr 中为什么群元素模 $p$ 运算，响应标量模 $q$ 运算？
10. 若复用 $k$ 但两个消息恰好产生同一挑战，能否直接使用差分公式求出私钥？
11. BLS 的同消息快速聚合为什么需要公钥持有证明等前提？
12. BLS 签名聚合成 96 字节，是否意味着验证 1 万人投票时只要传输 96 字节？
13. MuSig2 的一个最终签名，是否意味着签名者之间无需交互？
14. EIP-712 域正确且签名有效，为什么仍需 nonce？
15. 什么是“有限单群”和“素数阶有限循环群”的关系？
16. 把签名算法迁移到一个新业务后，哪些保证需要重新检查？

<a id="sec-071"></a>
### 4.2 参考答案

**1.** 任意碰撞可以自由选择两条消息，存在生日加速，理想量级约为 $2^{128}$；命中特定摘要的原像问题是另一种目标。不能把原像与碰撞混成一个“破解”。

**2.** 没有。两个业务对象被编码成同一字节串，哈希函数接收到的输入完全相同。需要修复的是序列化的无歧义性。

**3.** 手机号有结构和有限候选空间，攻击者可以枚举候选并比较摘要。哈希的原像安全定义不能替一个低熵输入空间增加熵。

**4.** GCM nonce 通常可以公开，但要遵守算法使用规则；交易 nonce 通常公开，是状态机序号；Schnorr 的 $k$ 必须保密且按协议安全生成、单次使用。

**5.** 不能隐藏。AAD 认证但不加密，用来把密文绑定到正确租户和用途，防止跨对象搬运或字段修改。

**6.** 协商成功没有证明收到的公钥属于预期对象。经典中间人攻击分别建立 Alice–中间人和中间人–Bob 两条关系；每一条关系内部都能算出一致的共享秘密，但两条关系通常使用不同密钥。如果 Alice 与 Bob 已通过独立且经过认证的渠道核对密钥或完整握手，那么已经加入了额外认证机制，不能再忽略这个前提。

**7.** 签名只检查授权关系，余额、nonce、业务权限、执行顺序、费用或合约条件仍可能不满足。

**8.** 曲线参数与公钥点不同，签名编码和摘要规则也可能不同。算法名称都叫 ECDSA，不代表协议互操作。

**9.** $p$ 决定群元素在有限域中的表示与乘法；$q$ 是所选子群的阶，指数相差 $q$ 会产生同一群元素，所以标量在模 $q$ 下计算。

**10.** 不能直接套该式。分母 $e_1-e_2$ 为零，不可逆。但 nonce 复用依然是严重设计错误，攻击者可能得到更多不同挑战的响应。

**11.** 恶意公钥可以抵消诚实人的公钥，使聚合公钥退化为攻击者自己控制的公钥。PoP 等机制限制这种登记方式；具体前提依所用方案而定。

**12.** 不是。仍要确定消息、参与者、权重、位图或其他成员信息，还可能有登记证据与通信。96 字节只描述所选变体中的聚合签名对象。

**13.** 不是。MuSig2 的签名生成有明确交互过程和秘密 nonce 管理。最终表示短，不等于生成过程零成本。

**14.** 有效签名可被重复提交。域把不同环境和用途分开，nonce 与消费状态决定同一个环境内一份授权是否已经使用。

**15.** 素数阶循环群是有限单群的一类；有限单群并不全部是适用于 Schnorr 的循环群。用词不足以指定正确算法参数。

**16.** 至少检查消息定义、编码、身份绑定、权限、重放域、时间与状态、密钥生成和保管、攻击者能力、交互并发，以及失败处理。旧算法的数学保证不能自动覆盖新业务语义。

## 六、多人共管资产：为什么选择多重签名

把一个私钥直接切成多段，会带来两个问题：

1.  **可用性问题**：任何必需片段丢失，都可能导致资产无法花费。
2.  **安全性问题**：当攻击者已知部分私钥时，需要搜索的未知部分变少，整体安全性会下降。

多重签名采用另一种设计：多个参与者各自拥有独立密钥，花费条件要求一定数量的有效签名。例如，3-of-5
方案要求 5 个参与者中的任意 3
个完成授权。它可以容忍部分参与者离线或丢失密钥，同时避免把单个私钥当作可拼接的密码片段。

## 七、分布式系统的不可能结论与比特币共识

在异步分布式模型中，消息延迟没有已知上限。若远程节点暂时无法联系，观察者可能无法判断它已经崩溃，还是消息只是延迟了。类似的模型假设会限制系统能够提供的共识保证。

课程强调：比特币并没有通过 PoW
获得传统意义上“一旦决定就永不改变”的绝对最终性。它通过工作量竞争让诚实节点在一定假设下逐步收敛，并让重写更深的历史通常需要更大成本。

这与分布式系统理论的关系，应结合各自的模型和保证来理解：

- 理论结论通常针对明确的通信、故障和安全假设。
- 实际协议可能采用概率性收敛，而非严格的不可逆决定。
- 不能把“实际运行中通常稳定”直接等同于“在所有条件下绝对保证”。

## 八、挖矿结果为什么不能直接冒领？

假设矿工 A
找到一个满足难度的区块头。其他矿工若想把同一个结果据为己有，通常需要修改区块内容，例如把奖励交易的收款地址改成自己的地址。这样会改变区块中的交易哈希，进而改变
Merkle 根与区块头哈希，原来的工作量证明通常就不再满足要求。

因此，区块内容、奖励归属和工作量证明通过哈希依赖关系绑定起来。

| 问题                       | 正确理解                                                       |

## 十、本讲小结

比特币的安全性来自多个机制的组合：哈希值建立可验证引用，签名绑定授权，奖励交易与区块哈希相互绑定，共识机制处理多个候选历史。理解这些机制的边界，才能避免把某一项技术误认为完整的安全保证。
