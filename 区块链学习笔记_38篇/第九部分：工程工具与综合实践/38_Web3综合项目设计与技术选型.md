## 附录 A：把本讲与现代密码学教材联系起来

<a id="sec-040"></a>
### A.1 阅读教材时应掌握的三个层次

第一层是安全定义。例如“签名不可伪造”需要说明攻击者能获得什么签名查询、最终输出什么才算成功；“承诺绑定”需要说明攻击者不能对同一个承诺打开出何种矛盾；“零知识”需要说明验证者可见信息与可模拟性。第二层是构造与假设，包括哈希、群、配对和协议组合。第三层是实现与上下文，包括编码、随机数、域分离、密钥管理、验证路径和错误处理。[R1] [R2]

本讲很多错误都发生在第二层与第三层之间。permit 的 ECDSA 可以完全正确，但若域中的验证合约被替换，业务授权就变了；KZG 的配对验证可以成功，但若应用没有把实际执行批次与承诺绑定，证明就与业务数据脱节；一个 release tag 的签名可以有效，但若部署使用另一个产物，签名没有覆盖实际运行对象。教材帮助建立安全命题，工程笔记负责把命题连接到实际字节和状态。

### C.2 参考答案

1. 资产身份至少要结合网络与合约地址，名称和符号可重复。跨链封装资产还要检查发行、托管和赎回关系。
2. approve 修改 allowance，不直接转移余额。普通有限额度下，花费 40 后额度剩 60，余额按实际转移改变；最大值等实现特例要另查。
3. permit 的目的之一就是把 owner 授权转交其他人提交；验证根据签名字段，不要求提交人必为 owner。它主要设置 allowance，价格、路由和目标资产需另外绑定。
4. 单枚授权针对某个 tokenId，转移后清除；operator 授权覆盖该 owner 在此合集的资产。safe transfer 检查合约接收接口，不证明接收者所有行为安全。
5. 这是变长字段拼接的编码歧义，两组输入先变成相同字节，再得到相同哈希，并未构造不同字节的密码学碰撞。
6. 账户实现自己的授权验证；EntryPoint 维护并检查 sender/key 对应的 sequence，账户可附加 key 规则。
7. EIP-7702 提供 EOA 代码委托相关协议能力；ERC-4337 组织用户操作、验证、打包和费用流程。它们可组合，但不能互相替代全部职责。
8. 签名绑定交易请求，执行时的池子状态可能已被其他交易改变。合约需要检查 minOut、期限及其他执行条件。
9. AMM 曲线本身产生价格影响，例子还采用 0.3% 手续费并按整数向下取整，因此不能按交易前一比一的边际比例直接兑换。
10. 不一定。提款还可能依赖有效性证明、争议窗口、桥规则和额外提交；数据最终性和提款完成是不同状态。
11. EVM 兼容描述执行接口或语义，层级分类取决于共识、结算、证明和数据依赖。侧链、L1 或私有链也可兼容 EVM。
12. 不能。承诺是绑定数据的短对象，不是可逆压缩保存所有信息。恢复数据还需要实际 blob 或可靠的数据恢复来源。
13. 版本字节替换 SHA-256 摘要的首字节，保留后 31 字节，总计 32。哈希算法由协议固定，替换后结果不兼容。
14. 展开 $(X-4)(22+5X)$，得到 $5X^2+2X-88$；模 101 时它等于 $f(X)-91$，且 $f(4)=91$。
15. 不能。KZG 绑定多项式数据与声明值；执行正确性由额外证明或争议规则约束，数据可用性和保存期限由另一组机制处理。
16. 挑战者需要独立重执行，找出错误转换并构造可裁决证据。摘要无法凭空提供完整交易和状态读取信息。
17. 同名假资产可以被替换进履约结果。还要绑定链、资产合约、数量、接收者、验证域、nonce 和期限等上下文。
18. null 说明该节点当前未返回已包含 receipt；执行失败的已包含交易有 receipt，并反映失败状态。两者都不应与网络错误混同。
19. 其他合约也能发出相同 topic。只有结合发出地址、事件形状和资产语义，才能解释预期资产的转移。
20. 一行是重复采集，一行被标记移除；余下两条事件属于同一 tx1，所以事件数和交易数不同，总最小单位为 3,000,000。
21. 源码验证建立特定编译配置下的源码/字节码对应；提交签名绑定提交对象与密钥；产物证明联系产物摘要与构建来源。都不单独证明业务安全。
22. Squash 产生新的提交对象和 SHA，原签名覆盖的对象与新提交不同。需要核对实际发布对象及相应证据。
23. 还应记录标签解析到的提交、依赖锁、编译配置、产物 digest、构建来源与部署环境；并限制标签改写权限。
24. 语句被执行不代表错误 chainId、错误验证合约、重复 nonce 和跨版本状态都被测试。防重放需要明确不变量、负例和状态一致性检查。

| EntryPoint | 验证与执行用户操作的协调合约 | 钱包前端、排序器 |
| Paymaster | 按规则承担操作费用的合约角色 | 消除执行成本 |
| L2 settlement | 基础层按规则认可或裁决 L2 状态 | 排序器快速回执 |
| DA | 在规定模型和窗口内的数据可获得性 | 数据承诺、永久存储 |
| KZG commitment | 多项式数据的群承诺 | 可逆压缩、执行证明、加密 |
| Validity proof | 对规定状态转换关系的有效性证据 | 未纳入约束的业务真实 |
| Fault proof | 对错误声明进行裁决的证据机制 | 单纯举报或 |
| Intent | 用户授权的目标与边界 | 任意求解器可随意改变的请求 |
| Indexer | 将链数据转换为查询模型的组件 | 共识节点的全部功能 |
| SemVer | 对公共 API 兼容性的版本约定 | 自动完成状态迁移 |
| Signed tag | 被签名的 Git 标签对象 | 不可改写的名字、无漏洞证明 |
| Attestation | 关于产物来源等内容的可验证声明 | 对全部代码性质的证明 |

## 一、先识别业务瓶颈

区块链常被用于解决交易记录共享、数据难以被单方篡改、多个参与方缺少共同可信记录等问题。但应用中出现的延迟或成本，未必来自账本或支付技术。

### 案例：保险理赔

理赔流程可能耗时很长，但延迟通常涉及事故证据收集、责任认定、人工审核和争议处理。如果金额已经确定，实际付款可能很快完成。

因此，在引入区块链之前，需要区分：

- **业务审核问题：** 谁来确认事故是否发生、责任归属和理赔金额？
- **支付结算问题：** 在金额确定后，资金如何到达收款方？
- **记录协作问题：**
  多家机构是否需要共享一份可审计、难以被单方改写的记录？

区块链可能改善多方记录与协作，但不能仅靠写入链上的交易自动完成现实世界的事故认定。

## 二、供应链追溯：记录可信不等于输入真实

供应链系统可以记录农产品的产地、采摘时间、运输过程、仓储和销售流向。多个参与方共同维护记录，有助于追踪责任与发现记录变更。

但这里存在一个关键的信任边界：

- 区块链可以让已写入的记录更难被单方篡改；
- 它不能自动验证录入时提供的信息是否真实；
- 如果有人在源头就把非有机蔬菜标记为有机，或者在运输中调换商品，账本本身无法凭空识别这种现实世界的欺骗。

因此，供应链追溯仍需要可靠的数据采集、身份管理、现场检查、传感器校验、审计和责任追究机制。链上完整性与链下真实性是两个不同的问题。

## 三、区块链建立的是哪一类信任

课程将区块链的重要目标概括为：让彼此缺少完全信任的参与方，仍能围绕共同的交易记录或状态达成一致。

这并不意味着所有参与方都必须放弃中心化服务。中心化与去中心化不是只有两个极端选项：

- 一个中心化电商平台可以接受比特币等链上资产作为支付方式；
- 一个系统可以用中心化机构处理客户服务，同时用区块链记录多个机构共同认可的结算结果；
- 一个完全开放的链上系统，也可能依赖中心化交易所、前端网站或链下数据服务。

因此，需要分别判断支付方式、账本维护、业务决策、争议解决和客户服务由谁控制。采用区块链支付，不会自动让整个商业模式变成去中心化。

## 四、不可逆转账与退款机制

区块链交易被确认后，通常不能由单个参与者像编辑数据库记录一样直接撤销。课程指出，这不等于区块链无法退款。

退款通常是新的交易：

1.  买方向卖方支付一笔资产。
2.  双方发现需要退款。
3.  卖方再发起一笔新交易，把相应资产退回买方。

账本上保留了支付与退款两笔记录。退款不是把第一笔交易从历史中抹去，而是通过后续状态变化完成资金返还。

传统支付系统有时提供拒付、争议处理或消费者保护机制。其覆盖范围取决于支付产品、合同和适用法律。使用不可逆转账方式时，用户需要考虑错误地址、欺诈和私钥泄露带来的损失，以及是否存在有效的救济途径。

## 五、加密货币支付适合哪些场景

课程认为，加密货币不必与所有已有支付方式正面竞争。若信用卡或本地转账已经能低成本、高效率地完成交易，换用另一种支付方式未必能带来实际收益。

更值得分析的场景包括：

- 跨境小额支付或专业服务付款；
- 传统银行转账流程复杂、到账时间较长或覆盖不足的场景；
- 需要把支付与互联网信息交互结合起来的应用；
- 多方之间需要共同验证支付记录的场景。

是否适用仍取决于交易费用、确认时间、汇率波动、法币兑换、合规要求、消费者保护和系统可用性。课程中的跨境咨询费案例说明的是一种需求类型，不代表所有跨境支付都更适合使用加密货币。

## 六、如何评价支付效率与能耗

课程提醒，评价支付方式时应与同一时期、同一应用场景下的替代方案比较。除了共识层能耗，还要考虑银行基础设施、数据中心、网络、合规与争议处理等成本。

同时，比较必须避免混淆指标：

- 年度总能耗与单笔交易平均能耗是不同指标；
- 单笔交易的能耗估算取决于如何分摊网络整体能耗；
- 吞吐量、最终确认时间、成本和可用性不能用单一指标替代；
- 协议演进可能改变系统的能耗与性能特征。

课程中的 PoW
能耗统计属于历史数据。引用或比较现实系统时，应重新核对数据来源、统计时间和测量方法。

## 七、智能合约的价值与边界

智能合约将业务规则写成程序，使符合条件的状态转换可以按统一规则执行。自动取款机可以作为直观类比：系统根据预设条件处理请求，但设备和程序仍可能出现故障。

智能合约的主要优势包括：

- 规则可以被公开检查；
- 多个节点按相同规则执行；
- 可将资产转移与程序条件绑定；
- 可以减少部分依赖人工操作的环节。

它的局限也很明确：

- 程序可能存在漏洞；
- 合约部署后，修复方式受到权限与升级设计限制；
- 链上执行不能自动验证所有现实世界事实；
- 一旦资金被错误锁定，未必存在简单的管理员恢复途径；
- 复杂业务中的判断、尽职调查和争议处理仍可能需要链下流程。

所以，智能合约应当经过代码审计、测试网验证、异常路径测试和权限设计审查。不可篡改性提高了规则执行的一致性，也使错误设计可能持续产生后果。

## 八、The DAO 给治理设计的启示

The DAO
事件表明，程序化决策和代币投票并不能自动替代所有商业判断。评估一个投资项目可能需要考察创始团队、财务状况、技术路线、市场和执行能力，这些信息不能只靠多数票生成。

去中心化也不是所有问题的统一解法。对于不同系统，需要比较：

- 谁有权修改规则；
- 谁承担决策失败的损失；
- 少数参与者如何保护自身权益；
- 如何发现并处理程序漏洞；
- 是否允许升级、暂停或紧急恢复；
- 应急权限是否会形成新的信任集中。

任何治理设计都有成本和权衡。投票可以表达偏好，却不保证多数人的判断一定正确；中心化管理可能提高协调效率，却可能带来单点控制与审查风险。

## 九、应用选型清单

在决定使用区块链之前，可依次回答：

1.  是否存在多个需要共同维护记录的参与方？
2.  各方是否缺少一个可被所有人接受的单一管理者？
3.  业务是否需要公开审计、历史追踪或多方验证？
4.  现实世界数据如何采集、签名、验证和纠错？
5.  若输入数据为假，系统能否发现或追责？
6.  交易是否需要退款、撤销或争议处理？
7.  智能合约出现漏洞时，资金如何保护和恢复？
8.  费用、吞吐量、确认时间和用户体验是否满足需求？
9.  区块链方案相对于普通数据库或支付系统，究竟改善了哪一项关键指标？
10. 新增的治理、运维和安全成本是否合理？

## 本讲小结

区块链的价值需要结合业务问题、参与方信任关系和系统成本判断。它可以增强多方记录的一致性与可审计性，但不能自动保证输入数据真实、商业模式合理或智能合约没有漏洞。技术选型的关键是明确它解决什么问题，以及它引入了哪些新的约束。
