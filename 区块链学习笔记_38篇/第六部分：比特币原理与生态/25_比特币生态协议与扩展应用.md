### 2.1 1 题目

1. 为什么两笔消费同一 UTXO 的交易可能都具有正确签名，而不能同时在同一有效历史中执行？
2. 为什么“累计工作量最大的有效链”比“区块最多的链”更准确？PoW 能否使超额发行合法？
3. 某交易位于高度 900010，活动链尖为 900015，有多少确认？若重组后该交易不再被收录，应怎样处理旧确认数？
4. 区块头为何固定为 80 字节？RPC 返回的 `height` 与 `confirmations` 是否都在这 80 字节中？
5. 在玩具 8 位哈希系统中，目标从 31 改为 15，单次成功概率和平均尝试次数怎样变化？
6. 某主网调整周期时间是目标时间的 $1/5$，能否直接将目标变为原来的 $1/5$？
7. Alice 消费 120000 sat，创建 90000 和 28000 两个输出，手续费是多少？旧输入是否继续保存“余额”？
8. 重复引用同一 outpoint 为什么需要单独检查？仅仅比较输出总和是否小于循环累加的输入总和为什么不够？
9. P2PKH 的 HASH160 与 P2WSH 的脚本承诺哈希是否相同？`3...` 地址是否必然是多签？
10. 一个 v1 witness 地址使用 Bech32 校验，校验本身通过，是否应当按 BIP350 接受？全大写地址和混合大小写地址有什么区别？
11. 哈希原像谜题与哈希碰撞谜题分别要求什么？为什么碰撞题必须检查两个输入不同？
12. 交易不符合节点默认标准策略，是否必然违反共识？常见脚本模板是否保证资金不会被任何人花掉？
13. 没有脚本树的 Taproot tweak 是否应该附加 32 字节零根？控制块首字节为 `c1` 是否表示另一种 Tapscript 叶版本？
14. 深度 3 的 Taproot 控制块有多少字节？四叶概率为 0.5、0.25、0.125、0.125 时，Huffman 树的平均深度是多少？
15. 所有 Taproot 输出是否都由多人控制？MuSig2 是否自动实现任意 t-of-n 门限签名？
16. BRC-20 的 mint 铭文从 Alice 转给 Bob，是否必然使已 mint 的余额转给 Bob？有效 transfer 创建后，Bob 是否已经入账？
17. Alice 总余额 300，已有有效未使用 transfer 占用 220，她还能创建金额 100 的 transfer 吗？首次转给自己会怎样？
18. Runes 数据位于 OP_RETURN，是否意味着所有符文都存在不可花费的 OP_RETURN UTXO 中？解析失败为什么不能随意忽略？
19. PSBT 是否加密？BIP371 是否就是“PSBTv1”？格式正确能否代替签名设备核对费用和收款输出？
20. RGB 的链上承诺能否恢复遗失的全部状态历史？RGB++ 是否让 Bitcoin 全节点执行 CKB 的全部业务脚本？

### 2.2 2 参考答案

1. 签名验证授权消息，UTXO 状态限制消费次数。同一密钥可以为两个冲突消息分别产生正确签名；先在有效历史中执行的支出会使旧输出不再可用，另一个不能再消费它。
2. 不同目标下单块贡献的工作量不同；链选择比较通过规则验证的累计工作，而非任意头部数量。超额发行使区块无效，不会因为哈希很小而获得豁免。
3. $900015-900010+1=6$ 次。若新活动链不包含该交易，不能继续显示旧的六次确认；应按新的链状态标记未确认或冲突等情况。
4. 六个规范字段的大小相加为 80。高度和确认数依赖区块在链中的位置与当前链尖，属于 RPC 上下文信息，不是头部序列化字段。
5. 从 $32/256=1/8$ 变成 $16/256=1/16$，平均尝试从 8 次变为 16 次。它描述期望值，不保证第八次或第十六次必定成功。
6. 不能直接如此调整。主网算法先把时间比率限制到至少 $1/4$，然后计算新目标，还需考虑上限、压缩及整数规则。
7. 手续费为 2000 sat。旧输出被整体消费，28000 的找零是新输出，其 outpoint 与原输入不同。
8. 不检查重复会把一份资金累计多次，从而错误允许超支。输入必须先形成没有重复的实际可消费引用，再核对金额、签名和状态。
9. HASH160 是 RIPEMD160$SHA256$，P2WSH 使用 SHA256$witnessScript$。`3...` 只表明常见主网 P2SH 地址编码，具体赎回条件可能多种多样。
10. 不接受；v1 应使用 Bech32m。全大写可以是同一有效地址的编码形式，大小写混合必须拒绝，其他校验与网络约束也不能省略。
11. 原像题是对固定目标哈希找到输入；碰撞题是找到不同输入得到相同哈希。没有不同条件时，两份相同消息就能轻易通过，未体现碰撞攻击。
12. 不必然，策略通常比共识更严格且可因节点而异。常见模板也可能绑定错误公钥或被设计成不符合预期授权；标准性不是安全审计结论。
13. 应使用空的树数据，而非零根。控制首字节低一位存输出点奇偶，`c1 & fe = c0`，仍是当前 `c0` 叶版本。
14. $33+32\times3=129$ 字节。该概率下可得到深度 1、2、3、3，平均 1.75；共识不强制采用这种树。
15. 都不是。Taproot 可以由单个签名者控制，MuSig2 的基本标准是 n-of-n 协作；更一般门限要求对应协议，不能通过更改一个阈值字面量得到。
16. 移动 mint 铭文不能替代余额转账。transfer 创建先占用发送者的可用余额，首次有效移动到 Bob 后才结算相应余额。
17. 可用量仅为 80，因此 100 的新请求不满足此模型要求。将那份仍有效的 transfer 首次转给自己，可释放对应占用，不能增发额外单位。
18. OP_RETURN 承载指令，余额通常分配到其他输出。某些格式错误按 Runes 规则形成 cenotaph 并销毁单位；任意忽略会与规范实现分歧。
19. PSBT 和其 Base64 形式都不提供加密。BIP371 扩展 v0、v2 的 Taproot 字段。签名设备仍应验证 UTXO、脚本、授权输出、费用及 sighash 语义。
20. 承诺通常只能验证已取得的数据，不能从哈希恢复缺失历史。RGB++ 将有关业务验证交给 CKB 及相应证据流程，BTC 全节点仍只执行 BTC 共识规则。

## 三、附录 C. 术语与教材衔接

| 术语 | 本讲中的准确含义 |
|---|---|
| outpoint | 交易标识加输出索引，用于定位被消费输出 |
| scriptPubKey | 输出中写明的花费条件字节 |
| scriptSig | Legacy/P2SH 等路径中的输入脚本材料，具体规则随类型而定 |
| witness | SegWit 输入携带的见证数据，不等于任意 JSON 证明 |
| redeemScript | P2SH 中被 HASH160 承诺、花费时揭示的脚本 |
| witnessScript | P2WSH 中被 SHA-256 承诺、在见证中提供的脚本 |
| txid / wtxid | 不含/包含 witness 的规范交易标识，两者不能任意替换 |
| chainwork | 根据各区块目标累计的工作量量度 |
| confirmations | 在当前活动链上下文中的确认数 |
| policy | 节点处理未确认交易的策略；不是全部共识规则 |
| x-only key | 按 BIP340 约定用横坐标编码并选取对应偶数纵坐标点 |
| tweak | 由指定数据导出的公钥修正量；Taproot 将其绑定内部密钥与脚本树 |
| control block | script path 提供的叶版本、奇偶信息、内部公钥和 Merkle 路径 |
| inscription ID | 定位铭文的交易及铭文索引标识，不等于输出索引 |
| runestone | Runes 对交易中协议指令负载的解释对象 |
| cenotaph | Runes 对特定畸形负载的处理语义，可能导致单位销毁 |
| PSBT | 不同构造、签名、终结角色交换交易材料的格式 |
| single-use seal | 将状态分配的一次性消费与可验证事件绑定的机制 |
| client-side validation | 相关客户端取得证据后验证业务状态，而非要求所有 BTC 节点执行该业务 |

教材衔接依据实际可访问的作者书目、公开目录/前言和出版社页面；没有声称读取付费全书，也没有虚构原书针对这些生态项目的案例。《现代密码学》存在不同作者和版本，用户未限定书目信息时，本讲不为它编造特定页码。

| 公开教材材料 | 与本讲的连接 | 复习时应追问的问题 |
|---|---|---|
| Katz、Lindell，*Introduction to Modern Cryptography* 第三版，作者页面及公开目录/前言 | 形式化安全目标、明确假设、哈希与签名的不同性质 | 验证成功具体证明了什么，攻击者还能改变哪些状态或上下文？ |
| Paar、Pelzl、Güneysu，*Understanding Cryptography* 第二版，2024 出版社页面 | 椭圆曲线、数字签名、哈希与工程实现之间的衔接 | 理论安全假设如何被编码、nonce 和验证边界破坏？ |
| BIP 与项目原始实现 | 把通用密码学原语落实到具体字节格式和状态规则 | 哪些是共识字节，哪些是钱包策略，哪些是应用索引器约定？ |

前两项公开资料入口见 [Katz/Lindell 作者页][R44]、[公开目录与前言][R45]、[Springer 书目与目录][R46]。教材提供理解密码学安全性的框架，BIP 和项目实现提供本讲所需的协议事实，两类资料不能互相替代。

## 五、状态分叉（State Fork）

两个矿工可能在相近时间挖出不同的有效区块。由于网络传播延迟，一部分节点先收到区块
A，另一部分节点先收到区块 B，于是暂时从同一父区块形成两条分支。

后续区块不断产生，节点按共识规则选择继续扩展的分支。另一分支可能失去竞争，成为未被主链采用的区块。只要节点遵循相同规则，这类分叉通常是暂时性的。

攻击者也可能故意制造分叉，尝试重写近期交易历史。例如，付款方在一条分支上支付后，又尝试在竞争分支上花费同一份资产。这类攻击的成功可能性与攻击者的算力、交易确认深度及网络条件有关。

## 六、协议分叉（Protocol Fork）

去中心化网络不能保证所有节点同时升级软件。若部分节点采用新规则，另一些节点继续采用旧规则，就可能对同一区块是否有效产生不同判断。

协议变更可能形成两类分叉：硬分叉和软分叉。

## 七、硬分叉（Hard Fork）

硬分叉通常意味着新规则允许某些旧规则不接受的区块或交易。课程以提高区块大小上限为例：

1.  新节点接受更大的区块。
2.  旧节点仍按旧上限验证，并拒绝超过上限的区块。
3.  新节点可能继续沿包含大区块的分支扩展。
4.  旧节点则沿自己认可的分支继续运行。

如果两群参与者长期坚持不同规则，两条链就可能并行存在。硬分叉是否最终造成持久分裂，取决于社区协调、升级情况及两边是否继续维护各自链。

## 八、软分叉（Soft Fork）

软分叉通常通过收紧规则实现兼容性：新规则认可的区块仍满足旧规则的基本要求，但旧规则可能允许一些新规则禁止的行为。

因此：

- 升级后的节点执行更严格的规则；
- 未升级节点可能仍把新规则下的区块视为有效；
- 未升级节点并没有获得新规则的完整验证能力。

软分叉的兼容性不代表所有节点的安全视图完全一致。激活方式、算力支持和具体规则都很重要。

## 九、硬分叉与软分叉的区别

| 维度                     | 硬分叉                         | 软分叉                       |
|--------------------------|--------------------------------|------------------------------|
| 规则关系                 | 新规则可能接受旧规则拒绝的区块 | 新规则通常收紧可接受范围     |
| 旧节点对新规则区块的判断 | 可能拒绝新规则产生的区块       | 通常仍可能接受新规则区块     |
| 兼容性                   | 可能导致持久链分裂             | 目标是保持向后兼容           |
| 风险重点                 | 社区分裂、两条链并行           | 未升级节点不能完整验证新约束 |

## 十、分叉前后的资产与交易

如果链在某个历史点分开，分叉点之前的交易历史可能被两条链共同继承。分叉之后，两条链的状态和后续交易逐渐不同。某笔旧资产在两条链上可能各有对应记录，但后续花费遵循各自链的规则。

课程还以以太坊 DAO
事件后的社区分歧作为历史案例：部分参与者支持通过协议变更处理被盗资产，另一部分参与者坚持原有规则，最终形成
ETH 与 ETC
两条不同的链。这个案例说明，技术规则的变更也涉及社区治理与对账本历史的不同判断。

不能仅凭“分叉前有一笔资产”就假定两条链上的资产可以互换；它们属于不同账本历史，需要分别检查交易、地址和协议规则。

## 十一、本讲小结

临时分叉通常由同时出块与网络延迟引起；协议分叉来自规则升级。硬分叉和软分叉的关键区别在于新旧规则的兼容关系。分叉处理依赖节点验证、共识规则和社区升级协调。
