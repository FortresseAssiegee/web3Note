## 三、内容提要

理解比特币，最有效的起点是一笔支付为什么能被别人独立验证。Alice 声称把钱给了 Bob，网络至少要回答四个问题：她引用的资金是否存在、她是否满足花费条件、同一份资金是否已被消费、面对彼此冲突的历史应接受哪一条。数字签名主要回答授权问题，UTXO 集回答当前可消费状态问题，脚本规定授权条件，PoW 和链选择处理公开网络中的历史竞争。任何一种工具单独存在都不能完整解决支付问题。[白皮书][R01]提出了这些组成部分的组合；后来的实现和软分叉进一步细化了交易格式与验证规则。

本讲按三条线索组织知识。第一条是“数据如何被承诺”：交易形成交易标识，交易集合形成 Merkle 根，区块头引用前一区块头，矿工对区块头做工作量证明。第二条是“状态如何被更新”：旧输出被消费，新输出被创建，签名与脚本约束每一个输入。第三条是“应用如何解释数据”：Ordinals、Runes、BRC-20、RGB 和 RGB++ 在不同层建立额外语义，它们不能简单视作 Bitcoin Core 内部已有的同一种代币功能。

| 学习问题 | 直接使用的机制 | 必须同时保留的边界 |
|---|---|---|
| 怎样发现区块内容变化？ | 哈希与 Merkle 承诺 | 有承诺还需要可信的根及链上下文 |
| 怎样证明可以花某个输出？ | Script、ECDSA 或 Schnorr 签名 | 私钥控制与现实身份不是同一件事 |
| 怎样拒绝同一笔钱花两次？ | UTXO 检查及区块内状态更新 | 签名有效的交易仍可能冲突或超支 |
| 怎样选取共同历史？ | 验证规则、累计工作量、网络传播 | 有限确认数提供概率性保障 |
| 怎样解释铭文或代币余额？ | 生态协议与索引器、客户端验证 | BTC 有效不自动等于应用操作有效 |

学完后应能把一句“转账成功”拆解成具体状态：签名已生成、某节点已接收、交易进入内存池、交易被某区块收录、该区块处于活动链、应用索引器已确认相应资产变更。这些状态的证据、失败原因和可逆性都不同。

## 四、Bitcoin 的基本介绍

Bitcoin 是一套公开验证的支付协议、运行该协议的节点网络及其账本系统；BTC 是协议中记账的原生单位。`1 BTC = 100,000,000 satoshi`，实现中的金额以整数 satoshi 表示。把金额保存为二进制浮点数再相减，可能因舍入使手续费或余额判断出现错误；因此后面的 Go 程序全用整数，并在加法之前检查范围。

在 Bitcoin 的 UTXO 模型中，链上没有一个名为“Alice”的全局账户字段。交易输出包含金额和锁定条件，钱包掌握满足某些锁定条件所需的密钥、脚本和证明，从而把这些输出归入“我的资金”。钱包余额是对钱包认识并可支配的输出进行汇总的结果，还可能区分已确认、未确认、冻结、待成熟或仅观察的资金。地址是常见锁定条件的便携编码，既不是存储硬币的容器，也不是自然人的身份证。[交易开发指南][R12]

网络中的角色可以重合，但职能应分开理解。全节点依据自己执行的规则验证区块和交易；矿工构造候选区块并寻找满足目标的头部哈希；钱包选择输入、生成收款条件、组织签名与追踪状态；浏览器提供可视化查询；矿池协调工作并结算参与者收益。运行钱包并不必然意味着运行全节点，掌握算力也不意味着能够让独立全节点接受违反发行或签名规则的区块。

密码学在这里主要用于完整性、承诺和授权，公开链上的交易通常没有被统一加密隐藏。对交易做 SHA-256 不会使公开交易内容保密；签名证明特定密钥对特定消息的授权，也不会证明签名者已经读懂交易、设备没有被盗或交易背景合法。Bitcoin 的公开可审计性与用户隐私之间存在真实张力，地址复用、输入合并、交易所关联信息都会改变外部观察者能推断的内容。

可以用一个支付失败例子理解分工：Alice 对一笔支出签名后又签了一笔消费相同输出的交易。两份签名都可能正确，密码学并未自相矛盾，因为签名只承诺两条不同消息。系统必须在某个有效历史中只允许该输出被消费一次。这个“唯一消费”约束来自账本状态与共识，而不是签名算法自动消除冲突。

## 五、比特币的发展过程

这里按机制变化梳理历史，不用价格变化代替技术演进，也不把 BIP 的写作日期、软件发布日、升级锁定日与共识激活高度混为一谈。

| 时间或高度 | 事件及原始依据 | 对理解本讲的意义 |
|---|---|---|
| 2008-10-31 | Satoshi 在密码学邮件列表发布论文链接；档案保留日期与原文。[邮件档案][R02] | 将电子签名、公开传播和 PoW 组织为防双花系统 |
| 2009-01-03 | 创世区块时间戳为 `1231006505`；主网创世参数及断言哈希可在 Core 源码核对。[chainparams][R03] | 区分论文提出与实际账本启动 |
| 2012 年的 P2SH 部署 | BIP16 描述按赎回脚本哈希付款的验证规则，BIP13 定义相应地址编码。[BIP16][R14]、[BIP13][R15] | 把复杂花费条件放到花费时揭示，发送方只处理承诺 |
| 2017 年，主网高度 481824 | Core 主网参数记录 SegWit 激活高度；BIP141 定义见证数据及区块权重。[参数][R03]、[BIP141][R08] | 将特定授权数据移入 witness，明确 txid 与 wtxid，缓解相关可塑性问题 |
| 2021 年，主网高度 709632 | Core 0.21.1 的部署说明指定 Taproot 最低激活高度；实际规则由 BIP340/341/342 配合定义。[部署说明][R23] | 引入 BIP340 Schnorr、P2TR 与 Tapscript |
| Ordinals/铭文应用阶段 | Ordinal Theory 和铭文协议在既有交易与见证结构之上定义追踪和内容解释规则。[Ordinal Theory][R24]、[铭文][R25] | 应用层新增解释，不需要为每种内容增加 Bitcoin 共识原语 |
| 主网高度 840000 | Runes 的官方实现说明把该高度作为启用点；同一高度也是第四次补贴减半的边界。[Runes][R28] | 两套独立规则可以共用同一个高度，不能据此认为减半机制负责发行符文 |

软分叉可以理解为在既有有效集合内增加约束：升级节点对新类型支出执行更多规则，而旧节点可能只看见一个在旧规则下可接受的结构。这个定义不等于“所有旧钱包会自动支持新地址”，也不等于“只升级矿工就足够”。用户能否正确生成地址、识别输出、计算签名消息和恢复备份，仍需钱包及工具配套。

研究历史时还应分清“协议能力存在”与“某种应用被设计出来”。Taproot 不是为某个后来出现的代币标准定制的共识升级。应用采用已有脚本与见证能力，只能说明这些能力被重新组合，不能反向推出 Bitcoin 节点验证了该应用宣称的所有经济属性。

## 六、从中心化数字货币到去中心化账本

如果由一个可信机构发行数字货币，机构可以维护一张登记表，记录每份货币当前归谁所有。支付时，机构检查货币是否已转出，再更新登记表。这种方案能够防止同一份价值被重复使用，但需要信任中心机构。

去中心化系统没有单一登记机构，因此需要一套所有节点都能独立验证的规则。比特币的关键问题包括：

1.  谁可以获得新币，以及新币如何按规则发行？
2.  一笔交易是否由资产控制者授权？
3.  交易所花费的资产是否真实存在、仍可花费？
4.  多个节点看到冲突交易或不同区块时，如何形成共同的账本历史？

## 七、交易如何表达资产转移

比特币使用基于交易的账本模型。交易通常包含输入和输出：

- **输入（Input）**：引用此前交易中某个尚未花费的输出，并提供满足其锁定条件所需的数据。
- **输出（Output）**：指定金额和后续花费该金额所需满足的条件。
- **交易签名**：证明花费方有权使用相应资产。
- **交易费**：输入总额与输出总额之间的差额。

每个输入都会指向某笔既有交易的特定输出。节点可以沿着这些引用检查资产来源，判断所花费的输出是否存在、是否已被使用。

## 八、双花为什么会产生冲突

假设 Alice 控制一个价值 5 BTC 的未花费输出。她构造两笔交易：

- 交易 $T_1$：把这 5 BTC 转给 Bob。
- 交易 $T_2$：把同一笔 5 BTC 转给 Carol。

两笔交易可能各自具有有效签名，但它们花费的是同一个输出，因此不能同时在同一条有效账本历史中成立。

节点收到交易后，会检查其输入是否仍可花费。若某笔交易已被接受进当前账本状态，另一笔冲突交易就无法再次消费同一输出。若网络中不同节点先后收到不同交易，它们的临时判断可能不同；后续区块与共识规则负责推动账本收敛。

## 九、节点如何验证一个区块

节点不会仅凭“某个矿工发布了区块”就接受它。验证通常包括：

1.  区块结构及字段是否符合协议格式。
2.  区块中的每笔交易是否有效。
3.  交易输入是否存在、是否重复花费，签名是否满足锁定条件。
4.  新发行的区块奖励是否符合协议规定。
5.  区块头的哈希是否满足目标阈值，难度参数是否正确。
6.  区块是否接在有效的历史分支上。

通过验证的区块才有资格参与共识中的链选择。课程常用“最长合法链”来解释；在工作量证明系统中，更精确的理解是比较协议认可的累计工作量。

## 十、工作量证明与账本排序

矿工将候选区块头与不同随机数进行哈希计算，直到找到满足目标阈值的结果。该结果证明矿工为候选区块投入了一定计算工作，但节点仍需独立检查区块内容。

当两个有效区块同时产生时，网络可能暂时出现分叉。节点会依据共识规则选择继续扩展的分支，之后另一分支可能不再被选中。确认数增加会提高攻击者改写历史的成本，但不会让交易在任意条件下获得绝对不可逆性。

## 十一、货币发行与激励

课程讨论的比特币协议包含两类主要激励：

- **区块补贴（Block
  Subsidy）**：协议允许矿工在区块中创建符合规则的奖励输出。
- **交易费（Transaction
  Fee）**：用户交易输入总额高于输出总额时，差额可由出块者获得。

区块补贴按协议规则随区块高度变化；随着补贴下降，交易费在矿工收益中的作用会发生变化。具体奖励数值会随历史时期变化，理解规则比记住某一时点的数值更重要。

## 十二、本讲小结

比特币的双花防护来自多层机制：签名验证授权，交易输入引用资产来源，节点维护当前可花费状态，工作量证明共识为冲突历史提供排序规则。单独验证签名无法解决双花问题。
