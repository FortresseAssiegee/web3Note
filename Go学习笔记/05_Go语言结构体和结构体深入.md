## 一、结构体的初始化

数组和切片把同一种类型的多个值放在一起；结构体则把一件事的不同属性组织成一个值。例如，一项待办任务需要标题、优先级和完成状态，它们分别适合用 `string`、`int`、`bool` 表示。结构体让这些属性具有明确名称，也让函数能够一次接收或返回一份完整记录。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)。

本章先解决三个实际问题：怎样创建一份记录，怎样读写其中的字段，以及复制这份记录时哪些数据会继续共享。内存对齐放在 1.4，方法和嵌入放在后续章节。

<a id="section-1-1"></a>

### 1.1 结构体的初始化

结构体的每一项称为**字段**：字段有名称，也有类型。`struct { ... }` 描述字段结构，`type 名称 struct { ... }` 为这种结构定义一个新类型。类型定义本身不是创建变量；`var p Point` 或 `p := Point{...}` 才会得到具体的结构体值。[官方依据：Type definitions](https://go.dev/ref/spec#Type_definitions)、[Struct types](https://go.dev/ref/spec#Struct_types)。

下面根据官方规范中坐标结构体的讲解思路，使用整数坐标编写一个完整程序。

```go
// 运行示例：I-01
package main

import "fmt"

type Point struct {
	X int
	Y int
}

func main() {
	p := Point{X: 3, Y: 4}
	q := Point{X: 10, Y: 20}
	fmt.Printf("type: %T\n", p)
	fmt.Println("p:", p.X, p.Y)
	fmt.Println("q:", q.X, q.Y)
}
```

输出：

```text
type: main.Point
p: 3 4
q: 10 20
```

`Point` 是类型，`p` 和 `q` 是两个变量，每个变量都有自己的两个整数字段。`p.X` 中的点号用于选择字段。`main.Point` 表示这个命名类型定义在当前 `main` 包里，不是标准库提供的坐标类型。

结构体的字段也可以是数组、切片、map、指针、另一个结构体或函数等类型。选择字段类型时，应先确认它代表的数据是什么：固定数量可考虑数组，数量变化可考虑切片，可能缺失的关联对象可考虑指针。类型不是装饰，它决定零值、复制行为和允许执行的操作。

字段名称还解决了“这个位置代表什么”的问题。若用 `[]int{3, 4}` 保存坐标，需要额外约定索引 0 是横坐标、索引 1 是纵坐标；使用 `Point{X: 3, Y: 4}`，这个对应关系进入了类型定义。它也使误写 `p.Z` 能被编译器发现。结构体并不是把所有数据都变成同一类型，也不是可以任意添加键的字典：哪些字段存在，在类型定义中已经确定。

声明中的 `X, Y int` 可以作为分别写 `X int`、`Y int` 的简写，两者仍是两个独立字段。结构体内部的非空白字段名不能重复，但不同结构体可以拥有同名字段：`Point.X` 与另一个类型的 `X` 不会仅因同名就成为同一个变量。字段属于具体结构体值，而不是所有该类型变量共享的一份全局状态。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)。

<a id="section-1-1-1"></a>

#### 1.1.1 使用字段名初始化

写成 `Person{Name: "Lin", Age: 20}` 的形式，称为带字段名的结构体字面量，常见英文是 **keyed literal**。这里的键是字段名，不是运行时查找的字符串。编译器会核对字段是否存在、值能否赋给该字段，未写出的字段则得到其类型的零值。[官方依据：Composite literals](https://go.dev/ref/spec#Composite_literals)。

```go
// 运行示例：I-02
package main

import "fmt"

type Person struct {
	Name   string
	Age    int
	Active bool
}

func main() {
	first := Person{Age: 20, Name: "Lin"}
	second := Person{Name: "Ming", Age: 21, Active: true}
	third := Person{"Rui", 22, true}

	fmt.Println(first.Name, first.Age, first.Active)
	fmt.Println(second.Name, second.Age, second.Active)
	fmt.Println(third.Name, third.Age, third.Active)
}
```

输出：

```text
Lin 20 false
Ming 21 true
Rui 22 true
```

`first` 中 `Age` 写在 `Name` 前面不影响含义，字段名已经说明每个值属于哪里；没有给 `Active` 赋值，所以它为 `false`。`third` 没有字段名，称为 **unkeyed literal**，值必须按结构体的字段声明顺序逐一对应。

两种写法的约束可这样比较：

| 写法 | 字段顺序 | 能否省略部分字段 | 修改类型定义后的影响 |
| --- | --- | --- | --- |
| `Person{Name: "Lin"}` | 可以调整初始化项顺序 | 可以，省略项取零值 | 新增字段通常不会迫使这条字面量补齐所有项 |
| `Person{"Lin", 20, false}` | 必须与声明顺序一致 | 非空列表需要逐字段提供 | 新增字段通常使原写法报错；交换同类型字段还可能悄悄改变含义 |
| `Person{}` | 没有初始化项 | 所有字段均取零值 | 明确表示该结构体类型的零值 |

不能在同一个结构体字面量中混用“部分带字段名、部分只给值”的形式，也不能重复给同一字段赋值。字段名写错通常能在编译期发现；两个字段都为 `int` 时，依赖位置的初始化却未必能发现“年龄和数量放反了”。因此，字段较多或用于跨包接口的结构体，带字段名通常更便于检查。[官方依据：Composite literals](https://go.dev/ref/spec#Composite_literals)、[Effective Go：Constructors and composite literals](https://go.dev/doc/effective_go#composite_literals)。

还有两个边界需要记住。第一，字段值必须满足赋值规则，不会因放进结构体而自动把一个变量从 `float64` 转成 `int`。第二，其他包中未导出的字段不能由调用方直接指定；可访问范围由包和标识符规则决定，而不是“知道这个字段在第几个位置就能绕过”。本节例子使用当前类型直接声明的字段，嵌入字段与提升字段的版本差异在第三章解释。

#### 1.1.2 使用默认值初始化

目录里的“默认值”首先应理解为 Go 的**零值**，即没有显式给值时由语言规定的初始值。它不等于业务默认设置：整数零值是 0，但一个服务器的业务默认端口可能是 8080；字符串零值是空字符串，但业务默认主机名可能是 `localhost`。

```go
// 运行示例：I-03
package main

import "fmt"

type State struct {
	Name   string
	Count  int
	Ready  bool
	Flags  [2]bool
	Values []int
	Labels map[string]string
	Next   *State
}

func main() {
	var state State
	fmt.Printf("name=%q count=%d ready=%t\n", state.Name, state.Count, state.Ready)
	fmt.Println("flags:", state.Flags)
	fmt.Println("slice:", state.Values == nil, len(state.Values))
	fmt.Println("map:", state.Labels == nil, len(state.Labels))
	fmt.Println("pointer:", state.Next == nil)
}
```

输出：

```text
name="" count=0 ready=false
flags: [false false]
slice: true 0
map: true 0
pointer: true
```

零值初始化会递归应用到结构体和数组的元素：`Flags` 的两个布尔值都为 `false`。切片、map 和指针字段的零值则是 nil，这并不意味着它们引用的对象也被自动创建。读取 nil map 得到元素零值，向 nil map 写入会 panic；nil 切片可以作为 `append` 的起点；nil 指针不能直接解引用。相同的 nil 字样，需要结合字段类型判断允许做什么。[官方依据：The zero value](https://go.dev/ref/spec#The_zero_value)、[Map types](https://go.dev/ref/spec#Map_types)、[Appending and copying slices](https://go.dev/ref/spec#Appending_and_copying_slices)。

业务默认设置可以通过普通函数表达。Go 不会因为一个函数叫 `DefaultConfig` 或 `NewConfig` 就自动调用它；调用方必须明确使用该函数返回的值。

```go
// 运行示例：I-04
package main

import "fmt"

type Config struct {
	Host           string
	Port           int
	TimeoutSeconds int
}

func DefaultConfig() Config {
	return Config{
		Host:           "localhost",
		Port:           8080,
		TimeoutSeconds: 5,
	}
}

func main() {
	zero := Config{}
	defaults := DefaultConfig()
	custom := DefaultConfig()
	custom.Port = 9090

	fmt.Printf("zero: %q %d %d\n", zero.Host, zero.Port, zero.TimeoutSeconds)
	fmt.Println("defaults:", defaults.Host, defaults.Port, defaults.TimeoutSeconds)
	fmt.Println("custom:", custom.Host, custom.Port, custom.TimeoutSeconds)
}
```

输出：

```text
zero: "" 0 0
defaults: localhost 8080 5
custom: localhost 9090 5
```

这个函数只创建并返回一个 `Config` 值。`custom.Port = 9090` 修改 `custom` 自己的整数字段，不会改变另一份 `defaults`。如果某些字段必须满足范围约束，初始化函数还可以返回错误；1.3 会用一个完整任务案例说明这种做法。[官方参考：Effective Go 的构造函数示例](https://go.dev/doc/effective_go#composite_literals)。

不要直接在结构体字段声明后写业务默认值，例如 `Port int = 8080`；这不是结构体字段的合法声明语法。写成 ``Port int `default:"8080"` `` 虽然可以作为字段标签存在，但语言自身不会读取它并替字段赋值。只有某个明确使用该标签的库或代码，才会执行对应操作。

因此，检查初始化是否完成时，最好把两个问题分开：**字段有没有确定的 Go 值，业务上能不能使用这个值。** `Config{}` 的每个字段都有确定值，并非“内容随机、尚未初始化的内存”；但端口 0 是否允许，取决于业务规则。同样，`Person{Age: 0}` 在语言上完全合法，是否代表未填写或刚出生，需要程序另作约定。初始化函数的作用是建立这种业务约定，不是替 Go 清理原本不确定的字段内容。

#### 1.1.3 使用指针初始化结构体

指针保存某个变量的位置。`*Person` 是“指向 Person 的指针”类型，`&person` 取得已有变量的地址，`*p` 则访问指针指向的变量。初始化时最常见的两种写法是 `new(Person)` 与 `&Person{...}`。

| 写法 | 得到的类型 | 指向的结构体初始状态 |
| --- | --- | --- |
| `var p *Person` | `*Person` | 指针为 nil，尚未指向某个 Person 变量 |
| `p := new(Person)` | `*Person` | 指向一个字段均为零值的 Person |
| `p := &Person{}` | `*Person` | 同样指向一个字段均为零值的 Person |
| `p := &Person{Name: "Lin"}` | `*Person` | 指向按字面量初始化的 Person |
| `p := &existing` | `*Person` | 指向已有变量，初始内容就是该变量当前的内容 |

其中 `new(Person)` 与 `&Person{}` 在这里表达相同的初始化效果。它们都不会使结果指针为 nil。`make` 用于切片、map、channel，不能写 `make(Person)` 创建普通结构体。[官方依据：Allocation](https://go.dev/ref/spec#Allocation)、[Making slices, maps and channels](https://go.dev/ref/spec#Making_slices_maps_and_channels)、[Effective Go](https://go.dev/doc/effective_go#allocation_new)。

```go
// 运行示例：I-05
package main

import "fmt"

type Person struct {
	Name string
	Age  int
}

func main() {
	var missing *Person
	p := new(Person)
	q := &Person{Name: "Lin", Age: 20}

	fmt.Println("nil states:", missing == nil, p == nil, q == nil)
	fmt.Printf("new value: %q %d\n", p.Name, p.Age)
	fmt.Println("literal value:", q.Name, q.Age)

	alias := q
	alias.Age = 21
	fmt.Println("after pointer copy:", q.Age, alias.Age)
}
```

输出：

```text
nil states: true false false
new value: "" 0
literal value: Lin 20
after pointer copy: 21 21
```

`alias := q` 复制的是指针值，两个指针访问同一个 `Person`。通过其中一个修改年龄，另一个也能看见。这里与结构体值复制的区别在于：复制指针并没有把它指向的整份记录复制出来。

直接读取 `missing.Name` 会尝试通过 nil 指针访问字段，导致运行时 panic。指针可能缺失时，应先判断 nil，或者让函数契约保证它非 nil。`&Person{...}` 也不意味着对象必定在堆上；对象的存储位置由具体编译与使用情况决定，不应由初始化语法直接下结论。[官方依据：Selectors](https://go.dev/ref/spec#Selectors)、[Address operators](https://go.dev/ref/spec#Address_operators)、[Go FAQ：堆与栈](https://go.dev/doc/faq#stack_or_heap)。

**为结构体创建存储，不会自动为所有引用类字段创建目标对象。** 下面继续观察 `new` 得到的零值，按字段类型分别准备可写内容。

```go
// 运行示例：I-06
package main

import "fmt"

type Session struct {
	Events []string
	Labels map[string]string
}

func main() {
	s := new(Session)
	fmt.Println("initial:", s.Events == nil, s.Labels == nil)
	s.Events = append(s.Events, "created")
	s.Labels = make(map[string]string)
	s.Labels["status"] = "ready"
	fmt.Println("events:", s.Events)
	fmt.Println("label:", s.Labels["status"])
}
```

输出：

```text
initial: true true
events: [created]
label: ready
```

切片字段从 nil 开始就能追加，并把返回值存回字段；map 字段需要先取得一个可写 map，再放入键值。也可以直接通过结构体字面量设置这些字段，例如 `Session{Labels: make(map[string]string)}`。要检查的是每一个字段当前的状态，而不是笼统地问“整个结构体是不是已经初始化过”。

**初始化函数应该返回结构体值，还是结构体指针？** 如果结果是一份可独立处理的小记录，返回 `T` 往往表达清楚；如果后续调用需要共享同一对象并更新状态，返回 `*T` 可以明确这种共享关系。指针也可以用 nil 表达“没有对象”，但调用方就要处理 nil。不能简单记成“结构体一律用指针更快”：复制开销、实际分配、对象生命周期和使用方式都影响结果，应先确定所需语义，再测量性能。

返回局部结构体的地址是合法的，例如函数中创建 `p := Person{Name: "Lin"}` 后 `return &p`，或者直接返回 `&Person{Name: "Lin"}`。Go 会使仍被引用的变量存储在函数返回后保持有效，不会因为局部变量的名字离开作用域就变成悬空指针。这是语言使用方式与 C 中直接套用栈地址经验时容易混淆的地方；具体栈堆位置仍由实现决定。[官方说明：Effective Go 的构造函数示例](https://go.dev/doc/effective_go#composite_literals)。

<a id="section-1-2"></a>

### 1.2 结构体的访问

<a id="heading-012"></a>

#### 字段选择、指针简写与可寻址性

访问结构体字段写成 `value.Field`。如果 `p` 是指向结构体的指针，`p.Field` 可以作为 `(*p).Field` 的简写；它简化了书写，并没有取消 nil 指针检查，也没有创建一份新结构体。[官方依据：Selectors](https://go.dev/ref/spec#Selectors)。

```go
// 运行示例：I-07
package main

import "fmt"

type Point struct {
	X int
	Y int
}

func main() {
	p := Point{X: 3, Y: 4}
	ptr := &p
	ptr.X = 8
	fmt.Println("through value:", p)
	fmt.Println("through pointer:", *ptr)

	x := &p.X
	*x = 9
	fmt.Println("after field pointer:", p)
}
```

输出：

```text
through value: {8 4}
through pointer: {8 4}
after field pointer: {9 4}
```

`&p.X` 取得的是变量 `p` 中字段 `X` 的地址；对 `*x` 赋值，会修改这个字段。这里 `p` 是可以明确定位存储的变量，所以字段也可以取地址。这种性质称为**可寻址性**：表达式能否代表一个可以取得地址的变量。[官方依据：Address operators](https://go.dev/ref/spec#Address_operators)。

不是所有“能读到一个值”的表达式都可寻址。例如函数返回的结构体临时值可以读取字段，但通常不能直接对其字段赋值；可以先把返回值保存到变量中。切片元素属于规范允许的可寻址表达式，因此 `items[i].Field = value` 可以直接修改结构体切片中的字段。map 中的结构体元素则有不同规则，稍后会专门说明。

<a id="heading-013"></a>

#### 值复制与字段内部的共享

结构体赋值按值复制。对于整数、布尔值、数组等字段，复制后可以分别修改；对于切片、map、指针等字段，复制的是这些字段的值，它们仍可能引用同一份更深层数据。不能把“结构体是值类型”理解成自动进行任意深度的独立拷贝。[官方依据：Representation of values](https://go.dev/ref/spec#Representation_of_values)、[Assignment statements](https://go.dev/ref/spec#Assignment_statements)。

```go
// 运行示例：I-08
package main

import (
	"fmt"
	"slices"
)

type Record struct {
	Name   string
	Flags  [2]bool
	Scores []int
}

func main() {
	a := Record{Name: "A", Flags: [2]bool{true, false}, Scores: []int{10, 20}}
	b := a
	b.Name = "B"
	b.Flags[0] = false
	b.Scores[0] = 99
	fmt.Println("a:", a.Name, a.Flags, a.Scores)
	fmt.Println("b:", b.Name, b.Flags, b.Scores)

	c := a
	c.Scores = slices.Clone(a.Scores)
	c.Scores[1] = 88
	fmt.Println("after clone:", a.Scores, c.Scores)
}
```

输出：

```text
a: A [true false] [99 20]
b: B [false false] [99 20]
after clone: [99 20] [99 88]
```

三个修改走的是不同路径。改 `b.Name` 替换 `b` 的字符串字段；改 `b.Flags[0]` 写入已复制的数组字段；改 `b.Scores[0]` 则通过复制后的切片值找到共享整数数组，所以 `a.Scores[0]` 也变成 99。`slices.Clone` 为当前整数元素建立副本，使后面的 88 不再写进 `a` 的数组。[官方依据：slices.Clone](https://pkg.go.dev/slices#Clone)。

如果结构体字段是 `[][]int` 或 `[]*Node`，克隆这一层切片仍不能自动复制所有行或所有节点。函数传参同样遵守值复制规则，因而一个接收结构体值的函数仍可能通过它的切片字段改变外部元素。后面比较值接收器和指针接收器时，会再次用到这个边界。

<a id="heading-014"></a>

#### map 中的结构体怎样更新

`map[string]Person` 取出的是结构体值，map 索引表达式不属于可寻址表达式，不能直接写 `people["lin"].Age = 21`，也不能取得 `&people["lin"]`。但 map 索引可以作为整体赋值的目标，所以一种清楚的做法是取出、修改、再存回。[官方依据：Address operators](https://go.dev/ref/spec#Address_operators)、[Assignment statements](https://go.dev/ref/spec#Assignment_statements)。

```go
// 运行示例：I-09
package main

import "fmt"

type Person struct {
	Age int
}

func main() {
	people := map[string]Person{"lin": {Age: 20}}
	person, ok := people["lin"]
	if !ok {
		return
	}
	person.Age = 21
	fmt.Println("before writeback:", people["lin"].Age)
	people["lin"] = person
	fmt.Println("after writeback:", people["lin"].Age)

	pointers := map[string]*Person{"lin": &Person{Age: 30}}
	if p, ok := pointers["lin"]; ok && p != nil {
		p.Age = 31
	}
	fmt.Println("pointer entry:", pointers["lin"].Age)
}
```

输出：

```text
before writeback: 20
after writeback: 21
pointer entry: 31
```

后一种 map 存储的是指针，虽然 map 元素本身仍不可寻址，但取出的指针可以访问它指向的结构体，因此能够更新年龄。这不是让 map 索引突然变得可寻址，而是修改的目标变成了指针所指的对象。使用指针方案还需要明确 nil 检查、对象共享以及并发读写的协调，不能仅为了少写一次赋值就忽略这些变化。

前一段的 `ok` 也有实际作用：如果键不存在，直接取值仍会得到 `Person` 的零值，年龄是 0；只看年龄不能判断“有一个年龄为 0 的人”还是“根本没有这个键”。第二段则同时判断 `ok` 和 `p != nil`，因为键存在与指针非 nil 是两个独立条件。结构体与容器一起使用时，字段规则之外，还必须保留容器查找的结果信息。[官方依据：Index expressions](https://go.dev/ref/spec#Index_expressions)。

<a id="heading-015"></a>

#### 导出字段、包边界与标签

以 Unicode 大写字母开头的字段名属于导出标识符，例如 `Name`；小写的 `name` 不导出。同一个包中的代码可以访问未导出字段，控制边界是包，而不是某一个文件。`package main` 也有这个规则，只是单文件练习不容易体现跨包限制。[官方依据：Exported identifiers](https://go.dev/ref/spec#Exported_identifiers)。

字段后面的字符串称为**标签**，例如 `` `json:"name"` ``。标签保存元数据，语言不会自动依据标签执行业务操作；`encoding/json` 等库会读取自己约定的标签。下面基于官方 `json.Marshal` 结构体示例，缩小字段数量并增加未导出字段，用来观察这一区别。

```go
// 运行示例：I-10
package main

import (
	"encoding/json"
	"fmt"
)

type Profile struct {
	Name   string `json:"name"`
	Age    int    `json:"age,omitempty"`
	secret string `json:"secret"`
}

func main() {
	p := Profile{Name: "Lin", secret: "internal"}
	data, err := json.Marshal(p)
	if err != nil {
		fmt.Println(err)
		return
	}
	fmt.Println(string(data))
	fmt.Println("same-package access:", p.secret)
}
```

输出：

```text
{"name":"Lin"}
same-package access: internal
```

`Name` 导出并被标签改成 JSON 键 `name`。`Age` 为 0，符合这里 `omitempty` 约定的空值条件，所以省略。`secret` 没有导出，即使写上 `json:"secret"`，默认结构体编码也不会把它变成导出字段；同包的 `main` 代码却可以直接访问它。[官方依据：encoding/json.Marshal](https://pkg.go.dev/encoding/json#Marshal)。

本例使用 `encoding/json` 的默认编码，没有自定义编码方法。标签不改变 Go 代码中的访问名称，写了 `json:"name"` 后，代码仍然使用 `p.Name`。如果数字 0 在业务中本身有含义，随意加入 `omitempty` 还可能抹去“明确传了 0”和“未提供”的区别，应按接口约定选择。

<a id="section-1-3"></a>

### 1.3 结构体简单的完整案例

<a id="heading-017"></a>

#### 任务：创建一条有效待办事项，完成后输出 JSON

现在把初始化、值访问和指针修改放进同一个小任务。要求是：标题去掉两端空白后不能为空；优先级只能是 1、2、3；新任务尚未完成；完成操作需要更新原任务；最后输出可读记录和 JSON。

用 `Task` 表示任务数据，`NewTask` 负责检查输入并返回结构体值，`completeTask` 接收指针并修改原值，`main` 负责调用和处理错误。这里先用普通函数表达流程；第二章再解释怎样把这类操作写成方法。

```go
// 运行示例：I-11
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"strings"
)

type Task struct {
	Title    string `json:"title"`
	Priority int    `json:"priority"`
	Done     bool   `json:"done"`
}

func NewTask(title string, priority int) (Task, error) {
	title = strings.TrimSpace(title)
	if title == "" {
		return Task{}, errors.New("title must not be empty")
	}
	if priority < 1 || priority > 3 {
		return Task{}, errors.New("priority must be in [1,3]")
	}
	return Task{Title: title, Priority: priority}, nil
}

func completeTask(task *Task) error {
	if task == nil {
		return errors.New("task is nil")
	}
	task.Done = true
	return nil
}

func main() {
	task, err := NewTask("  Read Go docs  ", 2)
	if err != nil {
		fmt.Println(err)
		return
	}
	fmt.Println("before:", task.Title, task.Priority, task.Done)
	if err := completeTask(&task); err != nil {
		fmt.Println(err)
		return
	}
	fmt.Println("after:", task.Title, task.Priority, task.Done)

	data, err := json.Marshal(task)
	if err != nil {
		fmt.Println(err)
		return
	}
	fmt.Println("json:", string(data))

	_, err = NewTask("   ", 2)
	fmt.Println("empty title:", err)
	_, err = NewTask("Read", 4)
	fmt.Println("invalid priority:", err)
	fmt.Println("nil update:", completeTask(nil))
}
```

输出：

```text
before: Read Go docs 2 false
after: Read Go docs 2 true
json: {"title":"Read Go docs","priority":2,"done":true}
empty title: title must not be empty
invalid priority: priority must be in [1,3]
nil update: task is nil
```

按状态变化阅读这个程序：

1. `NewTask` 先得到修剪后的标题，再检查两个条件；失败时返回零值 `Task{}` 和错误，调用方不能把错误结果当作已成功创建的任务。
2. 成功时只显式设置 `Title`、`Priority`，`Done` 自动为布尔零值 `false`，因此不需要再写一条多余的赋零语句。
3. `completeTask(&task)` 接收原变量地址。参数中的指针值虽然也是传值复制，但它仍指向同一个任务，所以写入 `Done` 后，`main` 观察到 `true`。
4. `json.Marshal` 读取导出字段并根据标签命名键；结果是字节切片，`string(data)` 使其以 JSON 文本打印。
5. 最后三次调用覆盖空标题、越界优先级和 nil 更新目标，返回清楚的错误，不让程序因为直接访问 nil 字段而中断。

这里的 `NewTask` 是约定清晰的普通函数，不是语言强制的构造器。由于字段仍然导出，其他代码仍可直接写 `Task{Priority: 99}`；如果一个包必须维护更严格的不变量，应结合未导出字段和受控操作设计接口，而不能仅凭函数名字保证所有对象都经过校验。

这个案例的业务规则由本笔记设定，所用机制依据官方规范；输入修剪、错误值和 JSON 输出分别使用标准库 [strings.TrimSpace](https://pkg.go.dev/strings#TrimSpace)、[errors.New](https://pkg.go.dev/errors#New)、[encoding/json.Marshal](https://pkg.go.dev/encoding/json#Marshal)。它没有引入第三方工具包，也不依赖方法、接口或反射知识才能运行。

<a id="section-1-4"></a>

### 1.4 结构体的内存对齐问题

一个结构体把若干字段放在同一个值中，但字段之间不一定毫无间隔。理解这里的规则，能够解释为什么“一个 `byte` 加一个 `int64` 再加一个 `byte`，字段内容合计 10 字节，结构体却可能占 24 字节”。本节只查询大小、对齐和偏移，不通过 `unsafe.Pointer` 读写任意内存。

<a id="section-1-4-1"></a>

#### 1.4.1 什么是内存对齐

**对齐要求**指一个值放置的位置必须满足的地址倍数。例如要求 8 字节对齐，意味着起始地址应是 8 的整数倍。**偏移量**是某个字段相对结构体起点的字节距离。例如字段偏移为 8，意思是从结构体起点向后 8 个字节开始存放该字段，不是说它的真实地址就是数字 8。[官方依据：Package unsafe](https://go.dev/ref/spec#Package_unsafe)。

为了让字段落在允许的位置，编译器可以在字段之间或结构体末尾留出不属于任何业务字段的字节，称为**填充字节**，英文 padding。字段间填充用于安排后续字段；尾部填充用于让整个结构体的大小符合相应布局要求。

查询时主要使用三个标准库函数：

| 操作 | 回答的问题 | 结果是否包含结构体填充 |
| --- | --- | --- |
| `unsafe.Sizeof(s)` | `s` 这个值本身占多少字节 | 包含 |
| `unsafe.Alignof(s)` | 该值需要怎样的起始对齐 | 返回对齐要求，不是内容大小 |
| `unsafe.Offsetof(s.Field)` | 字段相对结构体起点有多少字节 | 偏移会反映字段前面的间隔 |

对字段调用 `unsafe.Alignof(s.Field)` 时，得到该字段在结构体中的对齐要求；它对应反射 API 的 `FieldAlign`。不要把“一个类型的大小”和“这个类型作为字段需要多大对齐”当成同一个数字。[官方依据：unsafe.Sizeof](https://pkg.go.dev/unsafe#Sizeof)、[unsafe.Alignof](https://pkg.go.dev/unsafe#Alignof)、[unsafe.Offsetof](https://pkg.go.dev/unsafe#Offsetof)。

**示例 L-01：先观察真实布局，再手工解释。** 下面打印运行环境，避免把目标架构中的具体数值误当作语言规定的唯一布局。

```go
// 运行示例：L-01
// 具体布局数字按 Go 1.27.3 linux/amd64 记录。
package main

import (
	"fmt"
	"runtime"
	"unsafe"
)

type Record struct {
	A byte
	B int64
	C byte
}

func main() {
	var r Record
	fmt.Println(runtime.Version(), runtime.GOOS+"/"+runtime.GOARCH)
	fmt.Println("struct size and alignment:", unsafe.Sizeof(r), unsafe.Alignof(r))
	fmt.Println("A size align offset:", unsafe.Sizeof(r.A), unsafe.Alignof(r.A), unsafe.Offsetof(r.A))
	fmt.Println("B size align offset:", unsafe.Sizeof(r.B), unsafe.Alignof(r.B), unsafe.Offsetof(r.B))
	fmt.Println("C size align offset:", unsafe.Sizeof(r.C), unsafe.Alignof(r.C), unsafe.Offsetof(r.C))
}
```

本次环境中的输出：

```text
go1.27.3 linux/amd64
struct size and alignment: 24 8
A size align offset: 1 1 0
B size align offset: 8 8 8
C size align offset: 1 1 16
```

对应的布局可以列成表。这里的编号是相对结构体起点的字节偏移，不是实际地址：

| 字节偏移范围 | 内容 | 原因 |
| --- | --- | --- |
| `0` | 字段 A | 一个 byte |
| `1–7` | 字段间填充，共 7 字节 | 把 B 的起点移到 8 的倍数 |
| `8–15` | 字段 B | int64 的 8 字节内容 |
| `16` | 字段 C | 一个 byte |
| `17–23` | 尾部填充，共 7 字节 | 把整个结构体大小补到对齐要求的倍数 |

因此，24 来自 `1 + 7 + 8 + 1 + 7`。不能把这 14 个填充字节理解成额外声明了 14 个字段；它们是当前编译器为该类型安排布局的结果。[实现依据：cmd/compile/internal/types/size.go](https://go.dev/src/cmd/compile/internal/types/size.go)。

<a id="section-1-4-2"></a>

#### 1.4.2 为什么需要内存对齐

对齐首先满足目标架构和实现所要求的存储位置约束。官方规范明确指出，计算机架构可能要求变量地址按其类型的对齐要求放置。即使某种处理器允许某些不对齐访问，也不能据此绕过编译器对 Go 类型建立的布局约定；是否更快、差多少，还取决于具体架构、访问方式和工作负载。[官方依据：Package unsafe](https://go.dev/ref/spec#Package_unsafe)。

尾部填充还可以从数组中理解。假设 `Record` 的起点已经满足 8 字节对齐，如果它只占 17 字节，连续放置的第二个 `Record` 就从偏移 17 开始，不再满足同样的对齐要求。把每个元素的完整大小安排为 24 字节，就能让后面的元素继续从合适的位置开始。

```go
// 运行示例：L-02
package main

import (
	"fmt"
	"unsafe"
)

type Record struct {
	A byte
	B int64
	C byte
}

func main() {
	var rows [3]Record
	elementSize := unsafe.Sizeof(rows[0])
	fmt.Println("array equals three elements:", unsafe.Sizeof(rows) == 3*elementSize)
	fmt.Println("element size fits alignment:", elementSize%unsafe.Alignof(rows[0]) == 0)
	fmt.Println("array alignment matches element:", unsafe.Alignof(rows) == unsafe.Alignof(rows[0]))
}
```

输出：

```text
array equals three elements: true
element size fits alignment: true
array alignment matches element: true
```

这个程序打印布局关系，不打印真实地址，也不依赖某次分配恰好位于哪里。数组对齐与元素对齐一致，是规范给出的保证；本例结构体具体占多少字节，则由对应实现和目标架构共同决定。[官方依据：Size and alignment guarantees](https://go.dev/ref/spec#Size_and_alignment_guarantees)。

还应把对齐与并发同步分开。一个字段位置对齐，不意味着多个 goroutine 可以随意同时读写它，更不意味着某组字段的更新自动成为一个整体。共享可变状态仍需要互斥锁、通道或适当的原子操作。`sync/atomic` 对部分平台和类型还有自己的约束，应以接口文档为准。[官方依据：The Go Memory Model](https://go.dev/ref/mem)、[sync/atomic](https://pkg.go.dev/sync/atomic)。

<a id="section-1-4-3"></a>

#### 1.4.3 结构体的内存对齐规则

先区分两层规则。语言规范提供最低大小和对齐保证，例如 `uint32` 大小为 4 字节、结构体的对齐要求等于各字段对齐要求的最大值，且至少为 1；具体编译器再据此确定字段偏移与填充。本节的逐字节计算对应 Go 1.27.3 的标准编译器，不扩展成所有 Go 实现的二进制 ABI 承诺。

对于没有特殊零大小尾字段的普通结构体，可以用下面的步骤理解本次编译器的布局算法：

1. 以字段的声明顺序处理字段。开始偏移为 0。
2. 放置下一个字段前，把当前偏移向上调整到该字段对齐要求的倍数。
3. 记录这个字段的起始偏移，再加上字段本身的大小。
4. 处理完所有字段后，把总大小向上补到结构体对齐要求的倍数。

若字段的对齐要求为 `a`，放置前的偏移为 `x`，向上取整可以写成：

\[
\operatorname{roundUp}(x,a)=\left\lceil\frac{x}{a}\right\rceil a
\]

例如 `x=1, a=8` 时得到 8；`x=16, a=1` 时仍为 16。这只是帮助理解偏移如何计算的数学表达，不要求业务代码自己实现内存布局。[源码依据：calcStructOffset 与 CalcStructSize](https://go.dev/src/cmd/compile/internal/types/size.go)。

**对齐要求看字段的对齐，不是看最大字段占多少字节。** 例如内层结构体可能大小为 8、对齐为 4；把它放到外层，并不会仅因为“大小是 8”就要求外层也按 8 对齐。

```go
// 运行示例：L-03
// 具体布局数字按 Go 1.27.3 linux/amd64 记录。
package main

import (
	"fmt"
	"unsafe"
)

type Inner struct {
	Count uint32
	Flag  byte
}

type Outer struct {
	Tag  byte
	Data Inner
	End  byte
}

func main() {
	var inner Inner
	var outer Outer
	fmt.Println("inner size and alignment:", unsafe.Sizeof(inner), unsafe.Alignof(inner))
	fmt.Println("outer offsets:", unsafe.Offsetof(outer.Tag), unsafe.Offsetof(outer.Data), unsafe.Offsetof(outer.End))
	fmt.Println("outer size and alignment:", unsafe.Sizeof(outer), unsafe.Alignof(outer))
}
```

本次环境中的输出：

```text
inner size and alignment: 8 4
outer offsets: 0 4 12
outer size and alignment: 16 4
```

先计算 `Inner`：`Count` 在偏移 0 占 4 字节，`Flag` 在偏移 4 占 1 字节，再补 3 字节，得到大小 8、对齐 4。再计算 `Outer`：`Tag` 在 0；`Data` 从满足 4 字节对齐的偏移 4 开始，占完整的 8 字节；`End` 位于 12，之后补到 16。内层的尾部填充仍属于内层值的一部分，外层不会重新把它压缩掉。

以下边界尤其重要：

- **架构差异。** 一个数值类型的大小可能由规范固定，但它在某个目标架构上的对齐值仍需核对；不要只凭“64 位整数”推断在所有平台都要求 8 字节对齐。
- **间接引用。** 指针字段本身占指针值的空间，切片字段本身占切片值的空间；它们引用的其他存储不会被 `unsafe.Sizeof(外层结构体)` 递归统计进去。
- **零大小字段。** 标准编译器对非零大小结构体末尾的零大小字段有额外处理，第四章单独演示；不能仅按“空字段大小为 0，直接跳过”计算。
- **特殊库类型。** 标准库某些原子类型有特定对齐设计，不能把普通结构体的便捷口诀替代其文档要求。

来源：[unsafe.Sizeof](https://pkg.go.dev/unsafe#Sizeof)、[Size and alignment guarantees](https://go.dev/ref/spec#Size_and_alignment_guarantees)、[sync/atomic](https://pkg.go.dev/sync/atomic)。

<a id="section-1-4-4"></a>

#### 1.4.4 优化内存对齐

当程序保存大量同类型记录时，调整字段顺序可能减少填充。常见的检查起点是把对齐要求较大的字段放在一起，再安排较小字段。但这只是帮助寻找布局改进的经验，是否值得改变，应结合实测、可读性、接口兼容性和访问模式判断。

```go
// 运行示例：L-04
// 具体布局数字按 Go 1.27.3 linux/amd64 记录。
package main

import (
	"fmt"
	"unsafe"
)

type Before struct {
	A byte
	B int64
	C byte
}

type After struct {
	B int64
	A byte
	C byte
}

func main() {
	var before Before
	var after After
	fmt.Println("before size:", unsafe.Sizeof(before))
	fmt.Println("after size:", unsafe.Sizeof(after))
	fmt.Println("after offsets:", unsafe.Offsetof(after.B), unsafe.Offsetof(after.A), unsafe.Offsetof(after.C))
	fmt.Println("bytes per value saved:", unsafe.Sizeof(before)-unsafe.Sizeof(after))
}
```

本次环境中的输出：

```text
before size: 24
after size: 16
after offsets: 0 8 9
bytes per value saved: 8
```

`After` 中三个字段共占 10 字节，最后补到 16；它省去了 `Before` 中 A 与 B 之间的 7 字节空隙，但仍然有 6 字节尾部填充。若仅按连续存储的一百万个这种值计算，差额为 `1,000,000 × 8 = 8,000,000` 字节；这只是元素区间的计算，不是完整进程堆占用的测量结果。

调整字段顺序可能影响无字段名的复合字面量、反射遍历顺序、显式二进制编码顺序，以及与外部代码约定的布局。对外部包公开的类型尤其需要慎重；新类型优先使用带字段名的字面量，可以减少调用方对字段位置的依赖。仅仅看到 `Sizeof` 变小，也不能自动得出“整体性能一定更好”，例如不同 goroutine 对相邻字段的访问还涉及其他因素。

**内存布局也不等于数据传输格式。** 如果要把结构体发送到网络或写入文件，应明确编码规则，而不是把内存中的填充和平台字节序一并当成协议。下面结合标准库 `encoding/binary` 的固定大小编码，比较内存大小与编码字节数。

```go
// 运行示例：L-05
package main

import (
	"bytes"
	"encoding/binary"
	"fmt"
	"unsafe"
)

type Packet struct {
	Kind  uint8
	Count uint32
}

func main() {
	p := Packet{Kind: 1, Count: 258}
	var buf bytes.Buffer
	if err := binary.Write(&buf, binary.BigEndian, p); err != nil {
		panic(err)
	}
	fmt.Println("encoded size:", binary.Size(p))
	fmt.Println("encoded bytes:", buf.Bytes())
	fmt.Println("memory includes padding:", unsafe.Sizeof(p) > uintptr(binary.Size(p)))
}
```

本次环境中的输出：

```text
encoded size: 5
encoded bytes: [1 0 0 1 2]
memory includes padding: true
```

第一个字节保存 `Kind=1`；随后四个字节按大端序保存 258，即十六进制 `00 00 01 02`。本次内存布局中 `Count` 前存在对齐间隔，而 `binary.Write` 按字段内容连续编码，并不会自动把这些隐含填充写入文件。这个例子中的大小对比与目标布局相关，编码规则则由 `encoding/binary` 的接口约定和显式字节序决定。[官方依据：encoding/binary.Write](https://pkg.go.dev/encoding/binary#Write)、[encoding/binary.Size](https://pkg.go.dev/encoding/binary#Size)。

<a id="section-1-4-5"></a>

#### 1.4.5 总结

分析一个结构体布局时，先列出字段的声明顺序，再查每个字段的**大小与对齐**，逐个计算偏移，最后检查尾部填充。遇到嵌套值，使用内层完整大小和对齐要求；遇到引用字段，不把被引用对象误算进当前值；遇到末尾空字段，再检查第四章讨论的实现处理。

对入门阶段来说，最可靠的习惯是“先写清楚数据含义，再用 `Sizeof`、`Alignof`、`Offsetof` 核对确实重要的布局”。不要把某一平台的 24 字节、8 字节对齐，或一次字段重排带来的节省量，提升为所有 Go 程序共同的常量。

## 二、结构体方法

结构体把相关数据放在一起，方法则把“围绕这种数据执行的操作”与类型联系起来。例如，`Point` 保存坐标，求长度或缩放坐标可以写成它的方法；订单保存商品和数量，计算总价也可以成为相应方法。方法不会自动替开发者验证业务条件，但能够把操作入口组织得更清楚。

本章目录使用“接收器”一词，Go 文档中的 `receiver` 也常译为**接收者**：它是方法声明中位于方法名前的那个特殊参数。本章保留目录标题的“接收器”，正文统一称接收者。它不是消息队列中的接收端，也不是一种特殊的全局变量。[官方依据：Method declarations](https://go.dev/ref/spec#Method_declarations)。

<a id="section-2-1"></a>

### 2.1 定义结构体方法

普通方法的声明形式如下。这是语法示意，不是独立程序：

```go
func (receiver Type) MethodName(parameters) ReturnType {
    // 使用 receiver 及其他参数完成操作。
}
```

其中 `receiver` 是方法体内使用的变量名，`Type` 是接收者类型，`MethodName` 是方法名。调用时写成 `value.MethodName(arguments)`。Go 不需要 `class` 关键字，也不用把方法体写在 `struct { ... }` 的字段声明里。

从执行机制看，方法仍是带有参数的函数，接收者也按值传递。区别在于它与接收者的基础类型建立了关联，能通过选择器调用，并参与后面介绍的方法集合和接口实现判断。下面从官方规范的 `Point` 长度计算示例改编：使用 `3、4` 得到容易核对的长度 5，同时给出一个普通函数进行对照。[官方依据：Method declarations](https://go.dev/ref/spec#Method_declarations)。

```go
// 运行示例：M-01
package main

import (
	"fmt"
	"math"
)

type Point struct {
	X, Y float64
}

func (p Point) Length() float64 {
	return math.Sqrt(p.X*p.X + p.Y*p.Y)
}

func pointLength(p Point) float64 {
	return math.Sqrt(p.X*p.X + p.Y*p.Y)
}

func main() {
	p := Point{X: 3, Y: 4}
	fmt.Println("method:", p.Length())
	fmt.Println("function:", pointLength(p))
}
```

输出：

```text
method: 5
function: 5
```

两种写法都把坐标参与 `sqrt(3²+4²)` 的计算。把它写成方法的作用是让操作归属于 `Point` 的 API，而不是让计算公式或传值规则发生变化。也不是所有函数都必须改成方法：一个操作若与多个类型同等相关，或者只是独立的数据转换，普通函数可能更清楚。

定义方法时，还需要遵守以下规则：

- 对这里使用的普通非泛型类型，接收者通常写成本包定义的类型 `T` 或 `*T`；接收者的基础类型不能是指针类型或接口类型。方法也不限于结构体，自己定义的整数、切片等类型同样可以有方法。
- 接收者的基础类型必须与方法在同一个包中定义，不能在自己的包里直接给 `time.Time`、`http.Client` 等外部类型增加方法。需要扩展行为时，可以写辅助函数，或者定义自己的包装类型。
- 接收者参数只能有一个，且不能是可变参数。`p`、`c` 等名字只是局部变量名；同一类型的方法宜使用一致、简洁的接收者命名。
- 同一基础类型不能声明重名方法，不能用不同参数列表完成重载；结构体的非空白字段名与方法名也不能相同。[官方依据：Method declarations](https://go.dev/ref/spec#Method_declarations)。

类型定义和类型别名也要区分。`type New Original` 定义一个新的类型，不会自动继承 `Original` 的方法；`type Alias = Original` 则只是为同一类型增加一个名字，不会得到一套独立的方法。需要把一个外部类型的行为组合进自己的对象时，通常使用字段包装或嵌入，而不是仅换一个名字就期待它成为可任意扩展的“子类”。第三章会继续解释这两种组织方式。[官方依据：Type definitions](https://go.dev/ref/spec#Type_definitions)、[Alias declarations](https://go.dev/ref/spec#Alias_declarations)。

**版本提示：** 本章完整程序统一采用 `go 1.27.0` 模块语言设置，并包含普通方法与 Go 1.27 泛型方法的版本说明。当前 Go 1.27 已允许方法声明自己的类型参数，因此“方法永远不能声明自己的类型参数”不再是通用结论；但接口方法仍不能声明类型参数，泛型方法也不能用来实现接口方法。本章的方法集合示例均使用普通方法。[官方依据：Go 1.27 Release Notes](https://go.dev/doc/go1.27)。

<a id="section-2-1-1"></a>

#### 2.1.1 结构体作为函数接收器

写成 `(c Counter)` 时，接收者是一个结构体值。调用方法会按值传递这个结构体；方法中对普通字段重新赋值，修改的是接收者副本。如果希望构造一份变换后的新值，可以把副本返回，由调用方决定是否接收。

```go
// 运行示例：M-02
package main

import "fmt"

type Counter struct {
	N int
}

func (c Counter) Next() Counter {
	c.N++
	return c
}

func main() {
	original := Counter{N: 1}
	next := original.Next()
	fmt.Println("original:", original.N)
	fmt.Println("next:", next.N)
	original = original.Next()
	fmt.Println("after receiving result:", original.N)
}
```

输出：

```text
original: 1
next: 2
after receiving result: 2
```

第一次调用创建接收者副本，把副本中的 `N` 从 1 改为 2，再把结果赋给 `next`；`original` 没有被重新赋值，所以仍是 1。第二次调用后，调用方主动把结果赋回 `original`，它才变成 2。这个模式适合把对象作为一个值进行变换，但 Go 并不会因为开发者选了值接收者就自动建立“完全不可变”的保证。[官方依据：Calls](https://go.dev/ref/spec#Calls)、[Assignments](https://go.dev/ref/spec#Assignment_statements)。

即使调用方改用 `(&original).Next()`，`Next` 的接收者声明仍是 `Counter`，执行时仍然按值接收结构体。不能只看调用表达式出现了 `&`，就认为方法内部获得了可以替换原字段的指针接收者。决定方法体中接收者类型的是方法声明；调用表达式只是在满足对应调用规则。[官方依据：Method values](https://go.dev/ref/spec#Method_values)、[Calls](https://go.dev/ref/spec#Calls)。

**值接收者中的引用关系仍然存在。** 如果结构体字段是切片、map 或指针，复制的是这些字段的值；它们指向的数据不一定被复制。下面同时观察普通字段、切片描述信息和更深层数据的变化。

```go
// 运行示例：M-03
package main

import "fmt"

type State struct {
	Name   string
	Tags   []string
	Counts map[string]int
	Level  *int
}

func (s State) Revise() {
	s.Name = "local"
	s.Tags[0] = "changed"
	s.Tags = s.Tags[:1]
	s.Counts["hits"]++
	(*s.Level)++
	fmt.Println("inside length:", len(s.Tags))
}

func main() {
	level := 3
	s := State{
		Name:   "go",
		Tags:   []string{"basic", "api"},
		Counts: map[string]int{"hits": 1},
		Level:  &level,
	}
	s.Revise()
	fmt.Println("name:", s.Name)
	fmt.Println("tags and length:", s.Tags, len(s.Tags))
	fmt.Println("hits and level:", s.Counts["hits"], level)
}
```

输出：

```text
inside length: 1
name: go
tags and length: [changed api] 2
hits and level: 2 4
```

这里有四种不同的写入：`Name` 的重新赋值只影响副本；`Tags` 的重新切片只改变副本保存的长度；`Tags[0]` 写入双方共享的底层数组；map 更新和指针解引用分别修改共享的映射内容与整数变量。不能把它们都归为“改结构体字段，所以应该不影响原值”。应顺着每个表达式判断它究竟写到了哪一层。[官方依据：Representation of values](https://go.dev/ref/spec#Representation_of_values)、[Slice types](https://go.dev/ref/spec#Slice_types)、[Map types](https://go.dev/ref/spec#Map_types)。

如果一个方法承诺“不影响调用方的数据”，值接收者只是可能使用的方式之一，还需检查其字段中的共享引用，以及方法内部是否把引用交给其他函数。对需要独立修改的切片、map 或指针目标，应明确复制相应数据，而不是仅凭接收者签名判断。

<a id="section-2-1-2"></a>

#### 2.1.2 结构体指针作为函数接收器

写成 `(p *Point)` 时，调用方法复制的是指针值。方法体通过这份指针找到同一个结构体，因此对 `p.X` 的赋值会修改被指向的坐标。这里仍然是传值：指针本身也只是一个值，而它恰好让双方能访问同一个对象。

下例的 `Scale` 依据规范中的坐标缩放方法改编，并增加一个专门展示“重新给局部接收者赋值”的方法。

```go
// 运行示例：M-04
package main

import "fmt"

type Point struct {
	X, Y float64
}

func (p *Point) Scale(factor float64) {
	p.X *= factor
	p.Y *= factor
}

func (p *Point) RebindLocal() {
	p = &Point{}
	p.X = 100
}

func main() {
	p := Point{X: 3, Y: 4}
	p.Scale(2)
	fmt.Println("after Scale:", p)
	p.RebindLocal()
	fmt.Println("after RebindLocal:", p)
}
```

输出：

```text
after Scale: {6 8}
after RebindLocal: {6 8}
```

`Scale` 沿着指针写入原结构体，所以坐标变为 `(6, 8)`。`RebindLocal` 则先让方法内的接收者变量指向另一个结构体，之后写入新对象；它没有替调用方的变量更换对象。真实 API 如果要返回一个新的对象，通常应直接返回 `*Point`，让调用方接收，而不是指望给局部指针重新赋值能够传播出去。[官方依据：Method declarations](https://go.dev/ref/spec#Method_declarations)、[Calls](https://go.dev/ref/spec#Calls)。

对有效的 `*Point`，如果方法体写的是 `*p = Point{}`，含义又不同：它会把一个零值结构体赋给指针所指向的位置，因而修改原对象。读这三种写法时，可以依次念成“改对象的字段”“让局部指针换目标”“替换指针指向位置中的整个值”。星号和赋值目标的位置改变了写入对象，不能只凭它们都出现在指针方法里就判断结果相同。

`p.Scale(2)` 看起来是“值调用了指针方法”，能够通过是因为局部变量 `p` **可寻址**，即语言允许取得它的地址。在适用条件下，这种调用可理解为 `(&p).Scale(2)`。这是调用表达式的便利规则，不会把所有指针方法加入值类型 `Point` 的方法集合；下一节会验证这个差别。[官方依据：Calls](https://go.dev/ref/spec#Calls)。

**nil 指针能否调用方法，取决于方法如何使用它。** 指针接收者可以收到 nil；如果方法在解引用前明确处理 nil，就能定义一个合理行为。下面把 nil 配置约定为采用默认值，这个约定是示例 API 的设计，不是所有指针方法的默认功能。

```go
// 运行示例：M-05
package main

import "fmt"

type Options struct {
	TimeoutSeconds int
}

func (o *Options) Timeout() int {
	if o == nil || o.TimeoutSeconds == 0 {
		return 30
	}
	return o.TimeoutSeconds
}

func main() {
	var missing *Options
	empty := &Options{}
	custom := &Options{TimeoutSeconds: 8}
	fmt.Println("nil options:", missing.Timeout())
	fmt.Println("zero options:", empty.Timeout())
	fmt.Println("custom options:", custom.Timeout())
}
```

输出：

```text
nil options: 30
zero options: 30
custom options: 8
```

`o == nil || ...` 利用短路求值：左边为 true 时不会继续读取 `o.TimeoutSeconds`。若直接解引用 nil 的字段，仍然会 panic。对一个 nil `*T` 调用值接收者方法，则需要先得到它指向的 `T` 值，这个间接取值本身就会失败，不能期待在值接收者的方法体里再判断“自身是否 nil”。[官方依据：Selectors](https://go.dev/ref/spec#Selectors)、[Logical operators](https://go.dev/ref/spec#Logical_operators)。

选择指针接收者也不自动提供并发保护。两个 goroutine 若同时修改同一对象，仍需同步；更不能为了写“只读方法”而随意复制已经使用的锁。`sync.Mutex` 文档明确要求首次使用后不得复制，包含这类字段的结构体也应避免按值复制，通常采用指针接收者和指针传递。[官方依据：sync.Mutex](https://pkg.go.dev/sync#Mutex)、[The Go Memory Model](https://go.dev/ref/mem)。

### 2.2 结构体的方法集合

**方法集合**是与一个类型关联的方法列表，用来判断方法选择、方法表达式和接口实现。对于本节不含嵌入字段的普通结构体 `T`，规则可以概括为：

| 声明方式 | 在 `T` 的方法集合中 | 在 `*T` 的方法集合中 |
| --- | --- | --- |
| `func (t T) Read()` | 是 | 是 |
| `func (t *T) Update()` | 否 | 是 |

因此，`*T` 的方法集合同时包含值接收者和指针接收者方法，`T` 的方法集合只包含值接收者方法。包含嵌入字段时还会有方法提升规则，见第三章；不要把这里的简单表格当成全部嵌入情形的替代说明。[官方依据：Method sets](https://go.dev/ref/spec#Method_sets)。

**能否自动取址，还要看表达式。** 普通变量通常可寻址；map 中的结构体值和返回结构体值的函数调用结果不可寻址。即使这些表达式的静态类型同样都是 `Counter`，也不能都直接调用 `*Counter` 的方法。

| 表达式 | 对这里的 `*Counter.Add` 能否直接调用 | 原因 |
| --- | --- | --- |
| 局部变量 `c.Add(1)` | 可以 | `c` 可寻址，可以隐式取 `&c` |
| 切片元素 `items[0].Add(1)` | 索引有效时可以 | 切片元素可寻址 |
| 结构体值 map 元素 `values["x"].Add(1)` | 不可以 | map 元素不可寻址 |
| 返回值 `makeCounter().Add(1)`，函数返回 `Counter` | 不可以 | 返回的结构体值不可寻址 |
| 指针 map 元素 `pointers["x"].Add(1)` | 类型上可以 | 取出的元素本来就是 `*Counter`；还要保证指针有效 |

例如下面完整程序展示三种可行方式：把 map 值取出修改后写回、在 map 中保存指针，以及把函数返回值先保存为变量。

```go
// 运行示例：M-06
package main

import "fmt"

type Counter struct {
	N int
}

func (c *Counter) Add(n int) {
	c.N += n
}

func makeCounter() Counter {
	return Counter{N: 5}
}

func main() {
	values := map[string]Counter{"x": {N: 1}}
	temporary := values["x"]
	temporary.Add(1)
	values["x"] = temporary
	fmt.Println("value map:", values["x"].N)

	pointers := map[string]*Counter{"x": &Counter{N: 3}}
	pointers["x"].Add(2)
	fmt.Println("pointer map:", pointers["x"].N)

	returned := makeCounter()
	returned.Add(2)
	fmt.Println("saved return value:", returned.N)

	items := []Counter{{N: 1}}
	items[0].Add(3)
	fmt.Println("slice element:", items[0].N)
}
```

输出：

```text
value map: 2
pointer map: 5
saved return value: 7
slice element: 4
```

第一种方式如果漏掉 `values["x"] = temporary`，map 里仍保存旧结构体值。第二种方式保存的是对象指针，修改会被其他共享该对象的引用观察到；键不存在时读出的指针为 nil，不能直接套用本例的有效指针调用。选择哪一种应由数据共享与更新需求决定，而不是只为了少写一行代码。[官方依据：Address operators](https://go.dev/ref/spec#Address_operators)、[Calls](https://go.dev/ref/spec#Calls)。

**方法可以作为值保存，但绑定时间需要看清。** `f := c.Value` 是方法值：在形成 `f` 时就计算并保存接收者。若对应方法采用值接收者，保存的是当时的值副本；若采用指针接收者，则保存当时的指针。之后调用 `f()`，使用保存下来的接收者，而不是重新读取最初那条接收者表达式。[官方依据：Method values](https://go.dev/ref/spec#Method_values)。

```go
// 运行示例：M-07
package main

import "fmt"

type Counter struct {
	N int
}

func (c Counter) Value() int {
	return c.N
}

func (c *Counter) Add(n int) {
	c.N += n
}

func main() {
	c := Counter{N: 1}
	read := c.Value
	add := c.Add
	c.N = 10
	fmt.Println("saved value receiver:", read())
	add(5)
	fmt.Println("saved pointer receiver:", c.N)

	p := &c
	bound := p.Add
	p = &Counter{N: 100}
	bound(2)
	fmt.Println("old target and new target:", c.N, p.N)
}
```

输出：

```text
saved value receiver: 1
saved pointer receiver: 15
old target and new target: 17 100
```

`read` 形成时保存 `Counter{N: 1}`，所以后续把原变量改为 10 不影响它。`add` 形成时保存 `&c`，所以调用时写入当前 `c`，得到 15。`bound` 保存的同样是旧对象地址；后来只是变量 `p` 指向了新对象，已经保存的方法值不会重新绑定，因此旧对象变成 17，新对象仍为 100。

值接收者的方法值也只有按值复制的含义。接收者里若包含切片、map 或指针，保存的副本仍可能共享数据，不能把“形成时保存接收者”扩大为递归复制所有关联对象。

与之相对，`Counter.Value` 是**方法表达式**：它没有先绑定一个具体对象，而是形成一个函数，调用时显式把接收者放到第一个参数。下面根据规范中的方法表达式示例改编。

```go
// 运行示例：M-08
package main

import "fmt"

type Counter struct {
	N int
}

func (c Counter) Value() int {
	return c.N
}

func (c *Counter) Add(n int) {
	c.N += n
}

func main() {
	c := Counter{N: 3}
	read := Counter.Value
	update := (*Counter).Add
	readPointer := (*Counter).Value

	fmt.Println("read:", read(c))
	update(&c, 4)
	fmt.Println("after update:", read(c))
	fmt.Println("read through pointer:", readPointer(&c))
}
```

输出：

```text
read: 3
after update: 7
read through pointer: 7
```

`read` 的类型为 `func(Counter) int`；`update` 的类型为 `func(*Counter, int)`。`(*Counter).Value` 也合法，因为值接收者方法属于 `*Counter` 的方法集合，调用时会间接取得一个 `Counter` 值。相反，`Counter.Add` 不合法：方法表达式按指定类型的方法集合判断，不会借助某个可寻址变量自动补出地址。[官方依据：Method expressions](https://go.dev/ref/spec#Method_expressions)。

方法值适合把“某个对象上的一次操作”交给回调位置，例如保存 `counter.Add`，之后只需给增量；方法表达式适合把“同一种操作”交给通用代码，之后由调用方分别传入多个对象。选择时不仅要看参数数量，还要注意保存的方法值会让它绑定的接收者继续可用；尤其指针接收者可能使对象在回调存活期间仍被引用。它不会因为原变量改名、重新赋值或离开局部作用域，就自动变成无接收者的函数。

#### 2.2.1 接口与结构体方法

**接口描述调用方需要的行为。** 例如“能转换成一个说明字符串”，可以用包含 `String() string` 的接口表示；调用方只需要调用这个方法，不必知道对象还保存了多少字段。对于本节的普通方法接口，一个类型只要具有接口要求的完整方法，就隐式实现该接口，无须写 `implements` 声明。方法名和签名必须匹配，单纯“功能看起来相似”不够。[官方依据：Interface types](https://go.dev/ref/spec#Interface_types)。

标准库 `fmt.Stringer` 正是这样一个小接口。下面改编其官方 `Animal` 示例：改为 `Person`，增加显式接口变量和编译期检查，观察方法如何被通用输出函数调用。

```go
// 运行示例：M-09
package main

import "fmt"

type Person struct {
	Name string
	Age  int
}

func (p Person) String() string {
	return fmt.Sprintf("%s (%d)", p.Name, p.Age)
}

var _ fmt.Stringer = Person{}
var _ fmt.Stringer = (*Person)(nil)

func describe(value fmt.Stringer) string {
	return value.String()
}

func main() {
	p := Person{Name: "Ada", Age: 36}
	var named fmt.Stringer = p
	fmt.Println(p)
	fmt.Println(describe(named))
}
```

输出：

```text
Ada (36)
Ada (36)
```

`fmt` 看到值实现了 `String() string`，会按相应格式规则使用该方法。`describe` 只依赖接口，不需要接收具体的 `Person`。两条 `var _ ...` 声明利用赋值的类型检查，在编译期确认 `Person` 与 `*Person` 都实现 `fmt.Stringer`；它们没有执行 `String`，把 `(*Person)(nil)` 放在断言里也不代表程序打算对 nil 执行值接收者方法。[官方依据：fmt.Stringer](https://pkg.go.dev/fmt#Stringer)、[Method sets](https://go.dev/ref/spec#Method_sets)。

从 `describe` 的代码位置看，它只能直接使用接口公开的方法，不能因为这一次传入的是 `Person` 就写 `value.Age`。如果调用方确实需要年龄相关行为，可以把所需行为加入一个合适的小接口；如果必须依赖具体类型，则应明确采用类型断言或具体参数类型。接口的价值在于让依赖关系与实际需要对齐，不是把类型信息藏起来之后再到处取回。

方法签名也不会进行任意的“相近匹配”。例如，一个方法返回 `Person`，并不因此实现要求返回 `fmt.Stringer` 的同名接口方法，即便 `Person` 本身实现了 `fmt.Stringer`；返回值类型仍然不同。参数类型、结果类型以及是否为可变参数都需要符合相应函数类型规则。字段恰好叫 `String` 也不是方法 `String()`。[官方依据：Interface types](https://go.dev/ref/spec#Interface_types)、[Type identity](https://go.dev/ref/spec#Type_identity)。

一个常见错误是在 `String` 内部再次写 `fmt.Sprintf("%v", p)`，期望由 `fmt` 打印原字段。它可能再次调用同一个 `String` 方法，形成无限递归。本例直接格式化 `Name` 和 `Age` 这些字段，因此调用链会结束。方法实现不仅要满足签名，还要满足被调用时的行为约定。[官方说明：Effective Go 的 Printing](https://go.dev/doc/effective_go#printing)。

**接口实现判断不会替开发者自动取地址。** 下面的 `Counter` 可以在可寻址变量上写 `c.Add(3)`，但要求 `Add(int)` 的接口仍只能由 `*Counter` 实现。

```go
// 运行示例：M-10
package main

import "fmt"

type Counter struct {
	N int
}

func (c Counter) Value() int {
	return c.N
}

func (c *Counter) Add(n int) {
	c.N += n
}

type Valuer interface {
	Value() int
}

type Adder interface {
	Add(int)
}

var _ Valuer = Counter{}
var _ Valuer = (*Counter)(nil)
var _ Adder = (*Counter)(nil)

func main() {
	c := Counter{}
	c.Add(3)
	_, valueImplements := any(c).(Adder)
	_, pointerImplements := any(&c).(Adder)
	fmt.Println("direct call:", c.Value())
	fmt.Println("value and pointer implement Adder:", valueImplements, pointerImplements)

	var updater Adder = &c
	updater.Add(2)
	fmt.Println("after interface call:", c.N)
}
```

输出：

```text
direct call: 3
value and pointer implement Adder: false true
after interface call: 5
```

`any` 是空接口类型的别名；这里先把值放进接口，再用带 `ok` 的类型断言检查它是否实现 `Adder`，失败只得到 false，不会 panic。第一行的直接调用利用可寻址规则，第二行则比较具体类型的方法集合，两条规则并不矛盾。若把 `var updater Adder = &c` 改成 `var updater Adder = c`，会发生编译错误。[官方依据：Method sets](https://go.dev/ref/spec#Method_sets)、[Calls](https://go.dev/ref/spec#Calls)、[Type assertions](https://go.dev/ref/spec#Type_assertions)。

**把结构体值放进接口，也会复制该值。** 可以把普通接口值理解为“动态类型与动态值”的组合：动态类型说明里面实际放了什么具体类型，动态值则是相应的值。这个模型用于理解行为，不要求应用代码操作接口的内部表示。

```go
// 运行示例：M-11
package main

import "fmt"

type Label struct {
	Text string
}

func (l Label) Name() string {
	return l.Text
}

type Namer interface {
	Name() string
}

func main() {
	label := Label{Text: "old"}
	var value Namer = label
	var pointer Namer = &label
	label.Text = "new"
	fmt.Println("value in interface:", value.Name())
	fmt.Println("pointer in interface:", pointer.Name())
}
```

输出：

```text
value in interface: old
pointer in interface: new
```

`value` 中保存的动态类型是 `Label`，它保存了当时的结构体值；`pointer` 中保存的动态类型是 `*Label`，它指向原结构体。后者调用值接收者方法时，会从当前对象取得接收者值，因此读到 `new`。如果结构体含共享引用字段，前者的复制同样不自动成为深拷贝。[官方依据：Variables](https://go.dev/ref/spec#Variables)、[Representation of values](https://go.dev/ref/spec#Representation_of_values)。

**接口里的 nil 指针，不等于 nil 接口。** 只有接口没有动态类型和动态值时，它才等于 nil。下面将 nil `*LookupError` 放进 `error` 接口，接口仍记住了动态类型 `*LookupError`，因此接口判断为非 nil。

```go
// 运行示例：M-12
package main

import "fmt"

type LookupError struct {
	Key string
}

func (e *LookupError) Error() string {
	if e == nil {
		return "<nil LookupError>"
	}
	return "missing key: " + e.Key
}

func lookupError(found bool) error {
	if found {
		return nil
	}
	return &LookupError{Key: "config"}
}

func main() {
	var pointer *LookupError
	var err error = pointer
	fmt.Println("pointer is nil:", pointer == nil)
	fmt.Println("interface is nil:", err == nil)
	fmt.Println("method result:", err.Error())
	fmt.Println("successful lookup:", lookupError(true) == nil)
	fmt.Println("failed lookup:", lookupError(false))
}
```

输出：

```text
pointer is nil: true
interface is nil: false
method result: <nil LookupError>
successful lookup: true
failed lookup: missing key: config
```

本例的 `Error` 特意接受 nil，所以直接调用不会崩溃；这不改变 `err != nil` 的判断。错误返回函数在成功路径上应直接返回 nil 接口，而不是先声明一个 nil 的具体错误指针再把它作为 `error` 返回。不要把“打印看起来像 nil”和“接口确实等于 nil”当作同一件事。[官方依据：Go FAQ 关于 nil error](https://go.dev/doc/faq#nil_error)。

**将方法接到标准库接口：一个可以接收文本的结构体。** `io.Writer` 只要求 `Write([]byte) (int, error)`。调用方把字节交给它，实现者报告写入多少字节以及是否发生错误。下面借鉴 Effective Go 的 `ByteSlice.Write` 思路，改成持有字节切片的结构体 `ByteLog`，让它能作为 `fmt.Fprintf` 的目标。[官方依据：Effective Go 的 Pointers vs. Values](https://go.dev/doc/effective_go#pointers_vs_values)、[io.Writer](https://pkg.go.dev/io#Writer)。

```go
// 运行示例：M-13
package main

import (
	"fmt"
	"io"
)

type ByteLog struct {
	data []byte
}

func (b *ByteLog) Write(p []byte) (int, error) {
	b.data = append(b.data, p...)
	return len(p), nil
}

func (b *ByteLog) String() string {
	return string(b.data)
}

var _ io.Writer = (*ByteLog)(nil)

func main() {
	var log ByteLog
	n, err := fmt.Fprintf(&log, "job=%d", 7)
	if err != nil {
		panic(err)
	}
	input := []byte("!")
	m, err := log.Write(input)
	if err != nil {
		panic(err)
	}
	input[0] = '?'
	fmt.Println("written:", n, m)
	fmt.Println("stored:", log.String())
	fmt.Println("caller input:", string(input))
}
```

输出：

```text
written: 5 1
stored: job=7!
caller input: ?
```

调用过程是：`fmt.Fprintf` 先按格式组织 `job=7`，再通过 `io.Writer` 的 `Write` 方法把字节交给 `ByteLog`；`Write` 把字节追加到内部切片并接收新切片值，最后返回写入数量。接收者需要是指针，才能让更新后的 `data` 长度和存储引用留在原对象里。仅用值接收者追加，仍会遇到“只改了局部切片描述信息”的问题。

`Write` 使用追加复制字节，而不是长期保存调用方的 `p`，因此后续把 `input[0]` 改成 `?` 不影响日志里已经保存的 `!`。这也符合 `io.Writer` 对不得保留输入切片的要求。这个讲解类型在正常内存分配条件下接受全部字节，返回完整长度和 nil；真正实现文件、网络等 Writer 时，必须按文档处理短写与错误，不能机械地始终返回 `len(p), nil`。[官方依据：io.Writer](https://pkg.go.dev/io#Writer)。

本例没有文件、网络和并发访问。它的目的在于展示一个结构体怎样通过方法进入标准库调用链；若只是需要内存字节缓冲，实际项目可以直接使用已经提供丰富方法的 [bytes.Buffer](https://pkg.go.dev/bytes#Buffer)。

### 2.3 总结

接收者选择应先表达语义，再考虑复制成本。需要更新原对象、需要维持对象身份，或者对象包含不应复制的锁等状态时，通常使用指针接收者；小型、适合按值处理且不需要修改原字段的数据，可以使用值接收者。对同一类型尽量保持一致且可解释的接收者设计，但不要把规则简化成“超过多少字节一律使用指针”——性能还取决于调用方式、生命周期和编译器优化。[官方讨论：Effective Go 的 Pointers vs. Values](https://go.dev/doc/effective_go#pointers_vs_values)、[sync](https://pkg.go.dev/sync)。

例如，一个二维坐标通常可以复制后进行计算；一个带有锁、缓冲区和网络连接状态的服务对象则更适合以指针维持同一个实例。即使某个服务方法只读取字段，也不能因此忽略它复制了整个结构体里的锁。反过来，小型值对象采用指针接收者，也不代表它自动获得更好的性能或线程安全。API 需要先说明“操作同一个对象”还是“从旧值产生新值”，实现和调用方式再围绕这个含义保持一致。

| 读到的代码或现象 | 应当检查的地方 |
| --- | --- |
| 值接收者修改后，原值似乎也变了 | 是否写入了切片、map、指针引用的共享数据 |
| 指针接收者中重新赋值，却没替调用方换对象 | 修改的是接收者指针副本，还是它指向的字段 |
| `c.Update()` 可以，赋给接口却报错 | 直接调用是否用了自动取址；接口要求的方法是否属于 `T` |
| map 中的结构体不能直接调用修改方法 | 元素是否不可寻址；是否应取出修改再写回或改为保存指针 |
| 保存的方法读到旧字段值 | 方法值形成时是否已复制值接收者 |
| 指针改指向后，原方法值仍修改旧对象 | 方法值保存的是形成时的指针 |
| 错误指针是 nil，但 `err != nil` | 接口是否仍保存了具体动态类型 |
| 方法签名满足标准接口，但调用行为不正确 | 除签名外，是否遵守复制、错误、短写、资源和并发等接口约定 |

做一次完整判断时，可以依次写出：接收者的实际类型、调用表达式是否可寻址、方法调用复制的值、方法体真正写入的位置，以及接口需要哪些方法。把这几项逐项对应起来，才能准确解释方法为什么可调用、数据为什么会变化，以及同一个结构体为什么有时需要传值、有时需要传指针。

## 三、嵌套结构体

一个真实对象往往包含几组性质不同的数据。例如，调用方有姓名，也有地址；任务有任务名称，也需要一个记录日志的组件。把全部字段塞进一个很大的结构体虽然能运行，却可能模糊“哪几个字段属于同一个概念”。本章学习用已有类型组织新类型，并准确判断字段访问、方法调用和初始化会发生什么。

这里先区分三个词：**嵌套**描述一个结构体的字段又包含另一个结构体；**嵌入**是 Go 中省略显式字段名的特定声明形式；**组合**是通过持有、调用其他对象来构建功能的设计方式。前两者可以参与组合，但组合并不要求一定使用嵌入。规则依据见 [Struct types](https://go.dev/ref/spec#Struct_types) 与 [Effective Go：Embedding](https://go.dev/doc/effective_go#embedding)。

<a id="section-3-1"></a>

### 3.1 嵌套结构体

<a id="heading-033"></a>

#### 命名字段：把子对象的含义写在访问路径上

字段写成 `Home Address` 时，`Home` 是字段名，`Address` 是字段类型。访问城市需要写 `user.Home.City`：先从调用方中找到家庭地址，再读取城市。这个路径既说明存储关系，也说明业务含义。同一个类型可以在不同字段中反复使用，例如同时声明 `Home Address` 和 `Office Address`。

**示例 E-01：用命名字段组织调用方和地址。** 本例按结构体字段及赋值规则编写。

```go
// 运行示例：E-01
package main

import "fmt"

type Address struct {
	City       string
	PostalCode string
}

type User struct {
	Name string
	Home Address
}

func main() {
	original := User{
		Name: "Lin",
		Home: Address{
			City:       "Hangzhou",
			PostalCode: "310000",
		},
	}
	copied := original
	copied.Home.City = "Suzhou"

	fmt.Println("original:", original.Name, original.Home.City)
	fmt.Println("copy:", copied.Name, copied.Home.City)
	fmt.Println("postal:", original.Home.PostalCode)
}
```

输出：

```text
original: Lin Hangzhou
copy: Lin Suzhou
postal: 310000
```

`copied := original` 复制整个 `User` 值，也复制其中的 `Address` 值。修改副本的城市字段不会改写原来的城市字段。这个结论针对本例的字段：若地址里还有切片、map 或指针，复制那些字段值后，关联的数据仍可能共享；“结构体里套结构体”不会自动把整个对象图都深拷贝。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)、[Representation of values](https://go.dev/ref/spec#Representation_of_values)。

命名嵌套还可以表达递归关系，但不能让一个类型按值无限包含自身。例如链表节点应使用 `Next *Node` 指向下一个节点；直接声明 `Next Node` 会使节点大小无法确定，属于不合法的递归类型。这不是“只能嵌套一层”的限制，而是不能沿着只有结构体和数组的路径无限展开自己。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)。

<a id="heading-034"></a>

#### 嵌入字段：字段名隐含在类型名中

把 `Contact Contact` 简化成只写 `Contact`，声明的就是**嵌入字段**，旧资料也常称“匿名字段”。它实际上有字段名：未带包名前缀的类型名就是字段名。因此嵌入 `Contact` 后，仍可以通过 `member.Contact` 访问完整子对象；嵌入 `*Contact` 时，字段名同样是 `Contact`。

当访问路径没有歧义时，Go 允许把嵌入对象的字段或方法提升到较短的选择路径。例如 `member.Contact.Email` 可以写成 `member.Email`。**提升**指选择和调用上的便利，不表示内层数据被移动到了一个独立的新字段中。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)、[Selectors](https://go.dev/ref/spec#Selectors)。

**示例 E-02：长路径与短路径访问同一个字段。**

```go
// 运行示例：E-02
package main

import "fmt"

type Contact struct {
	Email string
}

type Member struct {
	Contact
	Name string
}

func main() {
	member := Member{
		Contact: Contact{Email: "old@example.com"},
		Name:    "Lin",
	}
	fmt.Println(member.Email == member.Contact.Email)
	member.Email = "new@example.com"
	fmt.Println(member.Contact.Email)
	fmt.Printf("%T %T\n", member, member.Contact)
}
```

输出：

```text
true
new@example.com
main.Member main.Contact
```

`member` 仍然是 `Member`，它的 `Contact` 字段仍然是 `Contact`。短路径访问不会把两个类型合并，也不会使 `Member` 自动成为 `Contact` 的另一种写法。需要一个 `Contact` 参数时，可以明确传入 `member.Contact`。

也不能仅根据“访问时少写了一层”推断内存布局改变了。按值嵌入时，内层结构体值是外层字段的一部分；嵌入指针时，外层保存的是指针，实际对象位于它所指向的位置。字段偏移、对齐和结构体总大小仍按第一章介绍的布局规则分析。选择路径描述怎样找到字段，物理布局描述这些字段占用哪些位置，两者相关，却不是同一个问题。

嵌入字段的声明也有约束：通常写类型名 `T`，或者指向非接口类型的 `*T`；`T` 本身不能是指针类型或类型参数。不能直接嵌入无名称的 `[]int`，也不能用 `**T` 代替上述形式。由于 `T` 与 `*T` 产生相同的字段名，在同一个结构体中同时嵌入二者会形成字段名冲突。嵌入也不会绕过包的导出规则，来自其他包的未导出字段不会因此变为公开字段。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)、[Exported identifiers](https://go.dev/ref/spec#Exported_identifiers)。

<a id="heading-035"></a>

#### 同名字段：先看深度，再判断是否唯一

选择器就是 `x.Field` 或 `x.Method` 中用来选择字段、方法的名字。规范用“深度”描述沿嵌入字段走了多少层：外层直接声明的字段深度为 0，经过一层嵌入找到的字段深度为 1，以此类推。选择短名字时，先选择最浅层；如果最浅层同时有多个同名候选，表达式就有歧义，不能随意挑其中一个。[官方依据：Selectors](https://go.dev/ref/spec#Selectors)。

**示例 E-03：显式路径解决歧义，外层字段优先于更深层字段。**

```go
// 运行示例：E-03
package main

import "fmt"

type Home struct{ City string }
type Office struct{ City string }

type Locations struct {
	Home
	Office
}

type Person struct {
	Locations
	City string
}

func main() {
	locations := Locations{
		Home:   Home{City: "Hangzhou"},
		Office: Office{City: "Shanghai"},
	}
	fmt.Println(locations.Home.City, locations.Office.City)
	// fmt.Println(locations.City) // 错误示意：两个同深度的 City 有歧义。

	person := Person{Locations: locations, City: "Shenzhen"}
	fmt.Println(person.City)
	fmt.Println(person.Locations.Office.City)
}
```

输出：

```text
Hangzhou Shanghai
Shenzhen
Shanghai
```

`Locations` 同时嵌入 `Home` 和 `Office` 本身合法，冲突发生在试图使用含糊的 `locations.City` 时。明确写出路径就能选择具体字段。`Person` 又直接声明了 `City`，所以 `person.City` 选择深度为 0 的字段；内层两个城市并没有被删除，完整路径仍然可用。

字段和方法都遵循相应的选择规则。因此，给一个公开结构体增加新的嵌入类型时，也要检查它是否带来新的名字冲突。便利的短路径会成为调用方实际使用的 API，不能只看新增字段在本文件里是否能编译。

<a id="heading-036"></a>

#### 初始化提升字段：注意 Go 1.27 的规则变化

结构体字面量可以使用符合规则的提升字段名。为使对象组成关系清晰，E-02 仍采用显式写法 `Member{Contact: Contact{Email: "..."}}`；旧语言模式的限制另作为版本差异说明。

**从 Go 1.27 起，这个限制已有变化：合法的提升字段可以用作结构体字面量的 key，但到达该字段的嵌入路径不能经过指针类型，也不能同时指定相互重叠的内外层字段。** 因此不能再把“提升字段永远不能用于字面量初始化”写成无版本条件的规则。[官方依据：Composite literals](https://go.dev/ref/spec#Composite_literals)、[Go 1.27 Release Notes](https://go.dev/doc/go1.27)。

**示例 E-04：Go 1.27 中直接初始化非指针嵌入的提升字段。** 这是单独标注语言版本的例子；若在本地运行，应将该示例的 `go.mod` 设为 `go 1.27` 或更高。

```go
// 运行示例：E-04
// 运行基线：Go 1.27.3（模块声明 go 1.27.0）
package main

import "fmt"

type Contact struct {
	Email string
	Phone string
}

type Member struct {
	Contact
	Name string
}

func main() {
	current := Member{Name: "Lin", Email: "lin@example.com"}
	nested := Member{
		Name:    "Lin",
		Contact: Contact{Email: "lin@example.com"},
	}
	fmt.Println(current.Name, current.Email)
	fmt.Printf("phone=%q equal=%t\n", current.Phone, current == nested)
}
```

输出：

```text
Lin lin@example.com
phone="" equal=true
```

两种写法构造了相同的字段值，省略的 `Phone` 仍是字符串零值。下面的局部写法在 Go 1.27 中仍不合法，它们分别违反重叠字段和指针路径规则；只作为错误示意，不与完整程序一起运行：

```go
// 错误：Contact 已整体指定，又重复指定其内部的 Email。
// Member{Contact: Contact{Email: "a"}, Email: "b"}

type PointerMember struct{ *Contact }
// 错误：到 Email 的提升路径经过 *Contact。
// PointerMember{Email: "a"}

// 合法写法仍然是显式创建并填入该指针字段。
// PointerMember{Contact: &Contact{Email: "a"}}
```

字面量可用的名字还要满足普通选择器的唯一性与可见性条件。遇到 E-03 那样的同层冲突时，新版本不会替开发者猜一个字段。需要兼容较早语言版本、或者希望把对象的组成关系写得更明显时，逐层显式初始化依然适用。

<a id="heading-037"></a>

#### 嵌入指针：方法存在与对象已初始化是两件事

嵌入 `T` 时，外层零值直接包含一个 `T` 的零值；嵌入 `*T` 时，外层零值包含的是 nil 指针。后者不会自动替开发者创建一个 `T`。读取其字段通常需要先让指针指向有效对象，不过一个明确处理 nil 的指针接收者方法，可以合法接收到 nil 并自行决定结果。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)、[Selectors](https://go.dev/ref/spec#Selectors)、[Method calls](https://go.dev/ref/spec#Calls)。

**示例 E-05：显式区分未设置的组件与已设置的组件。**

```go
// 运行示例：E-05
package main

import "fmt"

type Metadata struct{ Label string }

func (m *Metadata) Name() string {
	if m == nil {
		return "(missing)"
	}
	return m.Label
}

type Item struct{ *Metadata }

func main() {
	var item Item
	fmt.Println(item.Metadata == nil)
	fmt.Println(item.Name())
	// fmt.Println(item.Label) // 此时会因读取 nil 指针指向的字段而 panic。

	item.Metadata = &Metadata{Label: "ready"}
	fmt.Println(item.Label, item.Name())
}
```

输出：

```text
true
(missing)
ready ready
```

第一次调用等价于沿嵌入字段调用 `item.Metadata.Name()`；方法收到 nil 后返回缺省文本，没有读取字段。它并不能证明“nil 嵌入指针的任意方法都可安全调用”：方法体若解引用 nil，仍会 panic；若调用必须先取得一个 `Metadata` 值的值接收者方法，也可能在进入方法之前就因解引用 nil 出错。

本例中的外层 `item` 是实际存在的结构体值。若外层本身是 nil `*Item`，为了找到它内部的 `Metadata` 字段就需要访问一个不存在的外层对象，不能照搬这里的成功路径。判断 nil 问题时，应从外到内沿实际访问路径检查。

<a id="section-3-2"></a>

### 3.2 组合结构

组合的出发点是“这个对象使用哪些能力”。例如报告器需要一个写入目标，但不必把写入目标的所有方法都公开；一个任务可能希望直接提供日志方法，此时嵌入日志组件又能减少转发代码。两种方式都通过已有组件构建功能，只是对外暴露的接口不同。

<a id="heading-039"></a>

#### 提升的方法怎样进入方法集合

方法集合决定一个类型具有哪些方法，也影响它能否实现接口。假设 `T` 既有值接收者方法，也有指针接收者方法；再假设没有同名冲突或外层遮蔽，那么提升规则如下。[官方依据：Struct types](https://go.dev/ref/spec#Struct_types)、[Method sets](https://go.dev/ref/spec#Method_sets)。

| 外层声明 | 外层值 `S` 的提升方法 | 外层指针 `*S` 的提升方法 |
| --- | --- | --- |
| `type S struct { T }` | 接收者为 `T` 的方法 | 接收者为 `T` 和 `*T` 的方法 |
| `type S struct { *T }` | 接收者为 `T` 和 `*T` 的方法 | 接收者为 `T` 和 `*T` 的方法 |
| `type S struct { Part T }` | 不因该命名字段自动获得方法 | 不因该命名字段自动获得方法 |

第二行讨论的是类型上有哪些方法，**不是保证 nil 指针也能完成这些方法的工作**。第一行则要与“可寻址变量的调用允许自动取址”区分开：变量能写 `s.PointerMethod()`，不代表类型 `S` 的方法集合因此增加了该方法。

**示例 E-06：对照嵌入值与嵌入指针的接口实现。**

```go
// 运行示例：E-06
package main

import "fmt"

type Counter struct{ N int }

func (c Counter) Value() int { return c.N }
func (c *Counter) Inc()      { c.N++ }

type ByValue struct{ Counter }
type ByPointer struct{ *Counter }

type Reader interface{ Value() int }
type Incrementer interface{ Inc() }

func show(label string, value any) {
	_, canRead := value.(Reader)
	_, canIncrement := value.(Incrementer)
	fmt.Println(label, canRead, canIncrement)
}

func main() {
	value := ByValue{Counter: Counter{N: 1}}
	pointer := ByPointer{Counter: &Counter{N: 10}}
	show("ByValue:", value)
	show("*ByValue:", &value)
	show("ByPointer:", pointer)
	show("*ByPointer:", &pointer)

	value.Inc()
	pointer.Inc()
	fmt.Println("after:", value.Value(), pointer.Value())
}
```

输出：

```text
ByValue: true false
*ByValue: true true
ByPointer: true true
*ByPointer: true true
after: 2 11
```

`value.Inc()` 成功，是因为这里的 `value` 是可寻址变量，调用可以利用它的地址；传给 `show` 的 `ByValue` 值却仍不实现 `Incrementer`。`ByPointer` 则把 `*Counter` 的方法提升进值类型的方法集合，所以它的值也实现该接口。代码先初始化了嵌入指针，确保真正调用时有计数器可以修改。

复制 `ByValue` 会复制内部计数器值；复制 `ByPointer` 会复制指针，从而让副本继续引用同一个计数器。若决定用指针组件来让多个外层对象共享状态，还应另外设计并发访问规则；方法提升本身不会为共享状态加锁。

方法是否需要自动取址，还会影响某些表达式能否调用。例如 `map[string]ByValue` 的元素不是可寻址变量，不能仅凭上例中局部变量能调用 `Inc` 就推断 map 元素也可以。可改为取出值、修改后赋回，或者明确存放指针。若存放的是带已初始化 `*Counter` 的 `ByPointer` 值，`Inc` 已经属于其值类型的方法集合，调用不需要先取得外层 map 元素的地址。这种差异应由方法集合和实际引用关系解释，不是 map 为某种结构体额外提供了特殊待遇。[官方依据：Calls](https://go.dev/ref/spec#Calls)、[Index expressions](https://go.dev/ref/spec#Index_expressions)。

<a id="heading-040"></a>

#### 嵌入不产生传统的继承与虚方法覆盖

Go 的嵌入允许外层以更短路径使用内层方法，但调用提升方法时，接收者仍然是那个内层对象。外层声明同名方法会影响外层选择该名字的结果，却不会让内层已经编写的方法自动改为调用外层版本。Effective Go 对这个区别有明确说明。[官方依据：Effective Go：Embedding](https://go.dev/doc/effective_go#embedding)。

**示例 E-07：外层同名方法不会改写内层方法的接收者。**

```go
// 运行示例：E-07
package main

import "fmt"

type Base struct{}

func (Base) Name() string { return "base" }

func (b Base) Describe() string {
	return "description=" + b.Name()
}

type Derived struct{ Base }

func (Derived) Name() string { return "derived" }

func main() {
	value := Derived{}
	fmt.Println(value.Name())
	fmt.Println(value.Describe())
	fmt.Println(value.Base.Name())

	var named interface{ Name() string } = value
	fmt.Println("interface:", named.Name())
}
```

输出：

```text
derived
description=base
base
interface: derived
```

第二行最关键：`value.Describe()` 选择的是提升的 `Base.Describe`，实际接收者为 `value.Base`。方法体中的 `b` 是 `Base`，所以 `b.Name()` 仍调用 `Base.Name`。最后一行则是通过接口调用，接口保存的动态值类型为 `Derived`，其 `Name` 方法返回 `derived`。这两条调用路径不同，不能把接口分派的规则套到所有嵌入调用上。[官方依据：Selectors](https://go.dev/ref/spec#Selectors)。

名字 `Derived` 只是为了对比其他语言中容易产生的直觉，并不表示 Go 把它当成 `Base` 的子类。函数需要 `Base` 时，不能仅因嵌入关系直接传 `Derived`；应传 `value.Base`，或将函数参数设计为真正需要的接口。如果确实要让内部逻辑使用可替换的行为，应显式传入接口或函数，而不是期待嵌入自动提供动态覆盖。

<a id="heading-041"></a>

#### 命名组件与接口：明确选择向外提供什么

`io.Writer` 是标准库定义的写入能力接口，核心方法为 `Write([]byte) (int, error)`。一个只需要输出文本的报告器可以持有 `io.Writer`，实际目标既可以是内存缓冲区，也可以是其他满足接口的对象。字段有自己的名称，报告器只公开业务所需的 `Report` 方法。[官方依据：io.Writer](https://pkg.go.dev/io#Writer)。

**示例 E-08：使用命名字段组合报告器与写入目标。** 本例的业务组织为讲解编写，写入接口和缓冲区用法依据标准库文档。

```go
// 运行示例：E-08
package main

import (
	"bytes"
	"errors"
	"fmt"
	"io"
)

type Reporter struct {
	Destination io.Writer
	Prefix      string
}

func (r Reporter) Report(message string) error {
	if r.Destination == nil {
		return errors.New("missing writer")
	}
	_, err := fmt.Fprintf(r.Destination, "%s%s\n", r.Prefix, message)
	return err
}

func main() {
	var output bytes.Buffer
	reporter := Reporter{Destination: &output, Prefix: "status: "}
	if err := reporter.Report("ready"); err != nil {
		fmt.Println(err)
		return
	}
	fmt.Print(output.String())
	fmt.Println("missing:", (Reporter{}).Report("unused"))
}
```

输出：

```text
status: ready
missing: missing writer
```

一次调用依次经过 `Reporter.Report`、`fmt.Fprintf` 和实际目标 `*bytes.Buffer` 的写入方法，文本存入缓冲区，最后由 `output.String()` 读取出来。`bytes.Buffer` 的零值就可以使用，因此这里不需要额外构造函数；使用它也避免了文件和网络依赖。[官方依据：bytes.Buffer](https://pkg.go.dev/bytes#Buffer)、[fmt.Fprintf](https://pkg.go.dev/fmt#Fprintf)。

`Reporter` 不会因为字段保存了缓冲区就自动获得 `Read`、`Reset` 等方法。调用方看到的是我们显式声明的业务方法，这适用于只希望暴露组件部分能力的情况。这里的 nil 检查只检查接口本身是否为 nil；调用方仍应提供有效的写入对象，不能把“装着 nil 指针的非 nil 接口”当成已通过对象有效性检查，相关机制见第二章。

还应把“谁使用组件”和“谁负责组件的生命周期”分别写清楚。本例由 `main` 创建缓冲区，`Reporter` 只借用写入能力；`io.Writer` 接口没有 `Close`，因此报告器也没有据此关闭目标的依据。如果将来换成文件，通常由创建文件的调用方安排关闭，除非接口契约明确把所有权移交给报告器。组合让功能可以替换，但不会替程序决定资源由谁释放。[官方依据：io.Writer](https://pkg.go.dev/io#Writer)、[io.Closer](https://pkg.go.dev/io#Closer)。

`Report` 使用值接收者时，复制的是 `Reporter` 中的字段值。`Destination` 接口所保存的动态值为 `*bytes.Buffer`，复制接口后仍指向同一个缓冲区，所以写入不会消失在一个临时副本中。这个例子也再次说明：值接收者并不等于“没有外部可观察的修改”，要继续追踪字段里的引用。

<a id="heading-042"></a>

#### 嵌入组件：在需要公开它的能力时减少转发

下面参考 Effective Go 的 `Job` 嵌入 `*log.Logger` 示例，改用内存缓冲区作为输出目标，并去掉时间戳，使结果可重复。`Logger` 负责日志格式与写入，`Job` 增加任务名称；外层只为 `Printf` 增加任务前缀，其他日志方法仍通过提升提供。[官方改编来源：Effective Go：Embedding](https://go.dev/doc/effective_go#embedding)、[log.New](https://pkg.go.dev/log#New)。

**示例 E-09：嵌入日志组件，并显式扩展一个方法。**

```go
// 运行示例：E-09
package main

import (
	"bytes"
	"fmt"
	"log"
)

type Job struct {
	Command string
	*log.Logger
}

func (job *Job) Printf(format string, args ...any) {
	job.Logger.Printf("%s: %s", job.Command, fmt.Sprintf(format, args...))
}

func main() {
	var output bytes.Buffer
	job := Job{
		Command: "import",
		Logger:  log.New(&output, "job ", 0),
	}
	job.Printf("rows=%d", 3)
	job.Println("done")
	fmt.Print(output.String())
}
```

输出：

```text
job import: rows=3
job done
```

`job.Printf` 首先选择外层声明的方法，它再显式调用 `job.Logger.Printf` 完成输出。`job.Println` 则直接选择提升的日志方法，所以不会自动加上外层 `Printf` 特有的 `import:` 前缀。若业务要求所有日志都统一带任务信息，就要在日志组件的固定前缀、统一业务入口或完整包装中实现该约定，不能只改一个同名方法后推断其他方法也改变了。

嵌入还会让其他可提升的日志方法进入外层 API。设计时应确认这些能力确实适合任务对象；如果只需要一种受限输出行为，E-08 的命名组件方式更便于控制。选择依据是希望外层提供什么能力，不是“少写一个字段名就一定更好”。

<a id="section-3-3"></a>

### 3.3 嵌套结构体与组合的区别

原目录把“嵌套结构体”和“组合”分开列出，适合用来对比写法，但不要把它们理解为互斥的两种 Go 类型。嵌套主要描述数据形状，组合主要描述职责如何协作；嵌入是 Go 为字段和方法选择提供的具体机制。可以按下面的维度比较。

| 问题 | 命名字段嵌套，如 `Part T` | 嵌入字段，如 `T` 或 `*T` |
| --- | --- | --- |
| 是否持有一个组件 | 是 | 是 |
| 是否保留独立的内层对象边界 | 是，通过 `x.Part` 访问 | 是，通过 `x.T` 访问 |
| 怎样访问内层字段 | 通常写完整路径 `x.Part.F` | 无歧义时可用提升路径 `x.F` |
| 内层方法是否自动进入外层方法集合 | 不会；需要时显式转发 | 按值、指针和名字解析规则提升 |
| 是否一定独立复制内层状态 | 取决于字段是值还是引用 | 同样取决于嵌入的是值还是指针及更深层字段 |
| 是否使外层成为内层的子类型 | 不会 | 不会 |
| 对外 API 的控制 | 可逐个决定开放什么 | 需要评估被提升的所有可见能力与冲突 |
| 能否用于组合设计 | 可以 | 可以 |

来源：[Struct types](https://go.dev/ref/spec#Struct_types)、[Selectors](https://go.dev/ref/spec#Selectors)、[Effective Go：Embedding](https://go.dev/doc/effective_go#embedding)。

例如，订单包含“收货地址”和“账单地址”，命名字段能清楚表达两种角色；把同一个 `Address` 嵌入两次不仅无法表达角色，还会发生字段名冲突。相反，如果一个新类型明确希望拥有某个组件的整组公开方法，嵌入可以省去机械转发。无论使用哪一种形式，初始化、错误处理和对象生命周期都需要自己安排。

也不要把嵌入与定义新类型混淆：`type MyBuffer bytes.Buffer` 定义了一个新的具名类型，不会自动继承 `bytes.Buffer` 的方法；`type MyBuffer struct{ bytes.Buffer }` 则通过嵌入获得符合规则的提升方法。`type MyBuffer = bytes.Buffer` 又是别名，指向同一个类型。这三种声明解决的事情不同，阅读项目时先确认使用了哪一种。[官方依据：Type definitions](https://go.dev/ref/spec#Type_definitions)、[Alias declarations](https://go.dev/ref/spec#Alias_declarations)。

<a id="heading-044"></a>

#### JSON 是另一个要单独确认的可观察结果

字段在 Go 中怎样选择，与编码成 JSON 后怎样排列，是不同层面的规则。`encoding/json` 默认通常把嵌入结构体的可导出字段放进外层 JSON 对象；命名结构体字段通常保留一层嵌套对象。给嵌入字段设置明确 JSON 名称，又可以让它按该名称编码为一个字段。[官方依据：encoding/json.Marshal](https://pkg.go.dev/encoding/json#Marshal)。

**示例 E-10：同一份地址数据，两种结构组织得到不同 JSON 层级。**

```go
// 运行示例：E-10
package main

import (
	"encoding/json"
	"fmt"
)

type Address struct {
	City string `json:"city"`
}

type Named struct {
	Name     string  `json:"name"`
	Location Address `json:"address"`
}

type Embedded struct {
	Name string `json:"name"`
	Address
}

func printJSON(label string, value any) {
	data, err := json.Marshal(value)
	if err != nil {
		panic(err)
	}
	fmt.Printf("%s: %s\n", label, data)
}

func main() {
	address := Address{City: "Hangzhou"}
	printJSON("named", Named{Name: "Lin", Location: address})
	printJSON("embedded", Embedded{Name: "Lin", Address: address})
}
```

输出：

```text
named: {"name":"Lin","address":{"city":"Hangzhou"}}
embedded: {"name":"Lin","city":"Hangzhou"}
```

因此，把命名字段改成嵌入字段，可能在业务代码仍能编译的同时改变对外数据格式。JSON 的字段冲突处理还受标签、层级等规则影响，不能把普通 Go 选择器歧义的结论直接当作 JSON 编码结果。若通过方法提升让外层实现了 `json.Marshaler`，编码还可能转而调用该方法，而非逐字段生成对象；需要按接口和方法集合再次检查。[官方依据：encoding/json.Marshal](https://pkg.go.dev/encoding/json#Marshal)、[json.Marshaler](https://pkg.go.dev/encoding/json#Marshaler)。

阅读嵌套与组合代码时，可以按一个固定顺序判断：先找到每个实际字段，再确认它是值、指针还是接口；随后展开短选择路径，确定真正访问的对象；最后检查方法集合、初始化状态以及对外编码规则。这样既能看清代码复用了哪些实现，也能判断改动会影响哪些调用者。

<a id="chapter-4"></a>

## 四、特殊的结构体——空结构体

空结构体写作 `struct{}`，表示没有任何字段的结构体类型；`struct{}{}` 则是这个类型的一个值。它适合表达“只关心存在、发生或类型行为，不需要另外携带业务数据”。理解这一点以后，集合占位值、完成通知和并发名额计数就可以放在同一个框架下理解。

<a id="section-4-1"></a>

### 4.1 大小与内存地址

**空结构体值的大小为零。** 规范规定：如果结构体或数组不包含任何大小大于零的字段或元素，该类型大小为零。因此，`struct{}`、只含空结构体字段的结构体，以及 `[1000]struct{}`，都可以具有零字节的值大小。[官方依据：Size and alignment guarantees](https://go.dev/ref/spec#Size_and_alignment_guarantees)。

```go
// 运行示例：Z-01
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	a := struct{}{}
	b := struct{}{}
	var marks [1000]struct{}
	p := new(struct{})

	fmt.Println("empty size:", unsafe.Sizeof(a))
	fmt.Println("array size and length:", unsafe.Sizeof(marks), len(marks))
	fmt.Println("equal values:", a == b)
	fmt.Println("pointer is non-nil:", p != nil)
	fmt.Println("alignment at least one:", unsafe.Alignof(a) >= 1)
}
```

输出：

```text
empty size: 0
array size and length: 0 1000
equal values: true
pointer is non-nil: true
alignment at least one: true
```

数组仍有一千个逻辑元素，因此 `len` 为 1000、合法下标是 0 到 999；元素大小为零，不会取消索引边界。`a` 和 `b` 都是 `struct{}` 的值，由于没有任何不相等字段，二者相等。空结构体值本身也不是 nil；nil 用来描述指针、切片、map、通道等类型的特定零值，不能写 `struct{}{} == nil`。[官方依据：Array types](https://go.dev/ref/spec#Array_types)、[Comparison operators](https://go.dev/ref/spec#Comparison_operators)。

**大小为零，不代表只能存在一个变量，也不代表可以靠指针区分所有变量。** 规范允许不同零大小变量具有相同地址，并明确指出：指向不同零大小变量的指针可能相等，也可能不相等。下面是用于理解边界的片段，不给它指定跨实现固定输出：

```go
// 边界示意片段；不作为固定输出的完整示例。
var a, b struct{}
fmt.Println(&a == &b) // 不能据此建立“不同对象一定不等”的身份规则。
```

因此，不应使用 `*struct{}` 地址作为必须唯一的任务编号、注册标识或业务身份。打印地址、让变量逃逸到堆、改变编译选项，都可能影响具体实现的安排；语言没有承诺这些不同变量一定共享某个统一地址，也没有承诺它们一定不同。[官方依据：Comparison operators](https://go.dev/ref/spec#Comparison_operators)。

还要区分“元素值大小”与“容器整体成本”。一个切片仍然需要保存长度、容量等信息，一个 map 仍有键和索引结构，一个 channel 仍需要维护缓冲计数、同步状态和等待关系。把它们的元素类型换成 `struct{}`，表达的是元素不携带额外业务字段，不能据此声称整个容器或通信操作零成本。[官方说明：Slice types](https://go.dev/ref/spec#Slice_types)、[Map types](https://go.dev/ref/spec#Map_types)、[Channel types](https://go.dev/ref/spec#Channel_types)。

<a id="section-4-1-1"></a>

#### 4.1.1 结构体里面嵌入空结构体，占用空间怎么计算

本标题按本章结构被裁切的可见文字补全。这里“嵌入”先按日常含义理解为“把空结构体作为字段放入另一个结构体”，包含命名字段与嵌入字段；与第三章讨论的选择器提升是两个不同关注点。

**单个字段大小为零，不保证整个外层类型的大小不变。** 对本次 Go 1.27.3 标准编译器而言，非零大小结构体如果以零大小字段结尾，会先增加一个字节，再按结构体对齐要求取整。源码注释说明，这样避免对末尾零大小字段取地址时，产生指向堆中下一个对象的地址。这个处理属于具体实现，不能概括为“空结构体字段本身变成了一个字节”。[源码依据：CalcStructSize](https://go.dev/src/cmd/compile/internal/types/size.go)。

```go
// 运行示例：Z-02
// 以下具体布局数字按 Go 1.27.3 linux/amd64 记录。
package main

import (
	"fmt"
	"unsafe"
)

type EmptyOnly struct {
	A struct{}
	B struct{}
}

type AtStart struct {
	Marker struct{}
	Value  int64
}

type AtEnd struct {
	Value  int64
	Marker struct{}
}

type WithGuard struct {
	_     struct{}
	Value int64
}

func main() {
	var only EmptyOnly
	var first AtStart
	var last AtEnd
	var guard WithGuard
	fmt.Println("only empty fields:", unsafe.Sizeof(only))
	fmt.Println("at start size and offsets:", unsafe.Sizeof(first), unsafe.Offsetof(first.Marker), unsafe.Offsetof(first.Value))
	fmt.Println("at end size and offsets:", unsafe.Sizeof(last), unsafe.Offsetof(last.Value), unsafe.Offsetof(last.Marker))
	fmt.Println("marker field size:", unsafe.Sizeof(last.Marker))
	fmt.Println("guard first size:", unsafe.Sizeof(guard))
}
```

本次环境中的输出：

```text
only empty fields: 0
at start size and offsets: 8 0 0
at end size and offsets: 16 0 8
marker field size: 0
guard first size: 8
```

逐个推导：

| 类型 | 当前实现中的计算 | 本次结果 |
| --- | --- | ---: |
| `EmptyOnly` | 两个字段大小都为 0，整个类型也为 0 | 0 |
| `AtStart` | 空字段不向后推进偏移，int64 从偏移 0 开始 | 8 |
| `AtEnd` | int64 占 8 字节，零大小尾字段触发额外处理，再按 8 对齐取整 | 16 |
| `WithGuard` | 空白字段放在前面，后面的 int64 从偏移 0 开始 | 8 |

`AtEnd.Marker` 的 `Sizeof` 仍然是 0，改变的是外层结构体的布局。与此同时，`AtStart.Marker` 和 `AtStart.Value` 的偏移都为 0，也不矛盾：前者没有需要存放的字节，后者有八个字节的数据。这种结果不能用于推断所有字段都能任意重叠。

若使用的是 `[0]T` 这样的零长度数组字段，还要看它继承的元素对齐要求，不能把所有零大小类型都等同于 `struct{}` 的对齐。放在何处、外层是否已有非零字段、目标架构的对齐要求和编译器规则，都可能影响最终大小。检查时应同时输出 `Sizeof`、`Alignof` 和 `Offsetof`，而不只盯着空字段的大小。[官方依据：Size and alignment guarantees](https://go.dev/ref/spec#Size_and_alignment_guarantees)。

<a id="section-4-1-2"></a>

#### 4.1.2 空结构体的用途

下面几种用法的共同点是：需要一个合法的类型或值来占据某个语法位置，但不需要额外业务数据。具体效果来自包访问规则、map 规则或 channel 同步规则；空结构体只是其中一个部件。

<a id="section-4-1-2-1"></a>

##### 4.1.2.1 阻止 unkeyed 方式初始化结构体

`unkeyed` 指不写字段名、只按位置给值的结构体字面量，例如 `Point{3, 4}`。`keyed` 则显式写字段名，例如 `Point{X: 3, Y: 4}`。当一个包希望外部调用者使用字段名，以减少对字段顺序的依赖时，可以在导出的结构体中加入一个未导出的字段；`_ struct{}` 是不需要额外业务数据的一种写法。

原因分两步：无字段名形式需要提供与字段顺序对应的值；而外部包不能在结构体字面量中为另一个包的未导出字段指定元素。阻止外部按位置构造的是**字段可见性规则**，不是 `struct{}` 特有的初始化魔法。同包代码仍然可以使用完整的按位置写法，外部包也仍然可以用省略该字段的 keyed 字面量。[官方依据：Composite literals](https://go.dev/ref/spec#Composite_literals)、[Exported identifiers](https://go.dev/ref/spec#Exported_identifiers)。

**示例 Z-03：用两个包验证这条边界。** 这是一个完整多文件示例。三个文件如下：

| 文件 | 作用 |
| --- | --- |
| `go.mod` | 声明本示例模块路径及语言版本 |
| `api/options.go` | 定义导出的 Options 类型及包内构造函数 |
| `main.go` | 作为外部包使用 Options |

`go.mod`：

```mod
module example.com/ch06/z-03

go 1.27.0
```

`api/options.go`：

```go
// 示例附属文件：Z-03/api/options.go
package api

type Options struct {
	_              struct{}
	TimeoutSeconds int
}

func PositionalInsidePackage() Options {
	return Options{struct{}{}, 5}
}
```

`main.go`：

```go
// 运行示例：Z-03
// 多文件示例，需同时保存文中的 api/options.go 和 go.mod。
package main

import (
	"example.com/ch06/z-03/api"
	"fmt"
)

func main() {
	keyed := api.Options{TimeoutSeconds: 3}
	zero := api.Options{}
	inside := api.PositionalInsidePackage()
	fmt.Println(keyed.TimeoutSeconds, zero.TimeoutSeconds, inside.TimeoutSeconds)
}
```

在模块目录执行 `go run .`，输出：

```text
3 0 5
```

如果把外部包 `main` 中的一行改为下面的错误片段，编译器会拒绝为未导出字段进行这种位置赋值：

```go
// 故意错误的局部片段；不要放入上面的正确程序。
bad := api.Options{struct{}{}, 3}
_ = bad
```

这个设计有三个限制。第一，它不能强制所有调用者经过一个构造函数，因为 `api.Options{}` 和带字段名的部分初始化仍然允许。第二，调用方如果保留结构体值副本，并不会因这个空字段自动获得并发保护。第三，`_ struct{}` 并不是防止复制的检查标记；像 `sync.Mutex` 的不可复制约束以及 `go vet` 的相关检查，是另一套机制，不能靠这个空字段代替。

把空字段放在前面，还有助于避免本次实现中的“末尾零大小字段”布局影响；但它依然会改变字段列表，因此应在设计公开类型时一并考虑，而不是随意给已有公共 API 增加字段。源代码兼容性与内存字节数是两个不同问题。

<a id="section-4-1-2-2"></a>

##### 4.1.2.2 实现集合数据结构

集合只关心某个元素是否出现，不需要为每个元素另外记录一个业务值。`map[T]struct{}` 就可以把 map 的键作为集合元素，把空结构体作为占位值。例如 `map[string]struct{}` 表示一个字符串集合。

判断成员关系时使用 map 查询的第二个结果 `ok`，不要仅比较取出的值。对于 `struct{}`，不存在的键也会得到零值 `struct{}{}`，这个值本身与已存在键对应的值相同；只有 `ok` 能区分“存在”和“不存在”。这与官方 Go maps 博客用 map 建立集合的思路一致，本文把无需承载业务信息的值改为 `struct{}`。[官方依据：Go maps in action](https://go.dev/blog/maps)、[Index expressions](https://go.dev/ref/spec#Index_expressions)。

```go
// 运行示例：Z-04
package main

import (
	"fmt"
	"slices"
)

func main() {
	tags := make(map[string]struct{})
	for _, tag := range []string{"go", "rust", "go", "python"} {
		tags[tag] = struct{}{}
	}
	_, hasGo := tags["go"]
	_, hasJava := tags["java"]
	fmt.Println("members:", len(tags), hasGo, hasJava)

	delete(tags, "python")
	ordered := make([]string, 0, len(tags))
	for tag := range tags {
		ordered = append(ordered, tag)
	}
	slices.Sort(ordered)
	fmt.Println("after delete:", ordered)

	var nilSet map[string]struct{}
	_, exists := nilSet["go"]
	fmt.Println("nil map lookup:", exists)
}
```

输出：

```text
members: 3 true false
after delete: [go rust]
nil map lookup: false
```

重复加入 `go` 只会对同一个键赋值，所以初始成员数为 3。输出前单独排序，是因为 Go 不保证 map 的遍历顺序；不要把某次遍历顺序写成集合的固有顺序。nil map 可以查询和删除，但写入会 panic，故上面使用 `make` 创建可写集合。[官方依据：Map types](https://go.dev/ref/spec#Map_types)、[For statements](https://go.dev/ref/spec#For_statements)。

`T` 仍然必须满足 map 键的可比较要求；把值换成 `struct{}`，不会使 `[]int` 这样的类型突然可以当作键。如果使用 `map[string]bool` 表示集合，也应约定是按键是否存在，还是按布尔值 true 判断成员，否则写入 false 后会出现两种解释。`struct{}` 的优势首先是表达意图清楚，具体内存节省量要结合 map 的实现、键类型和规模测量，不能说整个集合“不占空间”。

##### 4.1.2.3 作为通道信号的传输

如果通道只需要表达“准备好了”“完成了”“可以继续了”，而不需要传递一段业务数据，可以使用 `chan struct{}`。发送时写 `ch <- struct{}{}`，接收时写 `<-ch`。空结构体值不携带字段，真正有意义的是这次发送、接收或关闭的事件。

开始前先区分两种协议：**发送一个值**通常供一次接收取走；**关闭通道**表示这个通道不会再发送值，缓冲中的值取完以后，所有接收都可得到零值及 `ok=false`。所以向同一通道发送一次，不等于通知每一位等待者一次；关闭专用通知通道则可以表达一次性的广播状态。[官方依据：Send statements](https://go.dev/ref/spec#Send_statements)、[Receive operator](https://go.dev/ref/spec#Receive_operator)、[Close](https://go.dev/ref/spec#Close)。

**示例 Z-05：用关闭通知发布已经完成的结果。** `done` 传递完成状态，`result` 保存业务结果；它们的职责不同。

```go
// 运行示例：Z-05
package main

import "fmt"

func main() {
	done := make(chan struct{})
	var result int

	go func() {
		result = 21 * 2
		close(done)
	}()

	<-done
	fmt.Println("result:", result)
	_, ok := <-done
	fmt.Println("receive after close:", ok)
}
```

输出：

```text
result: 42
receive after close: false
```

执行过程是：工作 goroutine 先写入 42，再关闭 `done`；主 goroutine 等到关闭事件后才读取 `result`。Go 内存模型规定，关闭通道先于因通道已关闭而返回零值的接收操作完成，这使前面的结果写入与后面的读取建立了同步关系。主 goroutine 不需要用一段猜测长度的 `Sleep` 等待任务。[官方依据：The Go Memory Model，Channel communication](https://go.dev/ref/mem#chan)。

这个同步只覆盖已经安排好的操作顺序。如果工作 goroutine 关闭 `done` 后又继续并发修改 `result`，上面的通知不能自动保护后续访问；仍需另行同步。还要注意第二次接收立即返回 `ok=false`，关闭后的空通道不会“重新变成未完成状态”。

**示例 Z-06：一个开始通知释放多个等待者。** 根据官方 pipelines 博客中关闭 `done` 作为广播的机制，改为统一开始信号，并使用 `sync.WaitGroup` 等待所有结果完成。

```go
// 运行示例：Z-06
package main

import (
	"fmt"
	"sync"
)

func main() {
	start := make(chan struct{})
	results := make([]int, 3)
	var wg sync.WaitGroup
	wg.Add(len(results))

	for i := range results {
		go func(index int) {
			defer wg.Done()
			<-start
			results[index] = (index + 1) * 10
		}(i)
	}

	close(start)
	wg.Wait()
	fmt.Println(results)
}
```

输出：

```text
[10 20 30]
```

每个 worker 都接收同一个已关闭通道，因此即使某个 worker 稍晚才执行到 `<-start`，它也能继续。不同 worker 写入结果切片的不同元素，主 goroutine 在 `Wait` 返回后统一读取；输出顺序由元素索引确定，不依赖 goroutine 谁先被调度。这里的开始广播和完成等待是两个方向的同步，不能仅关闭 `start` 后立刻假定所有工作已经完成。[官方依据：Go Concurrency Patterns: Pipelines and cancellation](https://go.dev/blog/pipelines)、[sync.WaitGroup](https://pkg.go.dev/sync#WaitGroup)。

关闭通知通道通常由一个明确的责任方完成。本例由主 goroutine 关闭 `start`；Z-05 由唯一工作 goroutine 关闭 `done`。重复关闭会 panic，向已关闭通道发送也会 panic；不能因为元素没有字段就忽略通道生命周期。若多个调用方都可能触发相同关闭，应重新设计所有权，或者在确有需求时使用 `sync.Once` 这样的单次执行工具。[官方依据：Close](https://go.dev/ref/spec#Close)、[sync.Once](https://pkg.go.dev/sync#Once)。

**示例 Z-07：用带缓冲通道表示有限个并发名额。** 缓冲容量为 2，获取名额时发送一个空结构体，归还时取出一个。缓冲已满时，下一次发送等待，因此最多同时持有两个名额。这个模式来自官方内存模型和 Effective Go 中的有界并发思路。

```go
// 运行示例：Z-07
package main

import (
	"fmt"
	"sync"
)

func main() {
	slots := make(chan struct{}, 2)
	results := make([]int, 6)
	var wg sync.WaitGroup

	for i := range results {
		slots <- struct{}{}
		wg.Add(1)
		go func(index int) {
			defer wg.Done()
			defer func() { <-slots }()
			results[index] = index * index
		}(i)
	}

	wg.Wait()
	fmt.Println("capacity and occupied:", cap(slots), len(slots))
	fmt.Println("results:", results)
}
```

输出：

```text
capacity and occupied: 2 0
results: [0 1 4 9 16 25]
```

`slots` 中保存的不是某个任务的数据，而是“正在使用一个名额”的占位值。工作函数结束时，后注册的归还动作先执行，再调用 `Done`；因此 `Wait` 返回后占用数为 0。这个程序保证最多两个 worker 同时持有名额，不保证它们一定在两个 CPU 核上同时执行，也不保证每一时刻恰好有两个 worker 在工作。[官方依据：The Go Memory Model](https://go.dev/ref/mem#chan)、[Effective Go：Channels](https://go.dev/doc/effective_go#channels)、[Defer statements](https://go.dev/ref/spec#Defer_statements)。

这个通道不需要为了“清理”而关闭：它不承担结束广播，所有任务结束后也没有等待者。给表示名额的通道随意增加关闭操作，反而可能破坏发送和归还协议。实际项目中如果获取名额还需要响应取消，应使用 `select` 同时等待名额和取消信号；这里先把基本计数关系讲清楚。

##### 4.1.2.4 空结构体和 channel 联合使用：阻塞、等待与退出

本小节按本章结构可见的“联合使用阻塞程序”主题扩展。关键不只是“让程序停住”，而是说明**谁在等、等什么事件、由谁发出事件、等到后如何退出**。一个没有生产者、没有关闭方、也没有取消路径的等待，可能使 goroutine 永远无法完成。

下面使用三个通知通道，分别表达“worker 已启动”“请求停止”“worker 已退出”。这三个状态分开，才能明确区分发出停止请求和已经停止。

```go
// 运行示例：Z-08
package main

import "fmt"

func main() {
	ready := make(chan struct{})
	stop := make(chan struct{})
	exited := make(chan struct{})

	go func() {
		close(ready)
		<-stop
		fmt.Println("worker stopped")
		close(exited)
	}()

	<-ready
	fmt.Println("request stop")
	close(stop)
	<-exited
	fmt.Println("main exit")
}
```

输出：

```text
request stop
worker stopped
main exit
```

这里的顺序由通道协议保证，而不是由打印速度保证：主 goroutine 在收到 `ready` 后发出停止请求；worker 在 `stop` 关闭后继续，打印并通知退出；主 goroutine 等到 `exited` 后结束。关闭 `stop` 不会强行终止一个正在运行的 goroutine，worker 必须执行接收或 `select` 才能响应，这是**协作式取消**。

在更一般的服务调用链中，可以使用标准库 `context` 传递取消和超时信息，`Context.Done()` 本身就返回只读的 `struct{}` 通道。即使已经发出取消，若调用方需要确认清理结束，仍要等待明确的完成条件；“取消请求”和“完成确认”是两个不同状态。[官方依据：context.Context](https://pkg.go.dev/context#Context)、[Go Concurrency Patterns: Context](https://go.dev/blog/context)。

<a id="heading-053"></a>

#### 补充：不同通道状态怎样影响阻塞

| 通道状态 | 发送操作 | 接收操作 | 需要注意 |
| --- | --- | --- | --- |
| nil 通道 | 一直阻塞 | 一直阻塞 | 在 select 中对应分支不会就绪 |
| 打开的无缓冲通道 | 等待配对接收 | 等待配对发送 | 需要另一方参与 |
| 打开的有缓冲通道 | 缓冲满时等待 | 缓冲空时等待 | 是否阻塞取决于当时状态 |
| 已关闭且仍有缓冲值 | panic | 先取出已有值，`ok=true` | 关闭不会丢弃已缓冲的值 |
| 已关闭且缓冲已取空 | panic | 立即得到零值，`ok=false` | 反复接收仍立即返回 |

依据：[Channel types](https://go.dev/ref/spec#Channel_types)、[Send statements](https://go.dev/ref/spec#Send_statements)、[Receive operator](https://go.dev/ref/spec#Receive_operator)、[Select statements](https://go.dev/ref/spec#Select_statements)。

**示例 Z-09：nil 通道可以有意关闭一个 select 分支。** 这个例子不会永久阻塞，因为另一个通道已经关闭、其接收分支就绪。

```go
// 运行示例：Z-09
package main

import "fmt"

func main() {
	var disabled <-chan struct{}
	ready := make(chan struct{})
	close(ready)

	select {
	case <-disabled:
		fmt.Println("disabled")
	case _, ok := <-ready:
		fmt.Println("ready:", ok)
	}
}
```

输出：

```text
ready: false
```

相反，如果只对一个 nil 通道接收，或者写一个没有 case 的 `select {}`，当前 goroutine 就没有自行完成的机会。若整个程序所有 goroutine 都在等待且没有可恢复的进展来源，运行时可能报告死锁；不能把这种写法当成普遍可靠的程序生命周期管理方式。已经关闭的通道在循环 select 中持续就绪，还可能让循环忙转，通常需要返回、跳出循环，或在合适的协议中把该通道变量设为 nil。[官方依据：Select statements](https://go.dev/ref/spec#Select_statements)、[Go Concurrency Patterns: Pipelines and cancellation](https://go.dev/blog/pipelines)。

需要等一组任务结束时使用 `WaitGroup`；需要一次完成通知时使用有明确关闭方的 `done`；需要把取消沿调用链传播时使用 `context`。三者解决的问题可以同时存在，但都要写清楚状态变化和责任方。空结构体让“无业务载荷的信号”更清晰，并不会自动解决遗漏通知、重复关闭或任务无法退出的问题。

### A.3 参考答案与定位

**1．零值按字段类型递归确定。** v 是结构体零值；p 是 nil 指针；q 是指向结构体零值的非 nil 指针。这些写法都不会自动把内部 map 变成可写 map；仍需使用 `make` 或 map 字面量。构造函数可以提供业务默认值，但语言零值本身不会读取当前的业务配置。见 1.1。[规范：The zero value](https://go.dev/ref/spec#The_zero_value)、[Allocation](https://go.dev/ref/spec#Allocation)。

**2．前两项修改副本，第三项可能修改共享存储。** Count 和数组 Values 的元素作为结构体值的一部分被复制；Tags 复制的是切片值，通常仍关联同一个底层数组，因此写 `b.Tags[0]` 会被 a 观察到。给 b.Tags 重新赋一个独立切片则是另一种操作。见 I-08、M-03。[规范：Representation of values](https://go.dev/ref/spec#Representation_of_values)。

**3．map 索引结果不是一个可寻址结构体变量。** 第一种写法应取出为局部变量、修改局部字段，再整体赋回该键。第二种写法取出的是指针值，若非 nil，它仍可以引用一个可修改的独立对象；map 中键不存在时得到 nil，必须检查。见 I-09、M-06。[规范：Index expressions](https://go.dev/ref/spec#Index_expressions)、[Address operators](https://go.dev/ref/spec#Address_operators)。

**4．本次是 0、8、16，总大小 24。** B 放到最前面后，对应偏移为 0、8、9，总大小 16。字段内容仍合计 10 字节，但为了整体对齐还需要尾部填充。数字限定于本讲所用工具链和目标架构；通用分析方法是检查字段对齐、偏移和完整结构体大小。见 L-01、L-04。[文档：unsafe](https://pkg.go.dev/unsafe)。

**5．T 包含 Read，`*T` 包含 Read 和 Write。** 对可寻址变量，`v.Write()` 可以按调用规则取地址，但接口实现按类型的方法集合判断，不会为了满足接口自动把 T 换成 `*T`。因此要求 Write 的接口应接收 `&v`。这里讨论的是普通方法和没有额外提升的 T。见 M-10。[规范：Method sets](https://go.dev/ref/spec#Method_sets)、[Calls](https://go.dev/ref/spec#Calls)。

**6．字段、局部指针、整块目标值是三个不同写入位置。** `p.Field = 1` 修改 p 指向对象的字段；`p = &T{}` 只让方法内的指针副本改指向；`*p = T{}` 把零值写到 p 原先指向的位置。第一和第三种要求解引用有效，不能在 nil 指针上直接执行。见 M-04。[规范：Assignment statements](https://go.dev/ref/spec#Assignment_statements)。

**7．接口不等于 nil。** 它带有动态类型 `*Worker`，其动态值才是 nil 指针。接口自身为 nil 要求没有动态类型和值。是否可以调用方法，还要看实际方法路径及方法体是否明确支持 nil 接收者，不能仅靠 `interfaceValue != nil` 得出安全结论。见 M-12。[官方解释：Go FAQ](https://go.dev/doc/faq#nil_error)。

**8．形成方法值时保存接收者。** 值接收者保存当时的值副本；指针接收者保存指针值，后续可观察该指针所指对象的修改。即使是值副本，内部切片或 map 仍可能共享数据；给原来的指针变量改指向，也不会让已经保存的旧指针自动跟着变。见 M-07。[规范：Method values](https://go.dev/ref/spec#Method_values)。

**9．因为实际接收者仍是 Base。** 提升让调用路径更简洁，但不会把 Base 方法里的接收者变成外层类型，也不会自动提供传统继承中的虚方法覆盖。函数要求 Base 时，不能仅因外层嵌入了 Base 就直接传外层；可以显式传内层字段，或使用恰当的接口表达所需行为。见 E-07。[官方解释：Effective Go，Embedding](https://go.dev/doc/effective_go#embedding)。

**10．需要看语言版本和路径。** 在本文统一使用的 Go 1.27 语言模式下，符合条件的提升字段可作为结构体字面量键；旧语言版本的限制作为历史差异说明。到达该字段的嵌入路径不能经过指针，也不能同时初始化相互重叠的内外层字段。可直接写 `Outer{Inner: Inner{X: 1}}` 的显式形式来兼容旧语言模式。见 E-04。[规范：Composite literals](https://go.dev/ref/spec#Composite_literals)、[Go 1.27](https://go.dev/doc/go1.27)。

**11．外层布局还受到尾部处理和对齐影响。** 本次标准编译器为非零大小结构体末尾的零大小字段留出额外空间，再整体取整；空字段自己的大小仍是零。不同零大小变量的指针可能相等也可能不相等，不能据此设计唯一业务身份。见 Z-01、Z-02。[规范：Size and alignment guarantees](https://go.dev/ref/spec#Size_and_alignment_guarantees)、[源码：CalcStructSize](https://go.dev/src/cmd/compile/internal/types/size.go)。

**12．限制来自未导出字段的包边界。** 外部包的按位置形式需要给该字段提供元素，但不允许这样指定另一个包的未导出字段。同包代码不受这条跨包限制；外部仍可用带字段名的形式省略该字段，也可以构造整个结构体的零值。因此它既不是强制构造函数机制，也不是禁止复制或并发保护机制。见 Z-03。[规范：Composite literals](https://go.dev/ref/spec#Composite_literals)。

**13．不存在的键也返回值类型的零值。** 空结构体的零值与已存入的占位值无法凭内容区分，应使用 `_, ok := set[key]`。nil map 可以查询和删除，写入需要先初始化，否则 panic。见 Z-04。[规范：Map types](https://go.dev/ref/spec#Map_types)、[Index expressions](https://go.dev/ref/spec#Index_expressions)。

**14．一次值交付、持续关闭状态、取消意图和完成事实不同。** 一次发送通常由一次接收消耗；关闭使之后的接收者在取尽缓冲后都观察到已关闭状态。停止请求只有在 worker 检查时才生效，不会强行打断任意代码；退出确认表示 worker 已走到相应完成位置。Z-08 用 exited 等待真实退出，避免把“刚发出请求”当成“清理已经结束”。见 Z-05—Z-09。[官方依据：Go 内存模型](https://go.dev/ref/mem#chan)、[context.Context](https://pkg.go.dev/context#Context)。
